# 침해사고 분석 보고서

> 상위: [네트워크 보안 강의계획서](plan.md)

두 번째 달(9~16일차)에는 작업 계획서와 함께 침해사고 분석 보고서를 씁니다. 첫 달에 "남은 위험"으로 적어 두고 넘어간 틈이 실제 사고로 일어났을 때, 무엇을 보고 알았고 어떻게 막았는지를 남기는 문서입니다. 보안 관제와 침해사고 대응 직무에서 매일 쓰는 문서와 같은 모양이라, 네 건이 모이면 포트폴리오에서 가장 힘 있는 부분이 됩니다.

작업 계획서와 무엇이 다른지부터 봅니다.

| | 작업 계획서 | 침해사고 분석 보고서 |
|-|-------------|----------------------|
| 다루는 것 | 내가 바꿀 일 | 이미 일어난 일 |
| 쓰는 때 | 바꾸기 전 | 알아챈 뒤 |
| 답하는 질문 | 무엇을, 어떻게 확인하고, 어떻게 되돌리나 | 무엇이, 언제, 어떻게 일어났고, 무엇을 했나 |
| 근거 | 확인 방법의 기대하는 결과 | 캡처, 로그, 설정, 커밋 해시 |

## 1. 두 번째 달의 사고 네 건

주말마다 사고 하나를 다룹니다. 사고의 씨앗은 모두 첫 달에 뿌려 두었습니다.

| 사고 | 일차 | 무슨 일 | 처음 생긴 틈 | 알아챈 수단 | 막은 수단 |
|------|------|---------|--------------|-------------|-----------|
| 01 | 10 | 인수한 회사에서 인사팀으로 들어온 접근 | 7일차, 경로 필터만 둔 신뢰 경계 | 감시용 ACL의 적중 횟수와 로그 | 10일차 확장 ACL |
| 02 | 12 | 텔넷으로 오간 관리자 비밀번호 | 2일차, 비밀번호만 건 텔넷 VTY | Wireshark 캡처 | 12일차 SSH와 `username … secret` |
| 03 | 14 | 공개한 서비스로 들어온 포트 스캔과 로그인 시도 | 9일차, 밖으로 공개한 서비스 | 방화벽 로그 | 13, 14일차 방화벽 규칙 |
| 04 | 15 | IDS 경보 두 건의 정탐과 오탐 판정 | 15일차, 처음 켠 IDS | IDS 경보와 모니터링 | 15일차 규칙 조정 |

사고는 강사가 새봄상사로 먼저 일으켜 보이고, 학생은 자기 실습망에서 같은 사고를 일으켜 기록합니다. 공격 역할도 각자 구축한 실습 환경 안에서만 맡습니다. 허락받지 않은 시스템을 스캔하거나 트래픽을 캡처하는 것이 불법이라는 점은 1일차와 12일차의 고지 그대로입니다.

## 2. 언제 쓰나

| 때 | 쓰는 것 |
|----|---------|
| 사고가 있는 날, 개인 실습 60분 가운데 20분 | 요약, 탐지, 타임라인, 분석의 근거. 사실부터 적는다 |
| 다음 회차 작업 계획서 시간 | 원인, 재발 방지, 교훈을 다듬어 커밋 |
| 16일차 | 네 건을 `07_보고서/` 최종 보고서의 한 장으로 묶는다 |

증거(캡처, 로그, `show` 출력)는 사고가 있는 날 바로 저장합니다. 장비를 고친 뒤에는 고치기 전의 화면을 다시 볼 수 없습니다. 실제 사고 대응에서도 증거 보존이 가장 먼저입니다.

## 3. 문서의 흐름

보고서의 칸은 침해사고 대응 지침(NIST SP 800-61)의 네 단계를 따릅니다.

| 대응 단계 | 보고서의 칸 |
|-----------|-------------|
| 준비 | (사고 전에 한 일. 첫 달의 설계와 점검표가 여기에 해당) |
| 탐지와 분석 | 탐지, 타임라인, 분석, 영향 |
| 봉쇄, 근절, 복구 | 대응 |
| 사고 뒤 활동 | 원인, 재발 방지와 남은 위험, 교훈 |

심각도는 세 단계로 매깁니다.

| 심각도 | 기준 |
|--------|------|
| 상 | 중요 자산의 기밀성이나 무결성이 실제로 깨졌거나, 서비스가 멈췄다 |
| 중 | 중요 자산에 닿는 길이 열려 있었고, 실제 접근이 있었다 |
| 하 | 시도는 있었으나 막혔거나, 영향이 없었다 |

## 5. 새봄상사 예시: 사고 01

10일차에 강사가 함께 쓰는 예시입니다. 7일차 4번 노트의 "길을 숨겨도 문은 열려 있다"가 실제로 일어난 사고입니다. 강사는 10일차 전에 한결물류 관리자 역할로 LC-R1에 정적 경로를 넣어 둡니다.

```markdown
# 사고 01: 인수한 회사에서 인사팀으로 들어온 접근

| 항목 | 내용 |
|------|------|
| 사고 번호 | 사고-01 |
| 작성자 | 강사 (새봄상사 네트워크 담당) |
| 작성일 | 10일차 |
| 심각도 | 중 |
| 상태 | 종결 (남은 위험 있음) |

## 요약

한결물류 PC에서 새봄상사 인사팀 PC로 들어온 접근을 확인했다. 원인은 7일차에 경로 필터만 걸고 패킷 필터를 미룬 틈과, 한결물류 라우터에 들어간 정적 경로다. HQ-R1 Gi0/2에 확장 ACL을 걸어 서버 VLAN 밖으로 가는 접근을 막았다.

## 탐지

| 항목 | 내용 |
|------|------|
| 언제 | 10일차 15:40 |
| 무엇으로 | HQ-R1 Gi0/2 의 감시용 ACL(LC-WATCH) 적중 횟수와 로그 |
| 누가, 어떤 상황에서 | 네트워크 담당자가 ACL 정책을 걸기 전, 무엇이 들어오는지 기록만 하던 중 |

## 타임라인

| 시각 | 일 | 근거 |
|------|----|------|
| 7일차 | 한결물류와 연결. 경로 필터만 걸고 패킷 필터는 10일차로 미룸 | 03_구축/인수회사_연결.md 의 남은 위험 |
| 10일차 15:20 | 감시용 ACL LC-WATCH 적용. 모두 허락하고 서버 VLAN 밖으로 가는 것만 기록 | 커밋 (해시) |
| 10일차 15:40 | 172.16.10.10 에서 192.168.10.42 (인사팀) 로 가는 ICMP 기록 | 증거/01_acl_log.txt |
| 10일차 15:45 | LC-R1 에 192.168.10.0/24 정적 경로가 있음을 확인 | 증거/01_lc-r1_route.txt |
| 10일차 16:00 | 확장 ACL LC-IN 으로 교체 | 커밋 (해시) |
| 10일차 16:01 | EIGRP 이웃이 끊김. ACL 이 EIGRP 알림까지 막음 | 증거/01_eigrp_down.txt |
| 10일차 16:03 | ACL 맨 앞에 EIGRP 허락 줄을 더해 이웃 복구 | 커밋 (해시) |
| 10일차 16:05 | 같은 시험이 인사팀에서 막히고, 서버로는 닿는 것을 확인 | 증거/01_after.txt |

## 분석

- 경로: LC-PC1(172.16.10.10)에서 LC-R1 의 정적 경로를 타고 HQ-R1 Gi0/2 를 거쳐 HR-PC1(192.168.10.42)로
- 판정: 정탐. 한결물류의 업무(배송 처리)에 인사팀 접근은 필요 없다
- 근거: ACL 로그 `list LC-WATCH permitted icmp 172.16.10.10 -> 192.168.10.42 (8/0), 1 packet`
- 근거: LC-R1 의 `S 192.168.10.0/24 [1/0] via 192.168.99.9`
- 확인하지 못한 것: 인사팀 PC 안의 자료를 열었는지는 이 실습망에서 확인할 수 없다

| 관리 | 인수한 회사 라우터의 설정 변경을 새봄상사가 알 길이 없었다. 연결 규정이 없었다 |

| 근본 | 한결물류에 정적 경로 삭제 요청. 연결 구간의 설정 변경은 미리 알리기로 규정 | 01_요구사항/인수회사_연결_규정.md |

## 재발 방지와 남은 위험

- 10일차 ACL 정책표에 신뢰 경계 줄을 더한다
- 15일차 모니터링에서 LC-IN 의 거부 적중이 늘면 알림을 받는다
- 남은 위험: 새봄상사에서 한결물류로 먼저 건 통신의 답도 막힌다. 10일차 뒷부분의 established 와 Reflexive ACL 로 푼다
- 남은 위험: 서버 VLAN 으로의 접근은 업무상 허락한다. 서버 자체의 방화벽은 13일차에

## 교훈

- 잘한 것: 막기 전에 기록부터 걸어, 실제로 무엇이 들어오는지 보고 판단했다
- 아쉬운 것: 7일차에 남은 위험으로 적어 두고도 세 회차 동안 열어 두었다. ACL 을 처음 걸 때 라우팅 알림을 잊어 이웃을 끊었다

## 증거 파일

- 증거/01_acl_log.txt, 증거/01_lc-r1_route.txt, 증거/01_eigrp_down.txt, 증거/01_after.txt
```

예시에서 쓴 ACL입니다. 10일차 노트에서 자세히 다룹니다.

```
ip access-list extended LC-WATCH
 permit eigrp host 192.168.99.10 any
 permit ip 172.16.10.0 0.0.0.255 192.168.10.96 0.0.0.31
 permit ip any any log
ip access-list extended LC-IN
 permit eigrp host 192.168.99.10 any
 permit ip 172.16.10.0 0.0.0.255 192.168.10.96 0.0.0.31
 deny ip any any log
interface gi0/2
 ip access-group LC-IN in
```

감시용 ACL을 먼저 거는 순서가 이 사고의 핵심입니다. 모두 허락하면서 기록만 하는 ACL로 실제 흐름을 본 뒤에 막으면, 업무 통신을 잘못 끊는 사고를 줄이고 보고서에 남길 증거도 생깁니다.

## 6. 잘 쓴 보고서의 조건

개인 실습의 꼭 할 것과 16일차 평가에서 이 표로 봅니다.

| 조건 | 보는 곳 |
|------|---------|
| 사실과 추측을 나눴다 | 분석의 "확인하지 못한 것" 줄이 있다 |
| 시각이 모두 적혀 있다 | 타임라인 |
| 주장마다 근거가 있다 | 근거 칸과 증거 파일 |
| 대응마다 커밋 해시가 있다 | 대응 칸 |
| 원인을 사람이 아니라 틈으로 적었다 | 원인 칸에 "누가 실수했다"가 없다 |
| 남은 위험을 숨기지 않았다 | 재발 방지와 남은 위험 |

## 수업 전에 확인할 것

- 패킷트레이서가 확장 ACL의 `log` 를 받아 `%SEC-6-IPACCESSLOGDP` 같은 로그를 띄우는지, `show access-lists` 에 적중 횟수가 보이는지. 로그가 안 뜨면 적중 횟수만으로 탐지한다
- 사고 03의 스캔 도구와 대상. 9일차에 공개할 서비스가 정해지면 구체화한다
- 사고 04의 IDS를 무엇으로 돌릴지(리눅스 VM의 Snort나 Suricata). 15일차 노트를 쓸 때 정한다
