## 1. 왜 Git인가

Git은 파일이 바뀔 때마다 그 순간의 모습을 기록해 두는 프로그램입니다. 게임의 세이브 포인트와 비슷합니다. 중요한 순간마다 저장해 두면, 일이 꼬였을 때 그 지점으로 돌아갈 수 있습니다.

| 이유 | 이 과목에서 |
|------|-------------|
| 포트폴리오의 집 | 16일 동안 만든 문서와 설정이 저장소 하나에 모인다. 링크 하나로 보여 줄 수 있다 |
| 바뀐 기록 | 매 회차 무엇을 바꿨는지 날짜별로 남는다. 2일차부터는 장비 설정의 바뀐 줄이 그대로 보인다 |
| 되돌리기 | 설정을 고쳤다가 통신이 끊겨도 어제의 커밋으로 돌아갈 수 있다 |

장비 설정을 Git으로 관리하는 네트워크 팀이 많습니다. 앞 노트의 기록 원칙과 부인 방지를 도구로 옮긴 것입니다.

## 2. Git과 GitHub는 다르다

| | Git | GitHub |
|-|-----|--------|
| 무엇인가 | 내 PC에 설치하는 프로그램 | 인터넷에 있는 저장소 보관 서비스 |
| 하는 일 | 바뀐 것을 기록한다 | 기록을 올려 두고 남에게 보여 준다 |
| 인터넷 | 없어도 된다 | 있어야 한다 |

Git만으로도 기록은 됩니다. GitHub는 그 기록을 인터넷에 올려 두는 곳이라, PC가 바뀌어도 이어서 작업할 수 있고 면접관에게 링크로 보여 줄 수 있습니다. 교실 PC에서 작업하고 집에서 이어 하는 것도 GitHub 덕분입니다.

## 3. 세 자리

Git으로 기록하는 일은 세 자리를 거칩니다.

```
작업 폴더  --git add-->  스테이지  --git commit-->  내 저장소  --git push-->  GitHub
```

| 자리 | 하는 일 | 명령 |
|------|---------|------|
| 작업 폴더 | 파일을 만들고 고치는 곳. 내 PC의 평범한 폴더다 | 편집기에서 저장 |
| 스테이지 | 이번에 기록할 파일을 골라 담아 두는 곳 | `git add` |
| 저장소 | 기록이 남는 곳. 한 번의 기록을 커밋이라 한다 | `git commit` |

택배로 생각하면 이렇습니다. 보낼 물건을 고르고(작업 폴더), 상자에 담고(add), 송장을 붙여 발송 기록을 남기고(commit), 택배 기사에게 넘깁니다(push). 상자에 담기만 하고 송장을 붙이지 않으면 기록이 없고, 송장을 붙여도 넘기지 않으면 GitHub에는 아무것도 가지 않습니다.

스테이지가 왜 따로 있는지 궁금할 수 있습니다. 파일 열 개를 고쳤어도 그중 계획서에 관한 세 개만 골라 "계획서 수정"이라는 기록 하나로 남기고 싶을 때가 있기 때문입니다. 기록을 일의 단위로 나눠 두면 나중에 찾기 쉽습니다.

> 2일차에 배우는 캡슐화도 데이터를 상자에 담고 주소를 붙이는 이야기입니다.

## 4. 커밋에 남는 것

첫 커밋을 올린 뒤 `git log` 를 치면 이런 기록이 보입니다.

```
commit d7be5b808c2f40e1255e16f3bd093f7071f4c3ba
Author: 홍길동 <12345678+hong@users.noreply.github.com>
Date:   Tue Oct 27 16:01:48 2026 +0900

    1일차: 프로젝트 계획서 초안
```

| 줄 | 무엇인가 |
|----|----------|
| commit 뒤의 긴 글자 | 커밋의 지문(해시). 내용이 한 글자라도 다르면 완전히 다른 값이 나온다 |
| Author | 누가. 1번 설정에서 적은 이름과 이메일 |
| Date | 언제. +0900은 한국 시간이라는 뜻 |
| 마지막 줄 | 무엇을. 커밋 메시지 |

지문이 내용에서 계산된다는 점이 중요합니다. 누군가 지난 기록을 몰래 고치면 지문이 달라져서 바뀐 것이 드러납니다. 1번 노트의 무결성을 Git은 이렇게 지킵니다. 평소에는 앞의 일곱 자리만 써도 커밋을 가리킬 수 있어서, `git log --oneline` 은 `d7be5b8` 처럼 짧게 보여 줍니다.

> 11일차 VPN이 길 위의 데이터가 바뀌지 않았는지 확인할 때도 같은 원리의 해시를 씁니다.

## 5. 오늘 쓰는 명령

| 명령 | 하는 일 |
|------|---------|
| `git clone <주소>` | GitHub 저장소를 내 PC로 가져온다 |
| `git status` | 지금 어느 파일이 어느 자리에 있는지 본다 |
| `git add .` | 바뀐 파일을 모두 스테이지에 올린다 |
| `git commit -m "메시지"` | 스테이지에 있는 것을 기록한다 |
| `git push` | 기록을 GitHub로 보낸다 |
| `git log --oneline` | 기록을 한 줄씩 본다 |

`git status` 는 언제 쳐도 아무것도 망가뜨리지 않습니다. 헷갈리면 먼저 칩니다.

커밋 메시지는 나중의 나에게 남기는 메모입니다. 이 과목에서는 일차로 시작하고, 무엇을 했는지 씁니다.

| 이렇게 쓰지 않는다 | 이렇게 쓴다 |
|--------------------|-------------|
| 수정 | 1일차: 프로젝트 계획서 초안 |
| asdf | 2일차: 주소 설계표 추가 |
| 최종 | 3일차: 영업팀과 인사팀 VLAN 분리 |

브랜치 같은 기능은 지금 배우지 않습니다. 6일차에 설계안 두 개를 비교해야 할 때 그 자리에서 배웁니다.

## 6. 마크다운

계획서와 README는 마크다운(`.md`)으로 씁니다. 마크다운은 기호 몇 개로 제목, 목록, 표를 만드는 글쓰기 방식입니다. 메모장으로도 열리는 평범한 글자 파일이라 Git이 바뀐 줄을 정확히 보여 주고, GitHub는 이것을 보기 좋게 그려 줍니다. 한글 파일(`.hwp`)이나 워드 파일은 Git이 무엇이 바뀌었는지 보여 주지 못합니다.

이 과목에서 쓰는 것은 이 정도입니다.

````markdown
# 큰 제목
## 작은 제목

- 목록
- 목록

1. 번호 목록
2. 번호 목록

**굵게**

| 부서 | 인원 |
|------|------|
| 영업팀 | 8 |

- [ ] 아직 안 한 일
- [x] 끝낸 일

[계획서](01_요구사항/프로젝트_계획서.md)
````

| 기호 | 만드는 것 |
|------|-----------|
| `#` | 제목. 개수가 많을수록 작은 제목 |
| `-` | 목록 |
| `**` 로 감싸기 | 굵은 글씨 |
| 세로 막대와 `---` | 표. 세로 막대가 칸을 나누고, 둘째 줄의 `---` 가 머리줄과 내용을 가른다 |
| `- [ ]` | 체크박스. 완료 기준 칸에 쓴다 |
| `[글자](주소)` | 링크. README에서 계획서로 가는 길 |

VS Code에서 `.md` 파일을 열고 Ctrl+Shift+V를 누르면 그려진 모습을 미리 볼 수 있습니다. 표가 깨져 보이면 대부분 칸 수가 줄마다 다르거나, 표 위에 빈 줄이 없는 경우입니다.

## 7. GitHub의 인증

처음 push할 때 GitHub 로그인 창이 뜹니다. 1번 노트의 인증이 여기서 일어납니다.

GitHub는 2021년 8월부터 Git 명령에 계정 비밀번호를 그대로 받지 않습니다. 비밀번호가 새면 계정 전체가 넘어가기 때문입니다. 대신 Git for Windows에 들어 있는 Git Credential Manager가 브라우저로 로그인을 받고, 그 결과로 받은 출입증(토큰)을 Windows에 보관했다가 push할 때마다 씁니다.

GitHub는 코드를 올리는 계정에 2단계 인증도 요구합니다. 가입 뒤 얼마 지나면 설정하라는 안내가 옵니다. 비밀번호에 더해 휴대폰 인증 앱의 숫자를 한 번 더 묻는 방식이라, 비밀번호가 새어도 계정을 지킬 수 있습니다.

## 8. 공개 저장소의 첫 규칙

포트폴리오는 남에게 보여 주려고 만드는 것이라 저장소를 공개로 둡니다. 공개 저장소는 누구나 읽을 수 있고, **한 번 올린 것은 지워도 커밋 기록에 남습니다.** 그래서 올리기 전에 한 번 더 봅니다.

| 올리지 않는 것 | 대신 |
|----------------|------|
| 실제로 쓰는 비밀번호 | 실습 장비에는 실습용 비밀번호만 쓴다 |
| 내 전화번호와 주소 | 연락처는 이력서에만 적는다 |
| 개인 이메일 | GitHub가 주는 noreply 주소로 커밋한다 |
| 실제 회사의 이름과 내부 정보 | 가상 회사로만 만든다 |

커밋에는 [대본 1번](commands.md)에서 적은 이메일이 그대로 찍혀 공개됩니다. 4번 절의 Author 줄이 그것입니다. 그래서 개인 이메일 대신 GitHub의 noreply 주소를 적습니다.

GitHub의 이메일 설정에는 개인 이메일이 찍힌 커밋의 push를 거절하는 옵션도 있습니다. 켜 두면 실수로 개인 이메일로 커밋했을 때 push가 `GH007` 오류로 막힙니다. 안전장치를 하나 더 두는 것이니 1일차에 켜 둡니다.

이것이 이 과목의 첫 보안 실습입니다. 내 정보의 기밀성을 내 손으로 지키는 일입니다.

- 동료가 저장소의 지난 커밋 하나를 몰래 고쳤습니다. 다른 사람은 어떻게 알아챌 수 있을까요?

### 물어볼 것

- "push하지 않고 PC가 초기화되면?" 기대하는 답은 "커밋은 그 PC의 저장소에만 있었으니 사라진다"입니다. 그래서 수업 끝에 push까지 해야 한다는 것을 여기서 못 박습니다.
- "지난 커밋을 몰래 고치면?" 지문이 바뀌어 GitHub의 기록과 맞지 않게 됩니다. 4번 절의 무결성 이야기로 답합니다.

### 자주 헷갈리는 것

| 헷갈리는 것 | 바로잡기 |
|-------------|----------|
| commit하면 GitHub에 올라간다 | commit은 내 PC에 기록할 뿐이다. GitHub에는 push해야 간다 |
| Git과 GitHub는 같은 회사 프로그램이다 | Git은 누구나 쓰는 프로그램이고, GitHub는 그 기록을 보관해 주는 서비스 중 하나다 |
| `git add` 하면 저장된다 | 스테이지에 올린 것이고, 기록은 commit에서 남는다 |
| noreply 주소는 메일을 못 받으니 불편하다 | 커밋에 찍히는 주소일 뿐, GitHub 알림은 가입한 이메일로 그대로 온다 |

### 진행 요령

- 세 자리는 `git status` 를 칠 때마다 색으로 확인시킵니다. 빨간 글씨는 작업 폴더에서 바뀐 것, 초록 글씨는 스테이지에 올라간 것입니다.
- push 때 뜨는 로그인 창을 [2번 노트](lesson-2.md)의 인증과 이어서 말합니다.
- 교실 PC를 여러 사람이 쓴다면 수업 끝에 자격 증명을 지우게 합니다(대본 7번). 남의 계정으로 push되는 일이 생길 수 있습니다.
- Git을 처음 보는 학생은 명령보다 "지금 내가 어느 폴더에 있는가"에서 더 많이 막힙니다. `pwd` 를 같이 알려 줍니다.
- 마크다운 표는 계획서 시간에 바로 씁니다. 여기서는 표 하나만 같이 그려 보고 넘어갑니다.
