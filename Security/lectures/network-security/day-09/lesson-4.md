## 학습 목표

- NAT가 숨기는 것과 막는 것을 구분한다.

## 목적

오늘 새봄상사는 처음으로 바깥 세상과 이어졌다. 직원은 인터넷에 나가고, 고객은 쇼핑몰에 들어온다. 길이 열린 만큼 들어올 수 있는 문도 생겼다. 키워드 요약은 NAT의 보안 이점으로 "내부 구조를 숨긴다"를 들었다. 그 말이 어디까지 맞는지 확인한다.

## 1. 숨기는 것과 막는 것

| NAT가 하는 일 | 보안으로 보면 | 한계 |
|---|---|---|
| 밖에는 공인 주소만 보인다 | 회사 안의 주소 체계가 드러나지 않는다 | 숨길 뿐이다. 공개한 주소로 오는 것은 그대로 들어온다 |
| PAT는 안에서 시작한 통신의 답만 돌려보낸다 | 밖에서 먼저 직원 PC로 들어오지 못한다 | 정책이 아니라 변환 표에 줄이 없어서 생긴 결과다 |
| 포트 포워딩은 적어 둔 포트만 넘긴다 | 쇼핑몰의 다른 문은 밖에서 안 보인다 | 80, 443으로 오는 공격은 막지 못한다 |

NAT는 주소를 바꾸는 장치이고, 무엇을 허락하고 막을지 정하는 장치가 아니다. 막는 일은 10일차 ACL과 13, 14일차 방화벽이 한다. 2번 노트에서 장애 때 지사 쪽 inside를 빠뜨리면 인터넷이 끊기는 것을 봤듯, NAT 설정은 통신을 위한 설정이다.

## 2. 밖에서 보이는 새봄상사

4일차 4번 노트에서 밖에서 친 tracert에 회사 안의 라우터 주소가 드러날 수 있다고 했다. 오늘 NET-PC에서 직접 입력해 본다.

```
C:\>tracert 203.0.113.10

  1   0 ms      0 ms      0 ms      198.51.100.1
  2   1 ms      0 ms      1 ms      203.0.113.2
  3   *         *         *         Request timed out.
  4   *         *         *         Request timed out.
```

| 줄 | 장비 |
|---|---|
| 1 | ISP-R1 |
| 2 | HQ-R1의 인터넷 쪽 주소 |
| 3부터 | 답이 없다. ICMP는 쇼핑몰로 넘기지 않고, HQ-R1이 null 경로로 버린다 |

패킷트레이서 버전에 따라 3번째 줄에 HQ-R1이 "닿을 수 없음"으로 답하는 줄이 보일 수도 있다. 어느 쪽이든 회사 안의 주소는 나오지 않는다.

192.168.으로 시작하는 주소는 한 줄도 나오지 않는다. 밖에서 보이는 새봄상사는 공인 주소 두 개(203.0.113.2와 203.0.113.10)와 열린 포트 두 개(80, 443)가 전부다. 이것이 오늘 만든 새봄상사의 공격 표면이다.

공격 표면은 밖에서 닿을 수 있는 모든 곳의 합이다. 서비스를 하나 열 때마다 넓어지고, 닫을 때마다 좁아진다. 쇼핑몰처럼 꼭 열어야 하는 문은 남기고, 나머지는 열지 않는 것이 최소 권한이다.

## 3. 공개 서비스 목록

밖에 연 문은 문서로 관리한다. 누가 왜 열었는지 모르는 문이 가장 위험하다. 오늘부터 `02_설계/공개_서비스.md`를 둔다.

```markdown
# 공개 서비스

| 서비스 | 밖에서 보이는 주소와 포트 | 안쪽 주소와 포트 | 누가 쓰나 | 왜 열었나 | 연 날 |
|--------|---------------------------|------------------|-----------|-----------|-------|
| 쇼핑몰 (HTTP) | 203.0.113.10:80 | 192.168.10.98:80 | 고객 | 온라인 판매 | 9일차 |
| 쇼핑몰 (HTTPS) | 203.0.113.10:443 | 192.168.10.98:443 | 고객 | 온라인 판매 | 9일차 |

## 열지 않기로 한 것

- 재택 근무자의 원격 접속: 포트를 열지 않고 14일차 VPN 으로
- 서버의 FTP 와 그 밖의 서비스: 밖에서 쓸 사람이 없다
```

"열지 않기로 한 것"을 함께 적는 이유가 있다. 개발팀 재택 근무자는 지금도 집에서 쇼핑몰 서버를 관리하고 싶어 한다. 가장 빠른 방법은 원격 접속 포트를 하나 더 포워딩하는 것이지만, 그 문은 인터넷 전체가 두드리게 된다. 새봄상사는 14일차의 VPN을 기다리기로 했고, 그 결정을 문서에 남긴다.

## 5. 오늘의 기록

`03_구축/인터넷_연결.md`를 이렇게 쓴다.

```markdown
# 인터넷 연결

## 구성

| 항목 | 값 |
|------|----|
| ISP 회선 | HQ-R1 Se0/0/1 203.0.113.2/30 - ISP-R1 .1 |
| 서버용 공인 주소 | 203.0.113.8/29 (쇼핑몰 .10) |
| 기본 경로 | HQ-R1 에서 ISP 로, OSPF 로 지사에 알림 |
| null 경로 | 192.168.0.0/16 (사설), 203.0.113.8/29 (받은 공인 주소) |

## NAT

| 종류 | 대상 | 바뀌는 주소 |
|------|------|-------------|
| PAT | 본사와 지사 (NAT-INSIDE) | 203.0.113.2 |
| 포트 포워딩 | 쇼핑몰 80, 443 | 203.0.113.10 |

## 시험

| 시험 | 결과 |
|------|------|
| 영업팀 PC 에서 NET-PC 로 ping | |
| 지사 PC 에서 NET-PC 로 ping | |
| NET-PC 에서 쇼핑몰 웹 | |
| NET-PC 에서 FTP, ping | |
| NET-PC 에서 tracert 203.0.113.10 | 안쪽 주소가 보이는가: |

## 남은 위험

- NAT 는 막지 않는다. 쇼핑몰 80, 443 으로 오는 것은 모두 들어온다 (13, 14일차 방화벽)
- 장비 관리 VLAN 도 NAT-INSIDE 에 들어 있어 인터넷에 나갈 수 있다 (10일차 ACL)
```

## 약어·용어

| 용어 | 뜻 |
|---|---|
| 공격 표면 | 밖에서 닿을 수 있는 모든 주소와 포트의 합. 서비스를 열 때마다 넓어진다 |
| 최소 권한 | 꼭 필요한 문과 권한만 남기고 나머지는 열지 않는 원칙 |
| tracert | 목적지까지 거치는 장비를 한 칸씩 보여 주는 명령 |
| ACL | 어떤 통신을 허락하고 막을지 적은 목록 (10일차) |
| 침해사고 분석 보고서 | 사고가 났을 때 영향, 원인, 대응을 칸마다 적는 양식 |

## 함께 생각해 보기

- 우리 회사의 공격 표면은 지금 무엇무엇인가? 공인 주소와 포트로 적어 본다.
- 재택 근무자가 "VPN까지 두 주를 못 기다리겠다"고 하면, 무엇을 근거로 설득하겠는가?

### 물어볼 것

- "PAT가 밖에서 먼저 들어오는 것을 막는다면 방화벽은 필요 없을까?" 필요하다. 우연히 생긴 결과일 뿐이고, 공개한 포트로 오는 것은 막지 못한다.
- "tracert 3번째 줄부터 답이 없는 것은 장애일까?" 아니다. ICMP를 쇼핑몰로 넘기지 않아서다.
- 두 번째 함께 생각해 보기의 답: 원격 접속 포트를 열면 인터넷 전체가 그 문을 두드린다는 것, 그리고 한번 열린 문은 누가 열었는지 잊혀 닫히지 않는다는 것. 사고 03에서 열린 문이 어떻게 두드려지는지 직접 보게 된다.

### 자주 헷갈리는 것

| 헷갈리는 것 | 바로잡기 |
|---|---|
| NAT를 하면 안전하다 | 숨길 뿐이다. 막는 것은 ACL과 방화벽이다 |
| 공격 표면은 서버 수다 | 밖에서 닿는 주소와 포트의 합이다. 서버 하나에도 문이 여럿이다 |
| 공개 서비스 목록은 연 것만 적는다 | 열지 않기로 한 것과 그 이유도 적는다. 다음 사람이 같은 고민을 반복하지 않는다 |
