# 4. 경로와 보안

> 상위: [4일차 정적 라우팅과 지사 연결](README.md)
> 드로잉: 4. 경로와 보안 드로잉 (7장)

## 학습 목표

- 경로를 바꿀 수 있는 사람이 통신을 쥔다는 것을 압니다
- tracert가 밖에 드러내는 정보를 압니다
- 쓰지 않는 주소로 가는 패킷을 버리는 null 경로를 압니다
- 원격으로 경로를 바꿀 때의 안전장치와 기록 습관을 압니다

## 다리 놓기

오늘 경로 몇 줄로 지사와 본사의 통신 전체를 움직였습니다. 경로 한 줄을 바꾸면 회사의 통신이 다른 곳으로 갑니다. 같은 힘을 공격자가 가지면 어떻게 될까요. 오늘 배운 경로를 보안의 눈으로 다시 봅니다.

## 1. 경로를 쥔 사람이 통신을 쥔다

| 경로가 바뀌면 | 일어나는 일 | 깨지는 것 |
|---------------|-------------|-----------|
| 통신이 공격자의 장비를 거쳐 가게 | 내용을 엿보거나 바꾼다 | 기밀성, 무결성 |
| 통신이 없는 곳으로 가게 | 통신이 버려진다 | 가용성 |

정적 경로는 설정 권한을 가진 사람만 바꿀 수 있습니다. 그래서 정적 경로의 보안은 결국 라우터에 누가 들어올 수 있느냐의 문제입니다. 2일차에 건 세 문의 잠금, 3일차에 관리 접속을 VLAN 99로 모은 일이 모두 경로표를 지키는 일입니다.

> 5일차부터는 라우터끼리 경로를 알려 주므로, 거짓 경로를 알려 주는 공격도 생각해야 합니다. 그래서 라우팅 프로토콜마다 인증을 겁니다.

## 2. tracert가 드러내는 것

tracert는 목적지까지 거치는 라우터의 주소를 차례로 보여 줍니다. 관리자에게는 고마운 도구지만, 밖에서 누군가 우리 쇼핑몰로 tracert를 치면 회사 안의 라우터 주소와 구조가 드러납니다.

tracert는 TTL을 1, 2, 3으로 늘려 가며 패킷을 보내는 방식으로 동작합니다. 2일차에 본 TTL은 라우터를 하나 지날 때마다 1씩 줄고 0이 되면 버려진다고 했습니다. 버린 라우터가 "여기서 버렸다"고 답하는데, 그 답에 라우터의 주소가 들어 있습니다.

```
TTL 1 로 보냄  ->  첫 번째 라우터가 버리고 답함 (1번 줄)
TTL 2 로 보냄  ->  두 번째 라우터가 버리고 답함 (2번 줄)
TTL 3 로 보냄  ->  목적지에 닿아 답함 (3번 줄)
```

공격자가 공격을 준비하며 맨 먼저 하는 일이 이런 정보 모으기입니다. 회사 안에서는 tracert를 그대로 두고, 밖에서 들어오는 것만 막는 것이 보통입니다.

> 14일차에 경계 방화벽에서 밖에서 오는 이런 탐색을 걸러 냅니다.

## 3. 쓰지 않는 주소는 버린다 (null 경로)

9일차에 본사 라우터에 인터넷으로 나가는 기본 경로를 넣으면, 경로표에 없는 목적지는 모두 인터넷으로 나갑니다. 그런데 회사 안의 주소인데 아직 쓰지 않는 대역(예를 들어 본사의 여유 대역 192.168.10.160/27)으로 가는 패킷도 경로표에 없으니 인터넷으로 나가 버립니다. 회사 안의 주소 체계가 밖으로 새고, 쓸데없는 통신이 회선을 씁니다.

이럴 때 회사의 사설 대역 전체를 null 경로로 막아 둡니다. null0은 받은 것을 그냥 버리는 가상의 포트입니다.

```
ip route 192.168.0.0 255.255.0.0 null0
```

이 줄은 /16이라 구체적인 /27이나 /30 줄에는 집니다. 그래서 실제로 쓰는 대역은 그대로 통하고, 경로표에 없는 회사 안의 주소만 인터넷 대신 null0으로 갑니다. [1번 노트](lesson-1.md)의 가장 구체적인 줄 규칙이 여기서 보안 도구가 됩니다.

> 9일차에 기본 경로를 넣는 날 이 줄을 함께 넣습니다. 오늘은 원리만 압니다.

## 4. 원격으로 경로를 바꿀 때

라우터에 원격으로 접속해 경로를 고치다가, 내가 들어와 있는 바로 그 길을 끊어 버리는 실수가 현장에서 자주 납니다. 접속이 끊기면 고치러 직접 가야 합니다. 지사 라우터라면 서울까지 가야 합니다.

| 습관 | 내용 |
|------|------|
| 바꾸기 전에 계획 | 작업 계획서에 바꿀 줄과 되돌리는 방법을 먼저 적는다 |
| 예약 재시작 | 실제 장비에서는 `reload in 10` 으로 10분 뒤 재시작을 걸어 두고 고친다. 고친 뒤 접속이 살아 있으면 `reload cancel`. 끊겼다면 10분 뒤 저장된 설정으로 돌아온다 |
| 저장은 확인 뒤에 | 확인하기 전에 `copy running-config startup-config` 하지 않는다. 그래야 재시작으로 되돌릴 수 있다 |
| 바꾼 뒤에 기록 | 설정 텍스트를 커밋해 바뀐 줄을 남긴다 |

예약 재시작은 패킷트레이서에서 지원하지 않을 수 있어 오늘은 이름만 압니다. 작업 계획서의 "되돌리는 방법" 칸이 왜 있는지가 여기서 분명해집니다.

## 5. 오늘의 기록

오늘의 산출물 중 `03_구축/지사_연결.md` 는 이렇게 씁니다.

```markdown
# 지사 연결

## 구성

| 회선 | 본사 | 지사 | 대역 | 용도 |
|------|------|------|------|------|
| 주 회선 | HQ-R1 Gi0/1 .1 | BR-R1 Gi0/1 .2 | 192.168.99.0/30 | 평소 |
| 예비 회선 | HQ-R1 Se0/0/0 .5 | BR-R1 Se0/0/0 .6 | 192.168.99.4/30 | 주 회선 장애 시 |

## 경로

- 본사: 지사 대역으로 주 경로(관리 거리 1)와 예비 경로(250)
- 지사: 기본 경로 둘 (주 1, 예비 250)

## 장애 시험 (날짜)

- 시험: 지사 PC에서 본사 서버로 ping -t, 본사 Gi0/1 shutdown
- 결과: Request timed out __개 뒤 예비 회선으로 넘어감
- 경로표: 끄기 전 [1/0] via 192.168.99.2, 끈 뒤 [250/0] via 192.168.99.6
- 한계: 중간 장비 고장은 정적 경로가 알아채지 못함. 5일차 동적 라우팅에서 다시 시험
```

## 강의 메모

### 시간 배분 (30분)

| 절 | 시간 | 방식 |
|----|------|------|
| 다리 놓기, 1 경로를 쥔 사람 | 6분 | 1일차 CIA로 표를 채운다 |
| 2 tracert | 8분 | TTL 그림. 오늘 친 tracert 결과를 다시 읽는다 |
| 3 null 경로 | 6분 | 가장 구체적인 줄 규칙과 잇는다 |
| 4 원격으로 바꿀 때 | 5분 | 지사까지 가야 하는 이야기 |
| 5 기록 | 5분 | 양식을 보여 주고 개인 실습으로 넘긴다 |

### 물어볼 것

- "누군가 우리 라우터에 경로 한 줄을 몰래 넣을 수 있다면 무엇을 할 수 있을까요?" 1번 절의 표가 답입니다.
- "tracert는 어떻게 중간 라우터의 주소를 알아낼까요?" TTL이 0이 된 라우터가 답하기 때문입니다.
- 두 번째 함께 생각해 보기의 답: 인터넷으로 나갑니다. 사설 주소라 인터넷에서 버려지기는 하지만, 그 전에 회사 밖으로 나가는 것 자체가 낭비이고 정보 노출입니다.

### 자주 헷갈리는 것

| 헷갈리는 것 | 바로잡기 |
|-------------|----------|
| null 경로를 넣으면 회사 안의 모든 통신이 막힌다 | /16 null 경로는 더 구체적인 줄에 진다. 실제로 쓰는 대역은 그대로 통한다 |
| tracert를 막으면 ping도 막힌다 | 둘은 다르게 막을 수 있다. 14일차 방화벽에서 나눠서 다룬다 |

### 진행 요령

- 이 노트는 실습이 거의 없습니다. 장애 시험 직후라 학생들이 지쳐 있으니, 오늘 친 화면을 다시 띄워 보안의 눈으로 읽게 하는 데 집중합니다.
- null 경로는 오늘 넣지 않습니다. 9일차 기본 경로와 함께 넣어야 의미가 생깁니다.
- `reload in` 은 실제 장비에서 쓰는 습관으로만 소개합니다. 패킷트레이서에서 되는지는 수업 전에 확인합니다.
