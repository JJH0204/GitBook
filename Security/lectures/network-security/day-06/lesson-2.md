# 2. Git 브랜치로 실험하기

> 상위: [6일차 OSPF와 Git 브랜치](README.md)
> 대본: [실습 명령어 모음](commands.md) 1번, 9번
> 드로잉: 2. Git 브랜치로 실험하기 드로잉 (9장)

## 학습 목표

- 브랜치가 무엇이고, 설계안을 실험할 때 왜 쓰는지 압니다
- 브랜치를 만들고 옮겨 다니고, 두 브랜치의 차이를 봅니다
- 브랜치를 옮기기 전에 커밋해야 하는 이유를 압니다
- 실험이 끝나면 병합하고 브랜치를 지웁니다

## 다리 놓기

오늘은 RIP으로 잘 돌아가는 망을 OSPF로 바꿔 봅니다. 그런데 바꿔 보니 더 나쁘다면 어떻게 할까요. 어제 설정으로 손으로 되돌리는 것은 번거롭고, 무엇을 바꿨는지 빠뜨리기 쉽습니다.

1일차에 Git을 쓰는 이유로 "되돌리기"를 들었습니다. 오늘은 한 걸음 더 나아가, 원래 판을 그대로 두고 옆에 실험 판을 따로 만들어 비교한 뒤 고르는 방법을 배웁니다. 이것이 브랜치입니다.

## 1. 브랜치: 원래 판을 두고 옆에서 실험

브랜치는 커밋 기록의 갈래입니다. 지금까지 우리는 main이라는 갈래 하나에서만 커밋했습니다. 실험용 갈래를 하나 만들면, 거기서 아무리 바꿔도 main은 그대로 남습니다.

```
main   ... 5일차(RIP)
                      \
ospf                   6일차(OSPF 실험)
```

보고서 원본을 두고 사본을 만들어 고쳐 보는 것과 비슷합니다. 다른 점은 사본이 원본과 어디서 갈라졌는지 Git이 기억하고, 두 판의 차이를 줄 단위로 보여 주고, 고른 쪽을 원본에 합쳐 준다는 것입니다.

| 상황 | 브랜치가 하는 일 |
|------|------------------|
| 설계안 두 개를 비교하고 싶다 | 안마다 브랜치를 만든다 |
| 실험이 실패했다 | 브랜치를 버리면 main은 그대로다 |
| 실험이 성공했다 | main에 병합한다 |

현장의 네트워크 팀도 장비 설정을 바꾸기 전에 브랜치에서 바꾼 설정을 동료에게 검토받고, 승인되면 병합합니다. 작업 계획서와 함께 쓰면 "무엇을 왜 바꾸고, 누가 확인했는지"가 모두 기록에 남습니다.

## 2. 명령

| 명령 | 하는 일 |
|------|---------|
| `git switch -c ospf` | ospf 브랜치를 만들고 그리로 옮긴다 |
| `git branch` | 브랜치 목록. 지금 있는 곳에 `*` |
| `git switch main` | main으로 옮긴다 |
| `git diff main ospf -- configs/HQ-R1.txt` | 두 브랜치의 그 파일 차이 |
| `git log --oneline --graph --all` | 모든 브랜치의 기록을 그림으로 |
| `git merge ospf` | 지금 브랜치(main)에 ospf를 합친다 |
| `git branch -d ospf` | 병합이 끝난 브랜치를 지운다 |

```
$ git switch -c ospf
Switched to a new branch 'ospf'

$ git branch
  main
* ospf
```

## 3. 옮기기 전에 커밋한다

브랜치를 옮기면 작업 폴더의 파일이 그 브랜치의 판으로 바뀝니다. ospf에서 OSPF로 바꾼 `configs/HQ-R1.txt` 를 커밋한 뒤 main으로 옮기면, 파일이 RIP 설정으로 돌아갑니다. 다시 ospf로 오면 OSPF 설정이 돌아옵니다.

그런데 커밋하지 않은 변경은 다릅니다. 충돌이 없으면 커밋하지 않은 변경은 옮겨 간 브랜치로 그대로 따라옵니다. ospf에서 고친 것을 커밋하지 않고 main으로 옮기면, 그 변경이 main의 작업 폴더에 남아 있다가 main에 커밋되어 버립니다. 실험이 원본에 섞이는 것입니다. 충돌이 있으면 Git이 옮기기를 거절합니다.

```
error: The following untracked working tree files would be overwritten by checkout:
	x.txt
Please move or remove them before you switch branches.
Aborting
```

그래서 규칙은 하나입니다. **브랜치를 옮기기 전에 `git status` 로 확인하고, 바뀐 것이 있으면 커밋한다.**

패킷트레이서 파일은 하나 더 조심합니다. 패킷트레이서로 `.pkt` 를 연 채 브랜치를 옮기면, 화면의 장비는 옛 판인데 파일은 새 판으로 바뀌는 엇갈림이 생깁니다. 옮기기 전에 패킷트레이서를 저장하고 닫습니다.

## 4. 비교하고 고른다

실험을 마치고 커밋했으면 두 판을 비교합니다.

```
$ git diff main ospf -- configs/HQ-R1.txt
-router rip
- version 2
+router ospf 1
+ router-id 192.168.255.1
```

5일차의 `03_구축/라우팅_비교.md` 에 OSPF 칸을 더해 같은 기준으로 비교합니다. OSPF가 낫다고 정하면 main에 병합합니다.

```
$ git switch main
$ git merge ospf
Updating 4be43a4..9cf6d77
Fast-forward
 configs/HQ-R1.txt | 4 ++--
 1 file changed, 2 insertions(+), 2 deletions(-)
```

Fast-forward는 main이 갈라진 뒤로 그대로였기 때문에, main의 표시를 ospf의 끝으로 옮기기만 하면 된다는 뜻입니다. 병합이 끝나면 브랜치를 지우고 push합니다.

```
$ git branch -d ospf
Deleted branch ospf (was 9cf6d77).
$ git push
```

## 5. 실험이 실패했다면

OSPF가 기대만 못했다면 병합하지 않습니다. main으로 돌아오면 RIP 망이 그대로 있습니다. 실험 브랜치는 지우거나, 기록으로 남기려면 GitHub에 올려 둡니다(`git push -u origin ospf`). 포트폴리오에서 "검토했으나 채택하지 않은 안"도 좋은 기록입니다.

## 함께 생각해 보기

- 우리 회사의 보안 정책을 바꾸기 전에 브랜치를 쓴다면, 누가 무엇을 확인한 뒤에 병합해야 할까요?
- ospf 브랜치에서 일하다 커밋하지 않고 main으로 옮겨 커밋했습니다. 무엇이 잘못되었고 어떻게 알아챌 수 있을까요?

### 물어볼 것

- "실험이 망하면 어떻게 되돌릴까요?" main으로 돌아오면 됩니다. 1일차의 되돌리기가 판째로 됩니다.
- "Fast-forward는 무슨 뜻일까요?" main이 그동안 그대로라, 표시만 앞으로 옮기면 된다는 뜻입니다.
- 두 번째 함께 생각해 보기의 답: 실험 변경이 main에 들어갔습니다. `git log --oneline --graph --all` 에서 ospf 브랜치에 커밋이 없고 main에 실험 커밋이 있으면 알아챌 수 있습니다. 커밋 메시지를 일차와 브랜치 목적으로 쓰는 습관이 이럴 때 도움이 됩니다.

### 자주 헷갈리는 것

| 헷갈리는 것 | 바로잡기 |
|-------------|----------|
| 브랜치를 만들면 폴더가 복사된다 | 폴더는 하나다. 옮길 때마다 파일의 내용이 그 브랜치의 판으로 바뀐다 |
| 커밋하지 않아도 브랜치를 옮기면 따로 보관된다 | 커밋하지 않은 변경은 따라온다. 옮기기 전에 커밋한다 |
| 병합하면 ospf 브랜치의 기록이 사라진다 | 커밋은 main에 그대로 남는다. 지우는 것은 브랜치의 이름표뿐이다 |
| `git checkout -b` 와 `git switch -c` 가 다르다 | 같은 일을 한다. 이 과목은 뜻이 분명한 `switch` 를 쓴다 |

### 진행 요령

- 브랜치는 오늘 수업 시작(작업 계획서 커밋 직후)에 만들고, 오늘의 모든 작업을 그 브랜치에서 합니다. 함께 하는 실습 파일(`_실습/새봄상사.pkt`)과 내 회사 파일 모두 브랜치 안에서 바뀝니다.
- 패킷트레이서를 연 채 브랜치를 옮기는 실수가 가장 흔합니다. 옮기기 전에 "저장, 닫기, 커밋, 옮기기" 순서를 칠판에 적어 둡니다.
- 출력 예시의 해시는 스크래치 저장소에서 실제로 뜬 값이라 학생 화면과 다릅니다.
