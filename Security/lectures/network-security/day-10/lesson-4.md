## 학습 목표

- 들어오는 쪽만 막는 ACL이 내가 건 통신의 답까지 막는다는 것을 안다.
- `established`가 TCP의 답만 통과시키는 원리와 한계를 안다.
- Reflexive ACL로 안에서 시작한 통신의 답을 기억해 통과시킨다.
- 회사 안과 경계에서 ACL의 기본값이 다른 이유를 안다.

## 목적

사고 01의 대응으로 LC-IN을 걸자 한결물류에서 먼저 들어오는 접근은 서버 VLAN으로만 좁혀졌다. 그런데 새봄상사 지사의 영업 직원이 배송을 확인하려고 한결물류 PC로 ping을 보내 보면 답이 오지 않는다. 사고 01 보고서의 남은 위험에 적은 "새봄상사에서 먼저 건 통신의 답도 막힌다"가 이것이다.

요청은 Gi0/2로 나갔고, 답은 Gi0/2로 들어온다. LC-IN은 들어오는 패킷이 "답"인지 "먼저 거는 시도"인지 모르고, 출발지가 한결물류이니 20번 줄에서 버린다.

## 1. established: TCP의 답만

2일차의 3-way handshake를 떠올린다. 먼저 거는 쪽의 첫 패킷은 SYN만 켜져 있고, 그 뒤의 답과 데이터에는 ACK가 켜져 있다.

```
permit tcp any any established
```

`established`는 ACK나 RST가 켜진 TCP 패킷에만 맞는다. 밖에서 먼저 거는 첫 패킷(SYN만)은 맞지 않으니 막히고, 안에서 건 연결의 답은 통과한다.

| 한계 | 이유 |
|---|---|
| TCP에만 쓸 수 있다 | UDP와 ICMP(ping)에는 연결과 플래그가 없다 |
| 속일 수 있다 | 공격자가 ACK를 켠 패킷을 만들어 보내면 맞는다. 연결이 실제로 있었는지는 보지 않는다 |

2일차에 "10일차 ACL의 established가 이 세 번을 이용한다"고 예고했던 것이 이것이다.

## 2. Reflexive ACL: 나간 것을 기억한다

Reflexive ACL은 안에서 나가는 패킷을 보고, 그 답만 들어올 수 있는 임시 줄을 저절로 만든다. 아파트 경비실이 "502호가 방금 택배를 부쳤으니, 그 택배 회사의 답장만 들인다"고 메모해 두는 것과 같다. 메모는 잠시 뒤 지워진다.

| 부분 | 하는 일 | 거는 곳 |
|---|---|---|
| `reflect LC-RETURN`이 붙은 줄 | 나가는 패킷을 보고 임시 목록 LC-RETURN에 답이 들어올 줄을 적는다 | 나가는 쪽(out) ACL |
| `evaluate LC-RETURN` | 들어오는 패킷을 임시 목록과 비교한다 | 들어오는 쪽(in) ACL |

```
ip access-list extended LC-OUT
 permit tcp any any reflect LC-RETURN
 permit udp any any reflect LC-RETURN
 permit icmp any any reflect LC-RETURN
ip access-list extended LC-IN
 15 evaluate LC-RETURN
interface gi0/2
 ip access-group LC-OUT out
```

LC-IN의 15번 자리에 `evaluate`를 끼워 넣었다. 20번 거부 줄보다 위에 있어야 답이 버려지기 전에 임시 목록과 비교된다. 1번 노트의 순서 원칙 그대로다.

```
HQ-R1#show access-lists
Reflexive IP access list LC-RETURN
     permit icmp host 172.16.10.10 host 192.168.20.10 (4 matches) (time left 287)
Extended IP access list LC-IN
    5 permit eigrp host 192.168.99.10 any (52 matches)
    10 permit ip 172.16.10.0 0.0.0.255 192.168.10.96 0.0.0.31 (8 matches)
    15 evaluate LC-RETURN
    20 deny ip any any log (6 matches)
```

지사 PC가 한결물류 PC로 ping을 보내자, 그 답만 들어올 수 있는 줄이 LC-RETURN에 생겼다. `time left`가 다하면 저절로 사라진다. 한결물류 PC가 지사 PC로 먼저 ping을 보내면 임시 목록에 줄이 없으니 여전히 20번 줄에서 버려진다.

| 시험 | 결과 |
|---|---|
| 지사 PC에서 한결물류 PC로 ping | Reply. 답이 임시 줄에 맞는다 |
| 한결물류 PC에서 인사팀 PC로 ping | 닿을 수 없음. 사고 01의 대응 그대로 |
| 한결물류 PC에서 서버로 ping | Reply. 10번 줄 |

## 3. 이것이 방화벽의 시작

나간 연결을 기억했다가 그 답만 들이는 일을 상태 추적이라고 한다. Reflexive ACL은 라우터에서 손으로 하는 작은 상태 추적이다. 13일차의 ZFW와 14일차의 PFSense는 이 일을 모든 연결에 대해 기본으로 한다. 그래서 방화벽이라고 부른다.

오늘 두 가지 방식의 ACL을 썼다.

| 자리 | 기본값 | 오늘의 예 | 이유 |
|---|---|---|---|
| 회사 안 부서 사이 | 필요한 것만 막는다 | SALES-IN 50번 `permit ip any any` | 같은 회사라 대부분의 통신이 업무다. 막을 것이 적다 |
| 신뢰 경계 | 필요한 것만 연다 | LC-IN 20번 `deny ip any any log` | 우리가 관리하지 않는 망이다. 열 것이 적다 |

경계에서는 들일 것만 적고 나머지는 버리며, 안에서 시작한 통신의 답은 상태 추적으로 들인다. 인터넷 경계도 같은 모양이 되어야 하고, 그 일을 13, 14일차 방화벽이 맡는다.

## 5. 탐지·방어

확인 상태: 미검증 (일반 지식으로 짧게 정리했다).

| 항목 | 내용 |
|---|---|
| 원인 | `established`는 ACK나 RST 플래그만 보고 연결이 실제로 있었는지는 보지 않는다. 그래서 ACK를 켠 가짜 패킷이 필터를 지나 방화벽 뒤의 장비를 탐색하는 데 쓰일 수 있다. Reflexive ACL은 임시 줄이 살아 있는 동안 그 주소 쌍의 답을 모두 들인다 |
| 완화 | 상태를 기억하는 방화벽(13, 14일차 ZFW, PFSense)으로 옮긴다. `established`를 쓸 때는 UDP와 ICMP를 따로 다룬다. 임시 줄의 지속 시간을 필요한 만큼으로 둔다 |
| 로그에서 보이는 흔적 | `deny ... log` 줄의 적중 횟수 증가. `show access-lists`의 Reflexive 임시 줄과 `time left`. 밖에서 먼저 들어오는 SYN만 켜진 패킷이 20번 줄에 쌓이는 모습 |

## 약어·용어

| 용어 | 뜻 |
|---|---|
| `established` | ACK나 RST가 켜진 TCP 패킷에만 맞는 ACL 키워드. 이미 맺어진 연결의 답을 통과시킨다 |
| Reflexive ACL | 나가는 패킷을 보고 그 답이 들어올 임시 줄을 저절로 만드는 ACL |
| `reflect` | 나가는 쪽 줄에서 임시 목록에 줄을 적게 하는 키워드 |
| `evaluate` | 들어오는 쪽 ACL에서 임시 목록과 비교하게 하는 키워드 |
| 상태 추적 (stateful inspection) | 나간 연결을 기억했다가 그 답만 들이는 방식. 방화벽의 기본 동작 |
| 3-way handshake | TCP 연결을 맺는 SYN, SYN+ACK, ACK 세 번의 교환 |

## 함께 생각해 보기

- `established`를 쓰면 안 되는 자리는 어디일까? 우리 회사에서 UDP를 쓰는 통신(DNS 같은)을 떠올려 본다.
- 부서 사이 ACL도 "필요한 것만 연다"로 바꾸면 무엇이 좋아지고 무엇이 힘들어질까?

## 강의 메모

### 시간 배분 (30분)

| 절 | 시간 | 방식 |
|---|---|---|
| 목적 | 4분 | 지사 PC에서 한결물류로 ping. 답이 없는 장면부터 |
| 1 established | 6분 | 2일차 handshake 그림을 다시 |
| 2 Reflexive | 12분 | 대본 11, 12번. 임시 줄이 생기고 줄어드는 time left |
| 3 방화벽의 시작 | 5분 | 두 기본값 표 |
| 4 보고서 | 3분 | 남은 위험이 줄어드는 기록 |

### 물어볼 것

- "LC-IN만 보고는 들어오는 패킷이 답인지 시도인지 알 수 있을까?" 없다. 나간 것을 기억하는 무언가가 필요하다.
- "`evaluate`를 20번 줄 아래에 두면 어떻게 될까?" 답이 20번 줄에서 먼저 버려진다.
- 두 번째 함께 생각해 보기의 답: 정책이 더 단단해지지만, 새 업무가 생길 때마다 줄을 더해야 하고 빠뜨리면 업무가 멈춘다. 그래서 보통 회사 안은 막을 것을 적고, 중요한 자산 앞(서버, 장비 관리)에만 열 것을 적는 방식을 섞는다.

### 자주 헷갈리는 것

| 헷갈리는 것 | 바로잡기 |
|---|---|
| `reflect`와 `evaluate`를 같은 ACL에 쓴다 | `reflect`는 나가는 쪽, `evaluate`는 들어오는 쪽 |
| LC-OUT 때문에 라우터의 EIGRP 알림이 막힌다 | 라우터가 스스로 만든 패킷은 나가는 쪽 ACL을 지나지 않는다 |
| established면 안전하다 | ACK를 켠 가짜 패킷에도 맞는다. 상태를 기억하지 않는다 |
| 임시 줄은 계속 남는다 | `time left`가 다하면 사라진다 |

### 진행 요령

- 패킷트레이서가 `reflect`와 `evaluate`를 받지 않으면, 이 절은 개념과 강사 설명으로 하고 실습은 `established`로 TCP만 확인한다(웹이나 텔넷으로). 수업 전에 확인한다.
- 시간이 모자라면 2번 절의 실습은 강사 화면으로만 보여 주고, 학생은 개인 실습의 더 해 볼 것으로 한다. 사고 01 보고서 시간이 먼저다.
