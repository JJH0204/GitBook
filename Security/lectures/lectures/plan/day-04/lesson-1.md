# 1. 라우팅과 경로표

> 상위: [4일차 정적 라우팅과 지사 연결](README.md)
> 드로잉: 1. 라우팅과 경로표 드로잉 (9장)

## 학습 목표

- 라우터가 경로표를 보고 다음 장비까지만 보낸다는 것을 압니다
- `show ip route` 의 한 줄을 읽습니다(종류, 목적지, 관리 거리, 다음 장비)
- 여러 줄이 맞으면 가장 구체적인 줄이 이긴다는 것을 압니다
- 가는 길과 돌아오는 길이 모두 있어야 통신이 된다는 것을 압니다

## 다리 놓기

3일차에 본 HQ-R1의 경로표에는 C와 L 줄만 있었습니다. 모두 라우터에 직접 붙은 VLAN입니다. 오늘 서울 지사(192.168.20.0/27)를 잇는데, 이 네트워크는 본사 라우터에 직접 붙어 있지 않습니다. 라우터는 직접 붙지 않은 네트워크를 스스로 알지 못합니다. 누군가 알려 줘야 합니다.

## 1. 라우터는 다음 장비까지만 안다

라우터는 패킷의 목적지 주소를 보고 경로표에서 맞는 줄을 찾아, 그 줄이 가리키는 다음 장비에게 넘깁니다. 목적지까지의 전체 길을 아는 것이 아니라 바로 다음 한 칸만 압니다.

택배 분류 센터와 같습니다. 대구 센터는 서울행 상자를 대전 센터로 보낼 뿐, 서울의 어느 집까지 어떻게 가는지는 모릅니다. 대전 센터는 다시 자기 표를 보고 다음 센터로 보냅니다. 센터 하나라도 표에 서울이 없으면 상자는 거기서 멈춥니다.

| 라우터의 일 | 내용 |
|-------------|------|
| 목적지 보기 | 패킷의 목적지 IP 주소를 읽는다 |
| 표 찾기 | 경로표에서 목적지가 들어가는 줄을 찾는다 |
| 넘기기 | 그 줄의 다음 장비(next hop)에게 보낸다 |
| 못 찾으면 | 버리고, 보낸 쪽에 `Destination host unreachable` 을 알린다 |

> 2일차 다른 대역 실험의 그 메시지가 바로 마지막 줄입니다.

## 2. 경로표 한 줄 읽기

```
S       192.168.20.0/27 [1/0] via 192.168.99.2
```

| 부분 | 뜻 |
|------|----|
| `S` | 경로를 안 방법. S는 정적(사람이 넣음) |
| `192.168.20.0/27` | 목적지 네트워크 |
| `[1/0]` | 앞은 관리 거리, 뒤는 메트릭 |
| `via 192.168.99.2` | 다음 장비의 주소 |

맨 앞 글자로 경로를 어떻게 알았는지 압니다.

| 글자 | 뜻 | 만나는 날 |
|------|----|-----------|
| C, L | 직접 연결된 네트워크, 라우터 자신의 주소 | 2, 3일차 |
| S | 정적 경로 | 오늘 |
| S* | 정적 기본 경로. 모르는 목적지는 모두 여기로 | 오늘 |
| R | RIP이 알려 준 경로 | 5일차 |
| O | OSPF가 알려 준 경로 | 6일차 |
| D | EIGRP가 알려 준 경로 | 7일차 |

관리 거리(Administrative Distance)는 경로를 알려 준 쪽을 얼마나 믿는지의 점수입니다. 낮을수록 더 믿습니다. 같은 목적지로 가는 길을 두 군데서 알려 주면, 관리 거리가 낮은 쪽을 씁니다.

| 알려 준 쪽 | 관리 거리 |
|------------|-----------|
| 직접 연결 | 0 |
| 정적 경로 | 1 |
| EIGRP | 90 |
| OSPF | 110 |
| RIP | 120 |

메트릭은 같은 방법으로 알게 된 길들 중 어느 길이 더 좋은지의 점수입니다. 정적 경로는 0입니다. 5일차부터 의미가 생깁니다.

## 3. 가장 구체적인 줄이 이긴다

목적지가 여러 줄에 맞으면, 네트워크 부분이 가장 긴 줄(프리픽스가 가장 큰 줄)을 씁니다.

| 경로표의 줄 | 192.168.10.40으로 가는 패킷 |
|-------------|------------------------------|
| `0.0.0.0/0` (기본 경로) | 맞는다. 모든 주소가 맞는다 |
| `192.168.10.0/24` | 맞는다 |
| `192.168.10.32/27` | 맞는다. 가장 구체적이라 이 줄을 쓴다 |

주소록에서 "대구"보다 "대구 중구"가, 그보다 "대구 중구 동성로"가 더 정확한 것과 같습니다. 기본 경로 `0.0.0.0/0` 은 네트워크 부분이 0비트라 모든 주소에 맞고, 다른 줄이 하나도 맞지 않을 때만 쓰입니다.

## 4. 경로를 아는 세 가지 방법

| 방법 | 누가 | 좋은 점 | 아쉬운 점 |
|------|------|---------|-----------|
| 직접 연결 | 라우터가 저절로 | 설정할 것이 없다 | 붙어 있는 네트워크만 안다 |
| 정적 경로 | 관리자가 손으로 | 예측할 수 있고, 밖에서 바꿀 수 없다 | 바뀔 때마다 사람이 고쳐야 한다 |
| 동적 경로 | 라우터끼리 알려 준다 | 망이 커져도 알아서 맞춘다 | 거짓 정보를 받을 수 있어 지켜야 한다 |

새봄상사처럼 본사와 지사 하나인 작은 망은 정적 경로로 충분합니다. 5일차부터 지사가 늘고 길이 많아지는 상황에서 동적 라우팅으로 바꿉니다.

## 5. 가는 길과 돌아오는 길

통신은 한 방향이 아닙니다. 지사 PC가 본사 서버에 ping을 치면, 요청은 지사에서 본사로 가고 답은 본사에서 지사로 돌아옵니다. 그래서 두 라우터 모두 상대 쪽 네트워크로 가는 길을 알아야 합니다.

지사 PC에서 본사 서버로 ping을 칠 때입니다.

| 설정 | 결과 |
|------|------|
| 본사 라우터만 지사로 가는 길을 앎 | 지사 라우터가 본사로 가는 길을 몰라 요청이 출발하지 못한다 |
| 지사 라우터만 본사로 가는 길을 앎 | 요청은 본사 서버에 닿지만, 본사 라우터가 답을 지사로 돌려보낼 줄 모른다 |
| 둘 다 앎 | 통신된다 |

한쪽만 설정하고 `Request timed out` 이 나오면, 요청은 갔는데 답이 못 돌아온 것일 수 있습니다. 경로 문제는 늘 양쪽 경로표를 함께 봅니다.

## 함께 생각해 보기

- 우리 집 공유기의 경로표에는 어떤 줄이 있을까요? 공유기에 연결된 집 안 네트워크와 기본 경로를 떠올려 봅니다.
- 관리 거리가 낮을수록 믿는다면, 누군가 관리 거리가 아주 낮은 거짓 경로를 라우터에 넣을 수 있다면 무슨 일이 생길까요?

### 시간 배분 (25분)

| 절 | 시간 | 방식 |

| 2 경로표 한 줄 | 7분 | 3일차의 `show ip route` 를 다시 띄워 C와 L을 읽고, 오늘 생길 S 줄을 예고 |
| 3 가장 구체적인 줄 | 5분 | 주소록 비유 |
| 4 세 가지 방법 | 4분 | |
| 5 돌아오는 길 | 3분 | 대본에서 일부러 한쪽만 설정해 보는 장면으로 이어진다 |

### 물어볼 것

- "대구 센터는 서울의 어느 집인지 알까요?" 모릅니다. 다음 센터만 압니다.
- "192.168.10.40으로 가는 패킷이 /24 줄과 /27 줄에 모두 맞으면?" /27입니다.
- 두 번째 함께 생각해 보기의 답: 그 라우터를 지나는 통신이 엉뚱한 곳으로 가거나(엿보기, 바꾸기) 버려집니다(마비). 라우터의 설정 권한을 지키는 2일차의 잠금, 그리고 5일차 동적 라우팅의 인증이 모두 이것을 막는 일입니다.

### 자주 헷갈리는 것

| 헷갈리는 것 | 바로잡기 |
|-------------|----------|
| 다음 장비 칸에 최종 목적지 주소를 적는다 | 바로 옆 라우터의 주소를 적는다. 최종 목적지는 그다음 라우터들이 책임진다 |
| 관리 거리가 높을수록 좋다 | 낮을수록 더 믿는다 |
| 관리 거리와 메트릭은 같은 것이다 | 관리 거리는 알려 준 쪽끼리의 비교, 메트릭은 같은 방법 안에서 길끼리의 비교 |
| 기본 경로는 항상 쓰인다 | 다른 줄이 하나도 맞지 않을 때만 쓰인다 |

### 진행 요령

- 경로표의 맨 위 Codes 설명은 길어서 처음에 겁을 줍니다. 오늘은 C, L, S, S*만 읽게 합니다.
- 관리 거리 표는 5~7일차에 계속 돌아옵니다. 칠판 구석에 남겨 둡니다.
