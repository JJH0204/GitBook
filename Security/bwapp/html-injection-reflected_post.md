## 1. 목적

GET과 달리 POST는 매개변수가 URL에 나타나지 않는다. 같은 취약점이 POST에서도 생기는 원리와 요청 값을 확인하는 방법, 방어를 설명한다.

## 2. 구성 요소

| 번호 | 요소 | 설명 |
|---|---|---|
| 1 | POST 본문 | 입력값이 URL이 아니라 요청 본문에 담긴다 |
| 2 | 프록시 | 브라우저와 서버 사이에서 요청을 보고 바꾸는 도구 |
| 3 | 인코딩된 값 | 특수 문자가 URL 인코딩되어 전달된다. 이중으로 인코딩된 경우도 있다 |

## 3. 동작 원리

1. 폼 제출 시 값이 본문에 담겨 전송된다.
2. 프록시로 요청을 열어 보면 `<`, `>`가 `%3c`, `%3e`로 인코딩되어 있다.
3. 서버가 디코딩해 응답에 출력할 때 이스케이프하지 않으면 GET과 같은 결과가 나온다.
4. 더블 인코딩 규칙은 [URL 더블 인코딩](doubleencoding.md)을 따른다.

URL에 값이 보이지 않는 것은 숨겨진 것이 아니라 단지 위치가 다른 것이다. POST라고 해서 안전하지 않다.

## 4. 탐지·방어

| 방어 | 내용 |
|---|---|
| 출력 이스케이프 | `htmlspecialchars()`를 출력 직전에 적용한다. 요청 방식과 무관하다 |
| 서버 측 검증 | 허용 문자와 길이를 정한다 |
| 로그 흔적 | 웹 서버 기본 로그는 POST 본문을 남기지 않는다. 본문 검사는 WAF 또는 애플리케이션 로그에서 한다 |

## 5. 약어와 용어

|---|---|
| WAF | 웹 애플리케이션 방화벽 |
