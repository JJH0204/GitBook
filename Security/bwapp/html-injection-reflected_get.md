## 1. 목적

입력값이 URL 쿼리로 전달되어 응답 HTML에 그대로 출력될 때, 입력에 든 HTML이 브라우저에서 해석되는 현상을 이해한다. bWAPP 보안 수준(low, medium, high)별로 방어가 어떻게 달라지는지 본다.

## 2. 구성 요소

| 번호 | 수준 | 관찰한 현상 | 확인 방법 |
|---|---|---|---|
| 1 | low | 입력한 HTML 태그가 서식으로 해석된다. 입력을 받는 매개변수가 방어 없이 출력된다 | 이름 입력란에 `<h1>hello</h1>`을 넣고 제목 서식으로 출력되는지 본다 |
| 2 | medium | 입력이 문자열로 처리되어 태그가 해석되지 않는다. 서버가 `<`, `>`를 HTML 엔티티로 바꾼다 | 같은 입력을 넣고 태그가 글자 그대로 보이는지 본다 |
| 3 | medium 우회 | 특수 문자를 URL 인코딩해서 보내면 처리 방식이 달라질 수 있다. 예: `<h1>hello</h1>`는 `%3ch1%3ehello%3c%2fh1%3e` | 주소창 쿼리에 인코딩된 값을 넣고 결과를 비교한다 |
| 4 | high | 출력 시 이스케이프가 적용되어 태그가 해석되지 않는다 | 같은 입력으로 확인한다 |

## 3. 동작 원리

* 브라우저는 서버에 입력을 보낼 때 특수 문자를 URL 인코딩한다. 서버는 받은 값을 디코딩한다.
* 서버의 필터가 인코딩된 문자열 형태를 검사하고 이후에 디코딩하면, 검사 시점과 사용 시점의 값이 달라진다. 자세한 규칙은 [URL 더블 인코딩](doubleencoding.md)에 있다.
* medium의 방어는 필터 방식이고, high의 방어는 출력 이스케이프 방식이다. 후자가 근본적인 방어다.

## 4. 탐지·방어

{% hint style="info" %}
NOTE: HTML 인젝션을 막는 가장 좋은 방법은 출력 시 `htmlspecialchars()`를 적용하는 것이다. 입력 길이를 제한하면 피해 범위를 줄이는 보조 수단이 된다.
{% endhint %}

| 방어 | 내용 |
|---|---|
| 출력 이스케이프 | `htmlspecialchars($값, ENT_QUOTES, 'UTF-8')`를 출력 직전에 적용한다 |
| 길이·형식 검증 | 이름 같은 입력은 허용 문자와 최대 길이를 서버에서 정한다 |
| 로그 흔적 | 쿼리에 `<`, `>` 또는 `%3c`, `%3e`가 포함된 요청 |

## 5. 약어와 용어

| 용어 | 뜻 |
|---|---|
| HTML 인젝션 | 입력이 HTML 문서 구조로 해석되는 취약점 |
| HTML 엔티티 | `<`를 `&lt;`로 쓰는 것처럼 문자를 대체하는 표기 |
