## 1. 증상

| 항목 | 내용 |
|---|---|
| 화면 | 입력이 `admin`을 포함하면 `no!`가 출력되고 종료된다 |
| 목표 | 쿼리 `id`가 디코딩 후 `admin`과 같아지게 해 `solve(26)`이 호출되게 한다 |

## 2. 가능 원인

| 번호 | 취약점 | 근거 코드 |
|---|---|---|
| 1 | 필터 검사 후에 입력을 다시 디코딩한다 | `preg_match("/admin/", ...)` 뒤에 `urldecode(...)` |
| 2 | PHP가 쿼리를 이미 한 번 디코딩한 값을 `urldecode`로 또 디코딩한다 | `$_GET['id']`는 1차 디코딩된 값이다 |

서버 코드는 다음과 같다.

```php
<?php  include "../../config.php";  
  if($_GET['view_source']) view_source();  
?><html>  
<head>  
<title>Challenge 26</title>  
<style type="text/css">  
body { background:black; color:white; font-size:10pt; }     
a { color:lightgreen; }  
</style>  
</head>  
<body>  
<?php  if(preg_match("/admin/",$_GET['id'])) { echo"no!"; exit(); }  $_GET['id'] = urldecode($_GET['id']);  
  if($_GET['id'] == "admin"){    solve(26);  
  }  
?>  
<br><br>  
<a href=?view_source=1>view-source</a>  
</body>  
</html>
```

## 3. 격리 절차

원본이 남긴 인코딩 문자열은 다음 두 가지다. 두 번째 문자열은 첫 번째 문자열의 `%`를 `%25`로 다시 인코딩한 이중 인코딩이다.

```
%22%61%64%6D%69%6E%22
%2522%2561%2564%256D%2569%256E%2522
```

1. (3-01) 필터가 `admin` 문자열을 직접 찾는다는 점을 확인한다. → 결과: 평문 `admin`은 `no!`로 차단된다.
2. (3-02) `id` 값을 이중 인코딩한 문자열로 보낸다. → 결과: 정규식 검사 시점에는 `admin`이라는 글자가 보이지 않아 통과한다.
3. (3-03) `urldecode` 뒤의 값을 `admin`과 비교하는 분기가 실행된다.

{% hint style="warning" %}
CAUTION: 원본은 인코딩 문자열 두 줄만 남기고 어느 줄이 최종 해답인지, 따옴표(`%22`)가 왜 포함됐는지 설명하지 않았다. 3-02의 결과는 코드 구조에서 읽은 것이며 실행해 확인하지 않았다.
{% endhint %}

## 4. 탐지·방어

이 절은 원본에 없던 일반 지식이며 미검증이다.

- 원인: 검증(필터)이 정규화(디코딩)보다 앞에 있다.
- 완화: 입력을 먼저 한 번만 디코딩·정규화한 뒤 검증하고, 같은 값을 검증과 사용에 모두 쓴다. 차단 목록 대신 허용 목록으로 검증한다.
- 로그 흔적: 접근 로그의 쿼리 문자열에 `%25`로 시작하는 이중 인코딩 패턴이 나타난다.
