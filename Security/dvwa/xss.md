## 1. 목적

XSS(Cross-Site Scripting)는 사용자 입력이 검증·인코딩 없이 HTML 응답에 포함되어, 피해자 브라우저에서 공격자가 정한 스크립트가 실행되는 취약점이다. 세션 쿠키 탈취, 화면 변조, 피싱 페이지 연결로 이어질 수 있다.

## 2. 구성 요소

| 유형 | 입력이 머무는 곳 | 영향 범위 | 원본의 관찰 |
|---|---|---|---|
| 반사형(Reflected) | 요청에만 있고 응답에 즉시 출력된다 | 그 링크를 연 사용자 | `name` 값이 비었는지만 검사하고 그대로 출력한다 |
| 저장형(Stored) | DB 등에 저장되어 페이지를 열 때마다 출력된다 | 페이지를 보는 모든 사용자 | 이름·메시지 두 필드 모두 영향을 준다 |

## 3. 동작 원리

1. 사용자 입력이 서버로 전달된다.
2. 서버가 입력을 인코딩하지 않고 HTML에 넣어 응답한다.
3. 브라우저가 입력 문자열을 코드로 해석해 실행한다.
4. 저장형은 2단계 전에 DB 저장이 끼고, 이후 모든 열람자에게 반복된다.

## 4. 보안 수준별 차이 (반사형)

| 수준 | 방어 방식 | 한계 |
|---|---|---|
| low | 방어 없음. 비었는지만 확인한다 | 입력이 그대로 실행된다 |
| medium | 특정 태그 문자열(`script`)을 공백으로 바꾼다 | 대소문자 변형, 문자열 안에 태그를 끼워 넣는 방식으로 우회된다 |
| high | 정규식으로 태그 이름을 문자 단위로 제거한다 | 스크립트 태그가 아닌 다른 태그의 이벤트 속성으로 우회된다 |
| impossible | `htmlspecialchars()`로 HTML 특수 문자를 이스케이프한다 | 일반 출력 문맥에서는 실행되지 않는다 |

## 5. 보안 수준별 차이 (저장형)

| 수준 | 관찰 |
|---|---|
| low | 입력 길이 제한이 화면(클라이언트) 쪽에만 있어 개발자 도구로 완화할 수 있다. 두 필드 모두 취약하다. 이전에 저장한 스크립트가 먼저 실행될 수 있다 |
| medium | `message` 필드는 `htmlspecialchars()`로 처리하지만 `name` 필드는 대소문자 변형 등에 취약하다 |
| high | 방어가 부족한 필드가 남아 있으면 여전히 위험하다 |

원본은 저장형으로 `body`의 `onload`에서 외부 사이트를 iframe으로 불러와 피싱 화면처럼 보이게 하는 사례도 다뤘다. 해당 문자열은 문서에 옮기지 않는다.

## 6. 탐지·방어 (일부 미검증)

{% hint style="warning" %}
CAUTION: 블랙리스트(특정 문자열 제거)는 우회된다. 출력 시 문맥에 맞는 인코딩이 기본 방어다.
{% endhint %}

| 방어 | 설명 |
|---|---|
| 출력 인코딩 | HTML 본문은 `htmlspecialchars()`(ENT_QUOTES, UTF-8)처럼 문맥(본문, 속성, JS, URL)에 맞게 인코딩한다 |
| 입력 검증 | 길이·형식을 서버에서 검증한다. 클라이언트 검증만 믿지 않는다 |
| CSP | `Content-Security-Policy`로 인라인 스크립트와 외부 스크립트 출처를 제한한다 |
| 쿠키 속성 | 세션 쿠키에 `HttpOnly`를 설정해 스크립트가 읽지 못하게 한다 |
| 로그 | 요청 파라미터에 `<`, `>`, `on…=` 패턴이 나타나고, 저장 필드에 태그가 들어 있으면 흔적이다 |

## 7. 약어·용어

| 용어 | 뜻 |
|---|---|
| XSS | 크로스 사이트 스크립팅 |
| CSP | 브라우저가 실행할 스크립트 출처를 제한하는 응답 헤더 |
| HttpOnly | 스크립트가 쿠키를 읽지 못하게 하는 쿠키 속성 |
