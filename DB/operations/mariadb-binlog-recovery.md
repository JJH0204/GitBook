# [생성형 AI] 이진 로그와 시점 복구

## 작업 식별

| 항목 | 내용 |
|---|---|
| Task ID | DB-OPS-008-DO |
| 유형 | D&O (개념) |
| 목적 | 이진 로그(binary log)가 무엇이고, 논리 백업과 합쳐 특정 시점으로 복구하는 흐름을 이해한다 |
| 작성 | 생성형 AI 초안 (사람 검토 전) |
| 확인 상태 | 미검증 (MariaDB 문서 지식을 정리한 것이며 이 환경에서 실행하지 않았다. 옵션 이름과 기본값은 사용 버전의 문서로 확인한다) |
| 개정 | R1 (2026-11-19) |

## 1. 목적

논리 백업(DB-OPS-006-MP)은 백업한 순간의 상태만 되돌린다. 백업 이후에 일어난 변경까지 복구하려면 변경 기록이 필요하며, MariaDB에서는 이진 로그가 그 기록이다.

## 2. 구성 요소

| 구성 | 설명 |
|---|---|
| 이진 로그 | 데이터를 바꾸는 문장(또는 변경된 행)을 순서대로 기록한 파일. `SELECT`는 기록하지 않는다 |
| `log_bin` | 이진 로그를 켜는 서버 설정 |
| `binlog_format` | 기록 방식. `STATEMENT`(문장), `ROW`(행 변경), `MIXED`가 있다 |
| `SHOW BINARY LOGS;` | 현재 로그 파일 목록을 보는 문장 |
| `mysqlbinlog` | 이진 로그를 SQL 텍스트로 풀어 주는 도구 (MariaDB에서는 `mariadb-binlog` 이름이 쓰이는 버전이 있다) |

## 3. 동작 원리

### 3.1 시점 복구 흐름

| 순서 | 동작 |
|---|---|
| 1 | 정기적으로 논리 백업을 받는다. 백업 시점이 복구의 출발점이다 |
| 2 | 사고가 나면 가장 최근 백업을 새 서버 또는 새 데이터베이스에 복원한다 |
| 3 | 백업 시점 이후의 이진 로그를 `mysqlbinlog`로 풀어 사고 직전까지의 구간만 골라 적용한다 |
| 4 | 결과를 확인한 뒤 서비스를 전환한다 |

구간은 `mysqlbinlog`의 시간 옵션(`--start-datetime`, `--stop-datetime`) 또는 위치 옵션(`--start-position`, `--stop-position`)으로 지정한다. 잘못된 `DELETE`가 실행된 직전 위치까지만 적용하는 것이 목표다.

### 3.2 백업과 이진 로그의 역할 구분

| 항목 | 논리 백업 | 이진 로그 |
|---|---|---|
| 담는 것 | 한 시점의 전체 데이터 | 시점 이후의 변경 이력 |
| 복구 단위 | 백업 시점 | 원하는 시점까지 |
| 크기 | 데이터 크기에 비례 | 변경량에 비례 |

{% hint style="danger" %}
WARNING: 이진 로그에는 변경된 데이터 값이 그대로 들어 있다. 파일 권한을 소유자만 읽도록 제한하고 외부에 공유하지 않는다.
{% endhint %}

{% hint style="warning" %}
CAUTION: 이진 로그는 같은 디스크에 두면 디스크가 망가질 때 데이터와 함께 사라진다. 다른 저장소에 복사해 두고, 오래된 로그 삭제 주기(`binlog_expire_logs_seconds` 등, 버전별 이름 확인)가 마지막 백업 주기보다 길어야 복구 구간이 비지 않는다.
{% endhint %}
