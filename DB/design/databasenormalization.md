## 1. 목적

정규화는 테이블을 작은 단위로 분해해 데이터 중복을 줄이고 데이터 무결성을 유지하는 과정이다. 이상(Anomaly)을 방지하는 것이 핵심 목표다.

정규화를 하는 이유는 다음과 같다.

1. 데이터 중복을 줄여 저장 공간 낭비를 막는다.
2. 한 사실을 한 곳에만 저장해 데이터 무결성을 유지한다.
3. 이상 현상을 막는다.
4. 데이터 구조를 일관되게 만든다. 단, 분해하면 조회 시 조인이 늘어 성능이 나빠질 수도 있다. 성능이 필요하면 물리적 설계에서 의도적으로 정규화를 되돌리기도 한다(반정규화).

### 이상 현상(Anomaly)

| 이상 | 설명 |
|---|---|
| 삽입 이상(Insertion Anomaly) | 특정 데이터를 넣으려면 불필요한 다른 데이터를 함께 넣어야 한다 |
| 삭제 이상(Deletion Anomaly) | 한 데이터를 지우면 관련 없는 데이터까지 함께 사라진다 |
| 갱신 이상(Update Anomaly) | 중복 저장된 값을 바꿀 때 모든 행을 고치지 않으면 값이 어긋난다 |

예시는 수강 테이블이다. 학생이름이 학생ID마다 여러 행에 중복된다.

| 학생ID | 강의ID | 학생이름 | 강의명 |
|---|---|---|---|
| 101 | C001 | 홍길동 | 데이터베이스 |
| 102 | C002 | 김철수 | 운영체제 |
| 101 | C002 | 홍길동 | 운영체제 |

* 갱신 이상: 학생 101의 이름을 바꾸면 2개 행을 모두 고쳐야 한다.
* 삽입 이상: 수강 신청을 하지 않은 학생 정보는 이 테이블에 넣을 수 없다(기본 키의 일부인 강의ID가 비기 때문이다).
* 삭제 이상: 학생 102의 수강을 취소하면 학생 102의 정보도 사라진다.

## 2. 구성 요소

정규형은 함수적 종속을 기준으로 정의한다.

| 용어 | 뜻 |
|---|---|
| 함수적 종속(Functional Dependency) | 속성 A의 값이 정해지면 속성 B의 값이 하나로 정해지는 관계. `A → B`로 쓴다 |
| 결정자(Determinant) | `A → B`에서 A |
| 후보 키(Candidate Key) | 행을 유일하게 식별하는 최소 속성 집합. 후보 키 중 하나가 기본 키가 된다 |
| 부분 함수 종속 | 기본 키의 일부 속성에만 종속되는 관계 |
| 이행적 종속(Transitive Dependency) | `A → B`, `B → C`이면 `A → C`가 B를 거쳐 성립하는 관계(B는 키가 아님) |
| 다치 종속(MVD) | 한 속성 값에 대응하는 두 속성 집합이 서로 독립적인 관계. `A ↠ B` |
| 조인 종속(JD) | 테이블을 둘 이상으로 분해한 뒤 조인하면 원래 테이블이 정확히 복원되는 관계 |

정규형 조건 비교는 다음과 같다. 위 정규형은 아래 정규형을 포함한다.

| 정규형 | 조건 | 해결 문제 | 예제 |
|---|---|---|---|
| 1NF | 모든 컬럼이 원자값을 가진다 | 한 컬럼에 값 여러 개 | 전화번호 여러 개 |
| 2NF | 1NF + 부분 함수 종속 제거 | 키 일부에 종속된 속성 | 강의ID → 강의명 |
| 3NF | 2NF + 이행적 종속 제거 | 비키 속성 간 종속 | 학과코드 → 학과명 |
| BCNF | 3NF + 모든 결정자가 후보 키 | 후보 키가 아닌 결정자 | 교수 → 과목 |
| 4NF | BCNF + 비자명한 다치 종속은 키로부터만 | 독립적인 다중 값 | 학생-동아리, 학생-자격증 |
| 5NF | 4NF + 모든 조인 종속이 후보 키로 설명됨 | 3개 이상 테이블로의 무손실 분해 | 중개인-제조사-제품 |

## 3. 동작 원리

### 3-1. 제1 정규형(1NF)

조건은 모든 컬럼이 더 나눌 수 없는 원자값(Atomic Value)을 갖는 것이다. 반복 그룹을 제거한다.

정규화 전(1NF 위반)이다. 전화번호 컬럼에 값이 두 개 들어 있다.

| 학생ID | 이름 | 전화번호 |
|---|---|---|
| 101 | 홍길동 | 010-1234-5678, 010-5678-1234 |
| 102 | 김철수 | 010-7777-8888 |

정규화 후(1NF)이다. 원자값만 저장되며 학생ID와 이름이 중복될 수 있다.

| 학생ID | 이름 | 전화번호 |
|---|---|---|
| 101 | 홍길동 | 010-1234-5678 |
| 101 | 홍길동 | 010-5678-1234 |
| 102 | 김철수 | 010-7777-8888 |

### 3-2. 제2 정규형(2NF)

조건은 1NF를 만족하고 부분 함수 종속을 제거하는 것이다. 기본 키가 복합 키일 때 키의 일부에만 종속되는 속성을 분리한다.

정규화 전(2NF 위반)이다. 기본 키는 (학생ID, 강의ID)다.

| 학생ID | 강의ID | 학생이름 | 강의명 |
|---|---|---|---|
| 101 | C001 | 홍길동 | 데이터베이스 |
| 102 | C002 | 김철수 | 운영체제 |
| 101 | C002 | 홍길동 | 운영체제 |

* 학생이름은 학생ID에만 종속된다(부분 함수 종속).
* 강의명은 강의ID에만 종속된다(부분 함수 종속).

정규화 후(2NF)이다. 세 테이블로 나눈다.

학생 테이블

| 학생ID | 학생이름 |
|---|---|
| 101 | 홍길동 |
| 102 | 김철수 |

강의 테이블

| 강의ID | 강의명 |
|---|---|
| C001 | 데이터베이스 |
| C002 | 운영체제 |

수강 테이블

| 학생ID | 강의ID |
|---|---|
| 101 | C001 |
| 102 | C002 |
| 101 | C002 |

### 3-3. 제3 정규형(3NF)

조건은 2NF를 만족하고 이행적 종속을 제거하는 것이다. 기본 키가 아닌 속성이 다른 비키 속성을 거쳐 기본 키에 종속되는 관계를 분리한다.

정규화 전(3NF 위반)이다. 학생ID → 학과코드 → 학과명의 이행적 종속이 있다.

| 학생ID | 학생이름 | 학과코드 | 학과명 |
|---|---|---|---|
| 101 | 홍길동 | CS01 | 컴퓨터공학 |
| 102 | 김철수 | EE02 | 전자공학 |

정규화 후(3NF)이다.

학생 테이블

| 학생ID | 학생이름 | 학과코드 |
|---|---|---|
| 101 | 홍길동 | CS01 |
| 102 | 김철수 | EE02 |

학과 테이블

| 학과코드 | 학과명 |
|---|---|
| CS01 | 컴퓨터공학 |
| EE02 | 전자공학 |

### 3-4. BCNF(Boyce-Codd Normal Form)

조건은 3NF를 만족하고 모든 결정자가 후보 키인 것이다. 3NF를 만족해도 후보 키가 아닌 속성이 후보 키의 일부를 결정하면 BCNF를 위반한다.

{% hint style="warning" %}
CAUTION: 원본의 교수-강의-강의실 예시(강의ID → 교수ID → 강의실)는 BCNF 위반이 아니라 이행적 종속이므로 3NF 위반 예시다. 아래 예시로 교체했다.
{% endhint %}

정규화 전(BCNF 위반)이다. 한 교수는 한 과목만 가르치고, 한 학생은 한 과목에서 한 교수에게만 배운다고 가정한다. 후보 키는 (학생, 과목)과 (학생, 교수)다. 교수 → 과목이 성립하는데 교수는 후보 키가 아니다.

| 학생 | 과목 | 교수 |
|---|---|---|
| 학생A | 데이터베이스 | 교수김 |
| 학생B | 데이터베이스 | 교수김 |
| 학생A | 운영체제 | 교수박 |

정규화 후(BCNF)이다. 결정자 교수를 기준으로 분해한다.

교수-과목 테이블

| 교수 | 과목 |
|---|---|
| 교수김 | 데이터베이스 |
| 교수박 | 운영체제 |

학생-교수 테이블

| 학생 | 교수 |
|---|---|
| 학생A | 교수김 |
| 학생B | 교수김 |
| 학생A | 교수박 |

{% hint style="warning" %}
CAUTION: BCNF로 분해하면 (학생, 과목) → 교수 같은 종속을 한 테이블에서 검사할 수 없게 될 수 있다. 3NF는 종속을 보존하며 분해할 수 있지만 BCNF는 항상 그렇지 않다.
{% endhint %}

### 3-5. 제4 정규형(4NF)

조건은 BCNF를 만족하고, 비자명한 다치 종속(MVD)이 있으면 결정자가 키(슈퍼키)여야 한다는 것이다. 한 학생이 가진 동아리와 자격증처럼 서로 독립적인 다중 값을 한 테이블에 넣으면 모든 조합이 중복 저장된다.

정규화 전(4NF 위반)이다. 학생ID ↠ 동아리, 학생ID ↠ 자격증이며 두 값은 서로 관계가 없다.

| 학생ID | 동아리 | 자격증 |
|---|---|---|
| 101 | 축구 | 정보처리기사 |
| 101 | 축구 | SQL 전문가 |
| 101 | 독서 | 정보처리기사 |
| 101 | 독서 | SQL 전문가 |

정규화 후(4NF)이다. 독립적인 다치 종속을 테이블로 분리한다.

학생-동아리 테이블

| 학생ID | 동아리 |
|---|---|
| 101 | 축구 |
| 101 | 독서 |

학생-자격증 테이블

| 학생ID | 자격증 |
|---|---|
| 101 | 정보처리기사 |
| 101 | SQL 전문가 |

### 3-6. 제5 정규형(5NF)

조건은 4NF를 만족하고, 모든 조인 종속이 후보 키로 설명되는 것이다. 5NF 분해는 둘보다 많은 테이블로 나눴다가 조인했을 때 원래 데이터가 정확히 복원될 때만 쓴다. 복원되지 않으면 분해하면 안 된다.

5NF가 필요한 예시이다. "중개인이 제조사를 대리하고, 제조사가 제품을 만들고, 중개인이 그 제품을 취급하면 중개인은 그 제조사의 그 제품을 판다"는 규칙이 성립한다고 가정한다.

중개인-제조사-제품 테이블(분해 전)

| 중개인 | 제조사 | 제품 |
|---|---|---|
| A | X사 | P1 |
| A | X사 | P2 |
| A | Y사 | P1 |

분해 후(5NF)이다. 세 테이블을 조인하면 위 3개 행이 그대로 복원된다.

| 중개인 | 제조사 |
|---|---|
| A | X사 |
| A | Y사 |

| 제조사 | 제품 |
|---|---|
| X사 | P1 |
| X사 | P2 |
| Y사 | P1 |

| 중개인 | 제품 |
|---|---|
| A | P1 |
| A | P2 |

{% hint style="warning" %}
CAUTION: 원본의 프로젝트-직원-부서 예시는 분해 후 조인하면 원본에 없던 행(p001, E02, D01)이 생긴다. 이 데이터에는 조인 종속이 없으므로 3개로 분해하면 안 된다. 5NF 예시로 쓸 수 없어 위 예시로 교체했다.
{% endhint %}

{% hint style="info" %}
NOTE: 실무에서는 3NF 또는 BCNF까지 적용하는 경우가 많다. 4NF와 5NF는 다치 종속과 조인 종속이 실제로 있을 때만 검토한다.
{% endhint %}
