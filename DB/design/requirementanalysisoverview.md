# 요구사항 분석 개요

## 작업 식별

| 항목 | 내용 |
|---|---|
| Task ID | DB-DSN-002-DO |
| 유형 | D&O (개념) |
| 목적 | 요구사항 분석의 목표와 수집·분류·명세화·검증 활동을 설명한다 |
| 확인 상태 | 미검증 (원본 페이지와 일반 지식을 정리한 것이며 이 환경에서 실행해 확인하지 않았다) |
| 개정 | R1 (2026-11-18) |

## 1. 목적

요구사항 분석은 사용자가 원하는 기능과 데이터를 정의해 데이터베이스와 시스템 설계의 기초를 만드는 단계다. 불완전한 시스템, 높은 유지보수 비용, 성능 저하를 예방한다.

목표는 세 가지다.

1. 사용자가 원하는 기능과 데이터를 정확히 이해한다.
2. 데이터의 흐름과 관계를 정의한다.
3. 데이터베이스 설계의 기초를 마련한다.

## 2. 구성 요소

| 번호 | 활동 | 설명 |
|---|---|---|
| 1 | 요구사항 수집 | 인터뷰, 설문 조사, 문서 분석 등으로 정보를 모은다 |
| 2 | 요구사항 분류 | 기능적 요구사항과 비기능적 요구사항으로 나눈다 |
| 3 | 요구사항 명세화 | 유스케이스 다이어그램, DFD, SRS로 문서화한다 |
| 4 | 요구사항 검증 | 사용자가 원하는 기능과 일치하는지 확인한다 |

### 요구사항 수집 방법(Requirement Elicitation)

| 방법 | 설명 |
|---|---|
| 인터뷰(Interview) | 이해관계자(Stakeholder)와 직접 대화해 요구사항을 수집한다 |
| 설문 조사(Survey/Questionnaire) | 많은 사용자에게 같은 질문을 해 데이터를 수집한다 |
| 문서 분석(Document Analysis) | 기존 시스템 문서를 검토해 요구사항을 파악한다 |
| 워크숍(Workshop) | 여러 관계자와 회의해 요구사항을 논의한다 |
| 프로토타이핑(Prototyping) | 간단한 모델을 만들어 사용자 피드백을 받는다 |

### 요구사항 분류(Requirement Classification)

| 구분 | 정의 | 포함 내용 |
|---|---|---|
| 기능적 요구사항(Functional) | 시스템이 무엇을 해야 하는지 | 데이터 저장, 조회, 수정, 삭제 등 |
| 비기능적 요구사항(Non-functional) | 시스템이 어떤 품질로 동작해야 하는지 | 성능, 보안, 확장성 등 |

기능적 요구사항 예시는 다음과 같다.

| ID | 요구사항 설명 |
|---|---|
| FR-01 | 사용자는 로그인 후 상품을 검색할 수 있어야 한다 |
| FR-02 | 사용자는 장바구니에 상품을 추가할 수 있어야 한다 |
| FR-03 | 관리자는 상품 정보를 추가, 수정, 삭제할 수 있어야 한다 |
| FR-04 | 사용자는 주문 후 결제할 수 있어야 한다 |

비기능적 요구사항 예시는 다음과 같다.

| ID | 요구사항 설명 |
|---|---|
| NFR-01 | 시스템은 초당 100건 이상의 주문을 처리할 수 있어야 한다 |
| NFR-02 | 사용자 로그인 시 2초 이내에 응답해야 한다 |
| NFR-03 | 비밀번호는 암호화되어 저장되어야 한다 |
| NFR-04 | 장애 발생 시 10초 이내에 자동 복구되어야 한다 |

### 요구사항 명세화 도구(Requirement Specification)

| 도구 | 설명 |
|---|---|
| 유스케이스 다이어그램(Use Case Diagram) | 사용자(액터)와 시스템 기능의 관계를 표현한다 |
| 데이터 흐름도(DFD) | 데이터가 어떻게 흐르고 처리되는지 표현한다. [DB-DSN-003-DO](data_flow_diagram.md)를 따른다 |
| 요구사항 명세서(SRS, Software Requirements Specification) | 요구사항을 문서로 상세히 정리한다 |

유스케이스 예시는 액터별 기능 목록으로 적을 수 있다.

| 액터 | 유스케이스 |
|---|---|
| 사용자 | 로그인, 상품 검색, 장바구니 추가, 결제 |
| 관리자 | 상품 관리, 재고 확인 |

### 요구사항 검증(Requirement Validation)

요구사항 분석이 끝나면 요구사항이 올바른지 검토한다.

| 방법 | 설명 |
|---|---|
| 검토(Review) | 프로젝트 팀과 함께 문서를 검토한다 |
| 프로토타입 테스트(Prototype Testing) | 시제품을 만들어 사용자 피드백을 받는다 |
| 테스트 케이스 작성(Test Case Generation) | 요구사항이 테스트 가능한지 확인한다 |

## 3. 동작 원리

1. 수집한 요구사항을 기능적·비기능적으로 분류한다.
2. 분류한 요구사항을 다이어그램과 문서로 명세화한다.
3. 명세를 사용자와 검토해 오류와 누락을 찾는다.
4. 검증된 명세를 개념적 설계([DB-DSN-004-DO](conceptual-design.md))의 입력으로 넘긴다.

## 4. 약어·용어

| 용어 | 뜻 |
|---|---|
| 이해관계자(Stakeholder) | 시스템과 이해관계가 있는 사용자, 관리자, 발주자 등 |
| FR / NFR | 기능적 / 비기능적 요구사항 ID 접두어 |
| SRS | 소프트웨어 요구사항 명세서 |
