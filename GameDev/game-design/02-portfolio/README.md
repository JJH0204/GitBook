# 02. 팀 프로젝트를 기획서 포트폴리오로 재가공하기

새로 뭔가를 만드는 것보다, **이미 진행 중인 프로젝트에서 내가 내린 결정**을 기획 산출물로 역산해 정리하는 편이 훨씬 효율적이다. 실제로 내린 결정에는 제약(일정, 인원, 기술)과 결과가 있어서, 가상의 기획서보다 설득력이 강하다.

## 작업 → 산출물 변환표

| 내가 한 작업 | 포트폴리오 산출물 | 면접관이 확인하려는 것 | 템플릿 |
|---|---|---|---|
| 핵심 메커니즘 구현 | **시스템 기획서**: 메커니즘이 코어 루프와 어떻게 연결되는지, 조작감과 판정 기준을 어떻게 잡았는지 다이어그램으로 | 재미를 구조로 설명할 수 있는가 | [system-spec-template](system-spec-template.md) |
| 몬스터·스테이지 배치 | **레벨 디자인 문서**: 동선, 시야 유도, 긴장과 이완의 배치, 기믹 배치 의도를 탑뷰 맵과 함께 | 플레이어 경험을 공간으로 설계할 수 있는가 | [level-design-template](level-design-template.md) |
| 개발 볼륨 축소·조정 | **프로덕션·우선순위 의사결정서**: 무엇을 버리고(Cut) 무엇을 살렸는지, MVP 기준과 근거 | 제약 속에서 판단할 수 있는가 | [production-decision-template](production-decision-template.md) |
| 아이템·세계관 텍스트 | **내러티브·컨셉 기획서**: 설정이 인게임 룰과 UI/UX 연출에 어떻게 맞물리는지 | 설정을 시스템으로 번역할 수 있는가 | [narrative-concept-template](narrative-concept-template.md) |

## 역산 절차

### 1단계: 결정 캐기 (매주 수요일, 결정 카드 2장)

기억에만 의존하지 말고 **흔적**에서 찾는다.

| 흔적 | 찾을 것 |
|---|---|
| 커밋 로그, 이슈, 태스크 보드 | 수치 변경, 기능 삭제, 일정 변경 |
| 회의록, 메신저 | "그냥 빼자", "이건 다음에" 같은 말이 나온 순간 |
| 이전 빌드, 스크린샷, 녹화 | 버전 간 차이 (무엇이 왜 바뀌었나) |
| 기획 시트 수정 이력 | 숫자가 바뀐 지점과 그 이유 |

찾은 결정은 하나당 [결정 카드](decision-card-template.md) 한 장으로 쓴다. **버린 선택지**까지 적는 것이 핵심이다.

### 2단계: 카드 묶기 (카드 10장 이상 모였을 때)

카드를 위 변환표의 네 산출물로 분류한다. 한 산출물에 카드가 3장 이상 모이면 그 문서를 쓸 재료가 생긴 것이다.

### 3단계: 템플릿 채우기

카드를 근거로 템플릿을 채운다. 카드에 없는 내용이 필요하면 다시 1단계로 돌아가 흔적을 찾는다. **기억으로 지어내지 않는다.**

### 4단계: "왜?" 세 번

문서의 주요 주장마다 "왜?"를 세 번 묻고 답이 문서 안에 있는지 확인한다. 면접에서 받을 꼬리 질문이 바로 이것이다.

### 5단계: 1페이지 요약

상세 문서 맨 앞에 1페이지 요약을 붙인다. 면접관은 요약만 보고 상세를 열지 말지 정한다.

## 포트폴리오 문서 공통 원칙

- **결론 먼저.** 첫 문단에 "무엇을 왜 했고 결과가 어땠는지"를 쓴다.
- **내 기여 범위를 분명히.** 팀 프로젝트라면 "내가 결정한 것 / 제안한 것 / 실행만 한 것"을 구분한다. 부풀리면 꼬리 질문에서 무너진다.
- **수치와 그림.** 문장 세 줄보다 표 하나, 표 하나보다 다이어그램 하나.
- **실패와 수정을 넣는다.** v1에서 무엇이 틀렸고 v2에서 어떻게 고쳤는지가 가장 강한 증거다. ([플레이테스트 로그](../03-documentation-habits/playtest-log-template.md)의 Before → After를 가져온다.)
- **이 훈련장은 연습장이고, 이 GitBook은 공개다.** 팀의 비공개 자료(내부 수치, 미공개 설정)는 적기 전에 가린다. 완성된 문서는 노션이나 PDF로 옮겨서 제출한다.
