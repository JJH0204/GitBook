# AI 검증 프롬프트

> **초안을 다 쓴 뒤에만** 쓴다. 모든 프롬프트는 "다시 쓰지 말고 목록만 달라"는 조건을 포함한다. AI가 내 문서를 고쳐 쓰기 시작하면 그 순간부터 그건 내 문서가 아니다.

## 쓰는 법

1. 프롬프트를 복사하고 `[초안]` 자리에 문서 전체를 붙여 넣는다.
2. 받은 목록의 항목마다 **유효 / 무효**를 판정하고 이유를 한 줄 쓴다.
3. 유효한 항목만 문서에 `[AI]` 태그로 추가한다. 반영하는 문장은 내가 쓴다.
4. "내가 놓친 이유"를 한 줄 쓴다. 같은 이유가 반복되면 그게 내 사각지대다.

---

## 1. 엣지 케이스 찾기

```
아래는 내가 직접 쓴 게임 시스템 기획 초안이다.

규칙:
- 초안을 다시 쓰거나 해결책을 제안하지 말 것.
- 초안에 이미 적힌 예외는 빼고, 빠진 엣지 케이스만 찾을 것.
- 각 항목은 "어떤 상황에서 → 기획서대로 구현하면 무슨 일이 생기는가"로 쓸 것.

다음 관점으로 찾아라: 동시 입력, 경계값(같을 때·0일 때·최대일 때), 상태가 겹칠 때,
처리 도중 대상이 사라질 때, 저장·로드·씬 전환, 일시정지.

출력: 표 (번호 | 상황 | 생기는 일 | 심각도 상/중/하), 최대 10개, 심각도 순.

[초안]
```

## 2. 어뷰징·악용 찾기

```
아래 기획 초안을 "이 시스템으로 이득을 보려는 플레이어"의 입장에서 읽어라.

규칙:
- 초안을 다시 쓰거나 해결책을 제안하지 말 것.
- 실제로 가능한 악용만. 기획서에 적힌 규칙의 틈을 근거로 들 것.

관점: 세이브 스컴(저장·재접속으로 재시도), 무한 반복(매크로·방치),
자원 순환(사고팔기·분해·재조합 차익), 판정 경계 프레임 노리기, 의도하지 않은 지배 전략.

출력: 표 (번호 | 악용 방법 | 근거가 된 규칙 | 얻는 이득 | 심각도), 최대 8개.

[초안]
```

## 3. 개발자 관점 질문

```
너는 이 기획서를 받아서 구현해야 하는 게임 프로그래머다.
아래 초안을 읽고, 구현을 시작하기 전에 기획자에게 물어야 할 질문만 뽑아라.

규칙:
- 초안을 다시 쓰거나 답을 추측하지 말 것.
- 초안에 답이 이미 있는 질문은 빼라.
- 질문마다 "답이 없으면 구현을 어떻게 임의로 하게 되는가"를 한 줄 붙여라.

출력: 표 (번호 | 질문 | 답이 없으면 생기는 일), 최대 10개.

[초안]
```

## 4. 수식 검산과 극단값

```
아래는 내가 만든 밸런스 공식과 내가 직접 계산한 검산값이다.

규칙:
- 공식을 바꾸자고 제안하지 말 것. 내 계산이 맞는지와 극단값에서 생기는 일만 말할 것.
- 계산은 단계별로 보여 줄 것.

1. 내 검산값이 공식과 일치하는지 확인하라. 틀렸다면 어느 단계가 틀렸는지.
2. 입력이 0, 음수, 매우 큰 값일 때 결과가 어떻게 되는지 (0으로 나누기, 음수, 폭발).
3. 입력 변수 둘이 동시에 극단으로 갈 때 생기는 문제.

[공식과 검산값]
```

## 5. 논리 비약 찾기

```
아래 문서의 주장과 근거의 연결만 검토하라.

규칙:
- 문서를 다시 쓰지 말 것. 아이디어를 평가하지 말 것.
- "이 주장은 이 근거만으로는 성립하지 않는다"인 곳만 지적할 것.

출력: 표 (번호 | 주장 (문서 인용) | 빠진 연결 고리 | 면접관이 할 법한 꼬리 질문).

[문서]
```

## 6. 플레이테스트 해석 반박

```
아래는 플레이테스트 관찰 기록과 내 해석이다.

규칙:
- 해결책을 제안하지 말 것.
- 관찰 사실과 내 해석을 분리해서 보고, 해석이 관찰보다 앞서 나간 곳만 지적할 것.
- 같은 관찰을 설명하는 다른 해석이 있다면 제시할 것.

출력: 표 (번호 | 관찰 | 내 해석 | 다른 가능한 해석 | 둘을 구분하려면 무엇을 더 관찰해야 하나).

[관찰 기록과 해석]
```

## AI 응답을 받은 뒤 체크

- [ ] 유효 항목은 내 문장으로 문서에 반영하고 `[AI]` 태그를 붙였다
- [ ] "내가 놓친 이유"를 썼다
- [ ] A(내가 찾은 수)와 B(AI가 추가로 찾은 유효 수)를 기록했다
