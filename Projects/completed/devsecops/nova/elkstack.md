# ELK 스택 구축 구상 (ELK)

## 작업 식별

| 항목 | 내용 |
|---|---|
| Task ID | PRJ-NOV-006-DO |
| 유형 | D&O (구상 기록) |
| 목적 | 쿠버네티스 클러스터에서 ELK 스택과 보안 도구를 운영하는 구상과 그 선택 이유를 설명한다 |
| 확인 상태 | 미검증 (구상 단계 메모를 정리한 것이며 구축 결과는 원본에 없다. 확인 필요) |
| 개정 | R1 (2026-11-18) |

## 1. 목적

ELK 스택(Elasticsearch, Logstash, Kibana)과 Beats로 로그를 수집·분석하고, 이를 쿠버네티스 클러스터 안에서 운영하는 방법을 구상한다. 원본의 질문은 다음과 같다.

- Beats, Elasticsearch, Kibana로 쿠버네티스 클러스터 환경에서 ELK 서비스를 구동하는 방법은 무엇인가?
- ZAP을 Jenkins와 연동하는 방법은 무엇인가?

## 2. 구성 요소

| 구성 요소 | 구상 내용 |
|---|---|
| ELK 사용 환경 구조 | 경량화 모델, 클라우드 서비스 전용 모델 두 가지를 후보로 적었다 |
| Elasticsearch | Helm 차트로 설치하는 것이 가장 편하고 표준화된 방식이다. 상태 저장(Stateful) 워크로드다 |
| CI/CD 환경 | Jenkins, Web, DB |
| 보안 도구 | WAF, Wazuh, ELK Stack, Snort. 코드 분석은 SonarQube, 동적 분석은 OWASP ZAP(Jenkins 연동) |
| 클러스터 | 마스터 노드 1개와 노드 4개를 Linux 위에 구성하는 구상 |

{% hint style="info" %}
NOTE: Elasticsearch는 디스크에 데이터를 저장하므로 StatefulSet과 영구 볼륨(PersistentVolume)을 쓰는 상태 저장 워크로드로 다룬다. Helm 차트 외에 Elastic 공식 ECK 오퍼레이터를 쓰는 방법도 있다. 미검증.
{% endhint %}

## 3. 동작 원리

구상의 흐름은 다음과 같다. 원본에 순서가 명시돼 있지 않아 키워드를 연결한 것이다. 확인 필요.

1. 쿠버네티스 클러스터 안에 웹 서비스, DB, Jenkins를 둔다.
2. Beats가 로그를 수집해 Elasticsearch에 보내고 Kibana로 본다.
3. WAF, Wazuh, Snort가 보안 이벤트를 만든다.
4. Jenkins 파이프라인에서 SonarQube와 ZAP이 코드·애플리케이션을 검사한다.

원본의 판단은 "클러스터 안에 전부 넣는다"(Kubernetes를 클라우드 환경으로 본다)였다. 이유는 세 가지다.

| 번호 | 이유 |
|---|---|
| 1 | 실무에 더 가까운 구현 환경이다(kind 기반 환경과 거리가 있는 구성) |
| 2 | 포트 포워딩 같은 네트워크 문제가 줄어들 것으로 기대한다 |
| 3 | 서비스를 각각 따로 구현하는 것은 어렵지 않다 |

대안은 kind 기반에 호스트 머신 1대를 쓰고, 원터치로 구성하던 방식을 기반으로 kind와 Jenkins 연동을 다시 하는 것이다. kind 사용법은 [쿠버네티스 인프라 구상](kubernetesinfraidea.md)을 본다.

## 4. 팀 구성과 진행 방식 메모

원본에 적힌 역할은 디렉터, RnD, 기획, 엔지니어다. 진행 방식 메모는 다음과 같다.

| 단계 | 내용 |
|---|---|
| 오리엔테이션 | 목표를 설정한다. 필요한 것을 각자 조사하고 피드백한다 |
| 문서 작성 | 하루 동안 작성한다. 시장 분석을 거쳐 아이디어 제안서를 낸다 |
| 프로젝트 | 개인 프로젝트를 완료하는 과정. 정보 전달, 평가, 포트폴리오 순서 |

교육 과정 설계에 대한 의견도 적었다.

- 처음부터 목표를 정하고 프로젝트를 하면서 평가를 했다면 6개월 과정이 될 것이다.
- 강좌 이름에 영역이 많으면 초점이 흐려진다.
- Dev, Sec, Ops, 클라우드, 정보보안 영역을 한 과정에서 융합하는 방향성이 무엇인지 질문한다.
