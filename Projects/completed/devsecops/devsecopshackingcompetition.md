# 데브섹옵스 해킹대회 (DevSecOps)

## 작업 식별

| 항목 | 내용 |
|---|---|
| Task ID | PRJ-DSO-001-DO |
| 유형 | D&O (프로젝트 개요) |
| 목적 | 해킹대회용으로 기획한 "의도된 취약점을 가진 웹 서비스" 프로젝트(가칭 Aurora)의 목표, 서비스 후보, 취약점 설계, 인프라 구상을 설명한다 |
| 확인 상태 | 미검증 (원본 메모를 정리한 것이며 구축 결과는 확인하지 않았다) |

{% hint style="warning" %}
CAUTION: 이 문서의 취약점은 격리된 실습 환경에서 학습용으로 구축한 서비스에 의도적으로 넣는 것이다. 공격 코드나 페이로드는 포함하지 않는다. 취약한 서비스는 인터넷에 공개하지 않는다.

## 1. 목적

두 팀이 협력해 취약한 웹 서비스를 만들고, 탐지 시스템과 로그 시스템, 보안 관제 솔루션을 적용해 공격을 탐지·분석하는 프로젝트다. 프로젝트 가칭은 오로라(Aurora)다. Firewall과 LED에서 착안했고, 두 팀이 함께 아름다운 빛을 만들자는 뜻이다.

학습 목표는 두 가지다.

- 웹 개발 프로세스를 이해한다.
- 보안 취약점을 학습한다.

## 2. 구성 요소

| 구성 요소 | 내용 |
|---|---|
| 취약한 서버 | 의도된 취약점 10개를 넣은 웹 서비스 |
| 안드로이드 모바일 앱 | 원본에 항목만 있고 설명은 원본에 없음. 확인 필요 |
| 탐지 시스템 | 공격 트래픽 탐지 |
| 로그 시스템 | 로그 수집·분석 |
| 보안 관제 솔루션 | 온프레미스 환경을 관리·감독 |
| 보고서 | 탐지 히스토리, 데이터 분석 결과, 해결 방안 |

## 3. 서비스 후보 선정

기획 질문은 "어떤 웹 서비스를 만들까", "어떻게 만들까"였다. 후보는 다음과 같다.

| 후보 | 비고 |
|---|---|
| SNS 플랫폼 | 테마(음식, 여행, 학원, 회사)를 지우고 기능만 보면 SNS 기능이 남는다는 메모가 있다 |
| 사내 홈페이지(오피스 플랫폼) | 가장 구체적으로 설계했다. 5절 참조 |
| 여행 플래너 | 취약점 목록을 정리했다 |
| 학원 홈페이지 | 기능 목록을 정리했다 |
| 레시피 공유 플랫폼 | 기능별 취약점을 정리했다 |

서비스 선정 기준은 다음과 같다.

- 서버와 사용자의 상호작용이 잦다.
- DB가 필요하다.
- 접근 제어, 파일 업로드, 텍스트 업로드, 검색, 파일 다운로드, 리다이렉트, 외부 API 기능을 포함할 수 있다.

기술 스택은 프런트엔드가 HTML, CSS, JS이고 백엔드가 Python이다. 실제 구현은 Flask 예제에서 시작해 Django, Gunicorn, MariaDB 구성으로 발전했다. 구조는 [Aurora 앱 구조 (Aurora)](auroraappstructure.md)를 본다.

## 4. 후보별 기능과 취약점 설계

원본이 기록한 기능과 취약점 유형이다. 방어 열은 일반 지식으로 추가한 것이며 미검증이다.

| 서비스 | 기능 | 설계한 취약점 유형 | 일반적인 방어 |
|---|---|---|---|
| 레시피 공유 | 회원 관리 | SQL Injection, 무차별 대입 공격, 세션 하이재킹 | 매개변수화된 쿼리, 로그인 시도 제한, 세션 쿠키 `HttpOnly`·`Secure` 설정 |
| 레시피 공유 | 레시피 업로드 | 파일 업로드(웹쉘, 확장자 우회), 저장형 XSS | 확장자·MIME 검증, 업로드 경로 실행 금지, 출력 이스케이프 |
| 레시피 공유 | 미디어 관리 | 대용량 파일 업로드 | 업로드 크기 제한 |
| 레시피 공유 | 댓글·평점 | CSRF, XSS | CSRF 토큰, 출력 이스케이프 |
| 레시피 공유 | 검색·필터링 | SQL Injection | 매개변수화된 쿼리 |
| 여행 플래너 | 전반 | XSS, 불충분한 HTTPS, SQL Injection, 불완전한 비밀번호 저장, CSRF, 파일 업로드, DDoS, 경로 탐색, API 키 유출, 인증·권한 문제 | 위 항목 방어에 더해 TLS 적용, 비밀번호 해시 저장, 키를 코드 밖에서 관리 |
| 공통 | 공인·개인 계정 | 계정 권한 차이를 이용한 취약점. 개인 계정은 jpg, png, avi, mp4만 올릴 수 있고 공인 계정은 php 등 웹쉘이 가능하게 설계 | 서버 측에서 권한별 업로드 정책 강제 |

## 5. 사내 홈페이지(온프레미스) 설계

| 항목 | 내용 |
|---|---|
| 로그인 | 사원 ID/PW(DB)와 직위 |
| 접근 제어 | 직위에 따라 페이지, 게시물, 업로드를 제한한다 |
| 게시 기능 | 공지, 부서 페이지 게시물(파일·텍스트 업로드, 검색) |
| 메시지 | 페이지 내 사내 메시지(정보 노출, 파일 업로드·다운로드) |
| 관제 | 온프레미스 환경을 관리·감독하는 관제 솔루션 |

학원 홈페이지의 기능 목록은 다음과 같다.

| 기능 | 내용 |
|---|---|
| 접근 제어 | 로그인, 담당별 분류(강사, 학생) |
| 파일 업로드 | 과제 제출 또는 공유 |
| 텍스트 업로드 | 공지사항 |
| 검색 | 게시물·과제 검색 |
| 파일 다운로드 | 과제 다운로드 |
| 리다이렉트 | 로그인 후 대시보드 |
| 외부 API | 지도 API, SMS 알림 |

UI에 대한 판단은 다음과 같다. UI가 멋질 필요는 있으나 시간이 부족하다. 어느 정도 타협하고 품질은 추후 보완한다.

## 6. 동작 원리

프로젝트는 취약한 버전(aurora_1.0)을 먼저 만들고, 모의해킹과 보안 솔루션 적용 후 피드백하는 순서로 진행한다.

1. 취약점을 의도적으로 넣은 서비스를 만든다.
2. 모의해킹을 수행한다.
3. 보안 솔루션을 적용하고 탐지 결과를 직접 확인한다(비포·애프터).
4. 장점은 살리고 단점은 해결한다.
5. 결과를 보고서로 정리한다.

### 개발 환경과 인프라 구상

| 항목 | 내용 |
|---|---|
| 개발 환경 | 호스트 Windows, VS Code, kind(컨테이너 기반 쿠버네티스), GitHub Actions로 Docker 이미지 push |
| 마스터 노드 | 웹 대시보드, 모니터링 |
| 웹 서비스 노드 | Django 웹, MariaDB, WAF |
| 보안 노드 | Suricata, 로그 분석 |
| 네트워크 | 허용 규칙 예: 모든 출발지 80/tcp, 사내 대역 5000-5010/tcp. 세부 규칙은 원본에 없음, 확인 필요 |

배포 예시는 Docker Hub의 `<계정>/aurora:latest` 이미지로 컨테이너를 실행해 웹 서버를 구축하는 방식이다. 이 이미지는 컨테이너 안에 MariaDB와 Django가 함께 실행된다.

### WAF 적용 방법

| 방법 | 내용 |
|---|---|
| Way 1 | 웹 서버 또는 프록시 서버에 WAF 설정: Nginx + ModSecurity, Apache + ModSecurity |
| Way 2 | 클라우드 기반 WAF 서비스 |
| Way 3 | 원본에 내용 없음. 확인 필요 |

### Django 보안 강화 항목

- 보안 미들웨어(`SecurityMiddleware`)를 활성화한다.
- `X_FRAME_OPTIONS`, `CONTENT_SECURITY_POLICY` 등 보안 헤더를 설정한다.
- Django 기본 기능으로 CSRF와 XSS를 방지한다.
- 사용자 입력을 검증한다(SQL Injection 방지).

## 8. 약어·용어

| 용어 | 뜻 |
|---|---|
| WAF | Web Application Firewall. 웹 요청을 검사해 공격을 차단하는 방화벽 |
| ModSecurity | 오픈소스 WAF 엔진 |
| Suricata | 오픈소스 침입 탐지·방지 엔진 |
