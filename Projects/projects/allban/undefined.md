# 기획

> #### 문제인지
>
> * PC방에서 관리해야 하는 메뉴 레시피 양이 너무 많다. \
>   (다른 PC방에 비해 직접 조리해야 하는 음식의 가지 수가 많음)
> * 매번 카운터 PC를 조작해 주문을 열람해야 하는 번거로움
> * 레시피 양이 많아지며 자연스럽게 조리법의 변경이 이뤄지게 되면 다른 근무자에게 공유되기 어려워짐
> * 레시피를 기록하는 종이를 주방에 붙여서 관리하는데 매번 새로 코팅하고 작성하는 시간적 번거로움
> * 타이머를 별도로 구매하여 음식 조리 시간을 관리하는데 주방에서 조리하는 사람이 중간에 바뀔 경우 어떤 타이머가 어떤 음식을 조리 중인지 인지하기 어려움
> * 외부 사설 업체에 맞길 경우 레시피 유출 우려가 있음\
>   (레시피는 매장의 고유 자산임으로 독립된 서버가 있어야 함)
> * (중요) 외부 사설 업체에서 제공한 프로그램의 UI/UX가 형편없어서\
>   "이거 내가 만들어도 이것보다 잘 만들겠다"는 생각을 함
> * PC방 사업의 프렌차이즈화를 위해 독자 프로그램이 있다면 상품성이 극대화 될 것이라 판단

#### 문제 정의

* 관리의 문제 (레시피 데이터 수정 및 공유, 조리 진행 사항 공유 등의 문제 해결)
* 자산 유출의 문제 (외부 사설 서버를 통한 데이터 관리가 아닌 매장내 독립된 서버를 구축하여 보안 강화)
* 사업화를 위한 가치 향상 문제 (사업화를 위한 차별화 전략으로서 매우 중요한 포인트)

***

#### 기술 스택 선정

* 디자인 툴: 피그마
  * 실무에서 자주 사용된다고 알려진 디자인툴
  * 다른 플렛폼과 호환성이 높아 작성한 디자인을 공유하기 적절하다 판단
* 개발 및 배포: 플러터
  * 윈도우 프로그램과 안드로이드 앱을 동시에 구현해야 하는 점에서 크로스플랫폼 구현에 최적화되었다 판단
  * 다트 언어에만 익숙해진다면 추후 IOS, Mac 프로그램 개발에도 활용할 수 있다 판단하여 사용하기로 결정
  * 윈도우 호스트 프로그램과 안드로이드 태블릿 클라이언트 간의 코드 재사용성을 높여 1인 개발 효율을 극대화하기 위해 선택
* 서버: 로컬 네트워크 서버 + VPN
  * 자산 유출을 우려해 외부에서 접근할 수 없는 매장내 PC를 서버 호스트 PC로 사용하기로 결정
  * 호스트 PC와 테블릿의 통신을 위해 별도의 라우팅 테이블 작업이 필요하다 판단
  * 위 문제는 추후 사업화 전략에서 변수로 작용할 것이라 판단해 외부 VPN 서비스를 이용해 매장 관리자가 모뎀 또는 공유기 설정을 별도로 하지 않아도 쉽게 연결하고 통신할 수 있는 환경을 만드는 것이 좋다고 판단
  * 웹 소켓 기능을 통해 호스트 PC와 연결된 다수의 안드로이드 디바이스와 실시간 통신이 가능하도록 구현하는 것이 목표
  * 게임 서버 아키텍처에서 사용하는 로컬 호스트-클라이언트 구조를 차용하여, 외부 망 차단 시에도 주방 운영이 중단되지 않는 가용성을 확보하고자 함

#### 사업화 전략

* 본 프로젝트는 PC방 사업외에도 레시피(자산)관리가 중요한 다른 프렌차이즈 본사와 협업할 수 있는 B2B 솔루션으로 확장해 별도의 사업화 또한 가능하다 판단
