## 1. 문제 인지

실제 PC방 아르바이트 경험에서 확인한 문제다.

1. 관리해야 하는 메뉴 레시피가 많다. 다른 PC방보다 직접 조리하는 음식의 가짓수가 많다.
2. 주문을 보려면 매번 카운터 PC를 조작해야 한다.
3. 레시피가 늘며 조리법이 바뀌면 다른 근무자에게 공유하기 어렵다.
4. 레시피 종이를 주방에 붙여 관리해서, 바꿀 때마다 새로 코팅하고 작성해야 한다.
5. 조리 시간 관리용 타이머를 따로 구매해 쓰는데, 조리 담당이 중간에 바뀌면 어느 타이머가 어느 음식인지 알기 어렵다.
6. 외부 사설 업체에 맡기면 레시피가 유출될 수 있다. 레시피는 매장 고유 자산이라 독립된 서버가 필요하다.
7. (중요) 외부 업체가 제공한 프로그램의 UI/UX가 좋지 않아 "내가 만들어도 이보다 잘 만들겠다"고 생각했다.
8. PC방 사업을 프랜차이즈로 확장할 때 독자 프로그램이 있으면 상품성이 커진다고 판단했다.

## 2. 문제 정의

| 구분 | 내용 |
|---|---|
| 관리 | 레시피 데이터 수정과 공유, 조리 진행 상황 공유 |
| 자산 유출 | 외부 사설 서버가 아니라 매장 안 독립 서버로 데이터를 관리해 보안을 강화한다 |
| 사업화 | 차별화 전략으로서 상품 가치를 높인다 |

## 3. 기술 스택 선정

| 영역 | 선택 | 이유 |
|---|---|---|
| 디자인 도구 | Figma | 실무에서 자주 쓰는 도구로 알려져 있고, 다른 플랫폼과 호환성이 높아 디자인 공유에 적절하다고 판단했다 |
| 개발·배포 | Flutter | Windows 프로그램과 Android 앱을 동시에 만들어야 해서 크로스플랫폼에 적합하다고 판단했다. Dart에 익숙해지면 iOS, Mac 프로그램에도 쓸 수 있다. Windows 호스트와 Android 태블릿 클라이언트의 코드 재사용성을 높여 1인 개발 효율을 높이려 했다 |
| 서버 | 로컬 네트워크 서버 + VPN | 자산 유출을 막으려 외부에서 접근할 수 없는 매장 PC를 호스트로 정했다 |

서버 구성의 세부 판단이다.

1. 호스트 PC와 태블릿이 통신하려면 별도의 라우팅 테이블 작업이 필요하다고 판단했다.
2. 이 문제가 사업화 단계에서 변수가 된다고 보고, 외부 VPN 서비스로 매장 관리자가 모뎀이나 공유기를 따로 설정하지 않아도 연결되게 하는 방향을 택했다.
3. 목표는 웹소켓으로 호스트 PC와 다수의 Android 기기가 실시간 통신하게 하는 것이다.
4. 게임 서버 구조의 로컬 호스트-클라이언트 방식을 차용해, 외부 망이 끊겨도 주방 운영이 중단되지 않는 가용성을 확보하려 했다.

## 4. 사업화 전략

PC방 외에도 레시피(자산) 관리가 중요한 다른 프랜차이즈 본사와 협업하는 B2B 솔루션으로 확장하는 별도 사업화가 가능하다고 판단했다. 구체적인 계약이나 대상은 원본에 없다.

## 5. 약어·용어

| 용어 | 뜻 |
|---|---|
| B2B | 기업 간 거래 |
| VPN | 가상 사설망 |
| 라우팅 테이블 | 패킷을 어느 경로로 보낼지 정한 표 |
| 웹소켓 | 서버와 클라이언트가 연결을 유지하며 양방향으로 데이터를 주고받는 통신 방식 |
| 크로스플랫폼 | 하나의 코드로 여러 운영체제용 앱을 만드는 방식 |
