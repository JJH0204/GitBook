## 1. 디스코드 서버

| 번호 | 항목 | 내용 |
|---|---|---|
| 1 | 역할 | 서버 역할을 세 가지로 정했다: 데모 피드백 창구, 펀딩 알림 전환 허브, 코어 팬 공간 |
| 2 | 구조 | 안내(규칙, 공지, 개발일지), 커뮤니티(한국어·영어 채팅, 팬아트 포럼), 데모(안내, 버그 제보 포럼, 피드백 포럼), 라운지, 운영진 전용 |
| 3 | 포럼 태그 | 태그로 버그와 건의를 분류한다. "수정 완료"와 "반영 예정" 태그는 운영진만 쓴다 |
| 4 | 권한 | "개발팀" 역할만 안내 카테고리에 글을 쓴다. 입장 시 규칙에 동의하게 했다 |
| 5 | AutoMod | 멘션 스팸, 스팸 의심 콘텐츠, 비속어를 막는다. 기본 단어 필터는 영어만 지원하므로 한국어 욕설은 사용자 지정 단어가 필요하다 |
| 6 | 운영 주기 | 매일 5분 점검, 주 1회 개발일지, 주 1회 지표 기록. 혼자 주 1~2시간 안에서 운영할 수 있게 범위를 줄였다 |
| 7 | 복구 | 가입 방식 복구, 역할 이름 복구, 채널 삭제, 감사 로그 확인 방법을 문서 끝에 적었다 |

## 2. 채널 전략

- 보조 채널과 주력 채널을 구분했다. 숏폼과 영상 채널을 주력으로 두고, 디스코드는 전환과 피드백을 맡긴다.
- SNS 계정은 언어마다 따로 만들지 않는다. 계정을 나누면 팔로워와 추천 신호가 흩어지고, 영상을 만드는 사람은 소수라 계정이 늘면 운영이 무너진다. 유튜브는 한 채널에서 언어별 제목, 설명, 자막을 추가하고, 디스코드는 한 서버에 언어별 채널을 둔다.
- 레딧은 새 계정의 글을 자동 관리 봇이 걸러 낸다. 공개 전에 개발자 개인 계정으로 댓글 활동을 하며 이력을 쌓고, 홍보가 아닌 제작 과정 글부터 올린다. 계정 구매, 추천 품앗이, 같은 GIF 도배는 하지 않는다.

## 3. 배운 점

- 커뮤니티는 **대응 시간 목표**(버그 48시간, 질문 24시간)와 **제재 순서**를 먼저 정해야 운영이 지속된다.
- 담당자와 말투 규칙(존댓말, 소개 문구, 해외 표기)을 문서로 고정하면 여러 사람이 올려도 일관된다.
- 자동화(웹후크, 봇)는 수동 운영이 부담이 될 만큼 올린 뒤에 한다.
