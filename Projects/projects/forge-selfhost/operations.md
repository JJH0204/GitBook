## 이 영역이 하는 일

서버는 Windows 호스트 위의 WSL 배포판에서 컨테이너를 돌린다. 이 구성은 사람이 로그인하지 않아도 매일 새벽에 백업하고 재부팅하고, 복구되지 않으면 알리는 자동화가 필요하다. 스크립트 12개 안팎이 작업 스케줄러에 등록되어 다음 순서로 돈다.

| 시각 | 작업 이름 | 스크립트 | 하는 일 |
|---|---|---|---|
| 부팅 + 1분 | 01-Boot-Start | `keepalive.ps1` | WSL 배포판을 붙잡는 상주 프로세스를 띄운다. 끝나지 않는 작업이다 |
| 05:00 | 02-Nightly-Maintenance | `maintenance.ps1` | 점검 공지, 백업, 컨테이너 정상 종료, WSL 종료, 재부팅을 순서대로 실행한다 |
| 05:40부터 30분 간격 | 04-Healthcheck | `healthcheck.ps1` | 배포판과 서비스 응답을 확인하고, 이상이면 1회 자동 복구한다. 러너도 본다 |
| 06:00 | Morning-Report | `morning-report.ps1` | 재부팅 후 실제 복구 결과를 판정해 알린다 |
| 부팅 + 1분 | 06-Windows-Runner | `winrunner.ps1` | 빌드 러너를 감독한다(상세는 [CI 해체 분석](ci.md)) |
| 06:30 | 07-Project-Report | `project-report.ps1` | 이슈·커밋 진행 상황을 집계해 알린다 |
| (공용) | - | `lib-notify.ps1` | 알림 전송과 상태 수집 함수 모음 |

등록은 `register-tasks.ps1`(01~04), `register-morning.ps1`, `register-winrunner.ps1`, `register-projectreport.ps1`이 한다. 오프사이트 동기화(`offsite-sync.ps1`, `register-offsite.ps1`)와 계층 보관 스크립트(`tier-pc*.ps1`)는 백업 문서의 범위라 여기서 다루지 않는다.

## 핵심 코드 해설

### 1. 배포판을 붙잡는 상주 작업 (`scripts/keepalive.ps1`)

WSL은 VM을 유지하면서도 배포판은 유휴 시 종료한다. 배포판이 내려가면 systemd, docker, 컨테이너가 전부 정리된다. VM 수준 유휴 설정은 이를 막지 못한다. 그래서 배포판 안에서 끝나지 않는 프로세스를 하나 띄운다.

```powershell
$keep = Start-Process -FilePath 'wsl.exe' `
    -ArgumentList '-d', '<배포판>', '-u', 'root', '--', 'sleep', 'infinity' `
    -WindowStyle Hidden -PassThru
...
$keep.WaitForExit()
```

스크립트가 끝나면 배포판도 내려가므로 작업 스케줄러의 실행 시간 제한을 0(무제한)으로 둬야 한다. 기본값(3일)을 두면 사흘 뒤 서버가 조용히 죽는다고 주석에 적혀 있다.

### 2. 순서가 있는 야간 점검 (`scripts/maintenance.ps1`)

단순 `shutdown /r`은 WSL VM을 강제로 끄므로 DB가 다음 기동에서 크래시 복구로 올라온다. 컨테이너를 먼저 정상 종료한다.

```powershell
& wsl.exe -d <배포판> -u root -e /usr/local/bin/selfhost-down.sh
& wsl.exe --shutdown
Start-Sleep -Seconds 10
& shutdown.exe /r /f /t 30 /c "<사유>"
```

백업과 재부팅을 분리하지 않은 이유는 백업이 길어졌을 때 재부팅과 겹치지 않게 하려는 것이다. 백업 종료 코드가 0이 아니면 1시간 뒤 보고까지 기다리지 않고 즉시 알린다. 종료 코드 2는 백업 저장소 마운트가 끊긴 경우로 해석한다.

### 3. 상태 전이에서만 알리는 헬스체크 (`scripts/healthcheck.ps1`)

```powershell
$prev = if (Test-Path $stateFile) { (Get-Content $stateFile -Raw).Trim() } else { 'OK' }
...
if ($prev -ne 'FAIL') { Send-Discord ... } else { W '이미 FAIL 상태로 통보됨 — 중복 알림 생략' }
'FAIL' | Set-Content $stateFile -Encoding ascii
```

30분마다 같은 실패를 알리면 같은 내용이 쌓인다(원본 주석: 과거 장애에서 10번 쌓였다). 상태 파일에 직전 판정을 적어 두고 OK에서 FAIL, FAIL에서 OK로 바뀔 때만 알린다. 05:00~05:20은 재부팅 직후라 실패가 정상이므로 알림을 생략하고, 러너는 서버가 뜬 뒤에야 붙으므로 05:40까지 더 늦게 본다.

서비스 점검과 러너 점검은 상태 파일을 따로 쓴다. 같이 쓰면 러너만 죽었는데 서비스 장애로 알리거나, 서비스 복구가 러너 상태를 덮어쓴다.

### 4. 프로세스가 아니라 서버가 기록한 접속 시각으로 러너를 판정 (`scripts/healthcheck.ps1`)

러너 프로세스가 떠 있어도 서버에 붙지 못한 경우를 놓치지 않으려고, 서버 DB가 기록한 러너의 마지막 접속 시각을 조회한다. 5분(300초) 넘게 소식이 없으면 죽은 것으로 본다. 조회는 DB 컨테이너 안에서 소켓 인증으로 하므로 비밀번호가 필요 없다고 원본이 설명한다(접속 정보는 문서에 옮기지 않았다).

자동 복구는 작업 상태가 `Running`이어도 먼저 `Stop-ScheduledTask`로 멈추고 다시 시작한다. 작업을 `-Force`로 교체하면 감독 프로세스만 죽고 인스턴스 상태는 Running으로 남아, 이후 시작 요청이 "이미 실행 중"(0x800710E0)으로 거부되기 때문이다.

### 5. 판정 기준을 컨테이너가 아니라 도달성으로 (`scripts/morning-report.ps1`)

아침 보고는 "컨테이너가 떴는가"가 아니라 "네트워크를 통해 실제로 닿는가"를 본다. 과거에 컨테이너는 멀쩡한데 VPN 무인 모드가 꺼져 있어 5시간 불통이었던 장애에서 나온 기준이다. 판정 규칙의 요점은 다음과 같다.

| 항목 | 규칙 |
|---|---|
| 서비스 응답 | 200이 아니면 문제 |
| VPN 무인 모드 | 조회 결과가 확실히 꺼짐일 때만 문제. 조회 실패는 문제로 보지 않는다 |
| 재부팅 수행 | 가동 시간이 아니라 "오늘 05:00 이후에 부팅했는가"로 본다 |
| 백업 | 종료 코드, 마지막 스냅샷이 26시간을 넘었는지, 오프사이트 상태 |

조회 실패를 "꺼짐"으로 단정하면 오탐이 나고(첫 무인 사이클에서 실제로 발생), 가동 시간으로 판정하면 06:00이 아닌 시각에 수동 실행할 때 항상 오탐이 난다. 두 규칙 모두 그 결함을 고친 결과다.

### 6. 알림 공용 함수 (`scripts/lib-notify.ps1`)

모든 스크립트가 dot-source로 불러 쓴다. 웹훅 주소는 스크립트가 아니라 별도 비밀 파일에서 읽는다(스크립트는 보관·로그로 복사되기 때문). 전송은 UTF-8 바이트로 하고 3회 재시도한다. `Get-SelfhostStatus`는 WSL 쪽 상태 스크립트가 `key=value`로 출력한 것을 해시테이블로 바꾼다.

{% hint style="danger" %}
WARNING: 같은 저장소의 다른 파일(`ci/build.yml`)에는 웹훅 주소가 값 그대로 들어 있다. 이 문서에는 옮기지 않았다. 해당 웹훅은 유출된 것으로 보고 서비스 쪽에서 삭제 후 재발급해야 한다(값을 바꾸기만 해서는 히스토리에 남은 이전 값이 무효화되지 않는다). 상세는 [CI 해체 분석](ci.md)에 적는다.
{% endhint %}

### 7. 진행 보고의 안전장치 (`scripts/project-report.ps1`)

이슈 DB 조회가 전부 실패하면 완료 0, 잔여 0이 되어 "진행률 0%" 보고가 나갈 수 있다. 집계 전에 조회 성공 여부를 판정하고, 실패하면 "조회 실패" 보고만 보내고 종료한다. 상태 그룹을 나열해 더하지 않고 `전체 - 완료 - 취소`로 잔여를 구하며, `외 N건`은 별도 `count`로 구한다. 부분에서 전체를 추정하지 않기 위한 것이다. 이슈 DB 쿼리의 접속 정보는 옮기지 않았다.

## 따라 만들기

확인 상태: 미검증. 각 단계의 기대 결과는 원본 주석과 기록에 근거한 설명이다.

1. 상주 작업을 만든다. 배포판 안에서 `sleep infinity`를 실행하는 스크립트를 쓰고, 작업 스케줄러에 "시작 시 + 1분 지연", 실행 시간 제한 없음으로 등록한다. 기대 결과: 로그아웃 상태에서도 배포판이 Running으로 유지된다.
2. 실행 계정을 정한다. WSL 배포판은 만든 사용자 계정에 등록되므로 시스템 계정으로 `wsl.exe`를 돌리면 배포판이 보이지 않는다. 사용자 계정에 "로그온 여부와 무관하게 실행"(S4U)을 쓴다. 기대 결과: 로그인 없이 부팅해도 스택이 올라온다.
3. 기동·종료 스크립트를 배포판 안에 둔다(`selfhost-up.sh`, `selfhost-down.sh`, `selfhost-status.sh`의 역할). 상태 스크립트는 `key=value` ASCII로 출력한다. 기대 결과: Windows 쪽 스크립트가 값을 해시테이블로 읽는다.
4. 야간 점검 스크립트를 쓴다. 순서는 공지, 백업(종료 코드 확인), 컨테이너 정상 종료, WSL 종료, 재부팅이다. 먼저 `-NoReboot`로 시험한다. 기대 결과: 재부팅 없이 공지와 백업까지 돌고 배포판이 다시 올라온다.
5. 헬스체크를 쓴다. 상태 파일 하나(서비스), 하나(러너)를 두고 전이할 때만 알린다. 1회 자동 복구를 넣고, 재부팅 직후 구간은 알림을 생략한다. 기대 결과: 일부러 서비스를 내렸을 때 알림이 1회만 나가고 복구 시 복구 알림이 나간다.
6. 러너 감독을 쓴다. 러너가 접속할 주소를 러너 설정 파일에서 읽어 응답 대기, 시작, 종료 감시, 30초 후 재기동, 시작 전 고아 프로세스 정리, 로그 크기 제한(1MB 초과 시 회전)을 넣는다. 기대 결과: 러너를 강제 종료하면 감독이 다시 띄우고, 5분 넘게 오프라인이면 헬스체크가 복구한다.
7. 아침 보고를 쓴다. 도달성, 백업, 재부팅 수행 여부를 판정하고 문제가 없으면 정상, 있으면 목록으로 알린다. 기대 결과: 사람이 없어도 06:00에 한 건의 결과가 도착한다.
8. 등록 스크립트를 쓴다. 관리자 권한을 먼저 검사하고, 등록 후 `Get-ScheduledTask`로 실행 대상을 되읽어 대조한다. 한글이 든 스크립트는 UTF-8 BOM을 넣는다. 기대 결과: 승격이 없으면 "등록 완료"를 출력하지 않고 종료 코드 1로 끝난다.
9. 무인 검증을 한다. 사람이 로그인하지 않은 채 재부팅하고, 타임스탬프와 로그로만 사후 판정한다. 기대 결과: 로그인 이전 구간에 남은 로그로 복구를 입증한다.

## 알려진 한계·주의

- 작업 번호가 스크립트 사이에서 어긋난다(위 CAUTION).
- `register-tasks.ps1`은 01~04를 `-Force`로 다시 등록한다. 상주 작업(01)을 `-Force`로 교체하면 감독 프로세스만 죽고 상태는 Running으로 남는 문제가 있어, 이후 작업은 각자 등록 스크립트를 따로 둔다(원본 `register-projectreport.ps1` 주석).
- `healthcheck.ps1`은 서비스 확인에 호스트의 VPN 주소를 쓴다. 이 네트워킹 모드에서는 호스트의 로컬 주소로 컨테이너에 닿지 않기 때문이라고 적혀 있다. 주소 값은 옮기지 않았다.
- `lib-notify.ps1`의 알림 푸터와 `healthcheck.ps1`의 경로·주소에 개인 환경 값이 하드코딩되어 있다. 따라 만들 때는 설정 파일로 빼는 편이 낫다(원본에 없는 제안).
- 알림 채널이 하나(채팅 웹훅)이고 그 전송이 실패하면 사람에게 닿지 않는다. 전송 실패는 로그에만 남는다(`Send-Discord`는 3회 재시도 후 `$false`를 반환).
- Windows PowerShell 5.1은 BOM 없는 UTF-8 한글을 깨뜨려 파싱이 실패한다. 이 스크립트들은 `pwsh`(7)로 돌리며, 5.1과 호환이 필요한 파일에만 BOM을 넣었다.
