# 도입 결과와 회고

## 작업 식별

| 항목 | 내용 |
|---|---|
| Task ID | PRJ-FSH-003-DO |
| 유형 | D&O (결과와 회고) |
| 목적 | 구축 결과, 겪은 문제, 반복된 실패 패턴, 배운 점을 기록한다 |
| 확인 상태 | 미검증 (작성자의 기록을 정리한 것이며 이 환경에서 재현하지 않았다) |
| 개정 | R1 (2026-11-18) |

## 1. 결과

| 항목 | 상태 |
|---|---|
| Gitea(코드) | LFS 포함 약 19GB, 저장소 3개 이관 |
| Plane(이슈) | 워크스페이스 1개, 프로젝트 5개, 이슈 159개 이관 |
| CI/CD | 워크플로 실행 검증, 저장소 가드레일과 Unity 빌드·설치 파일 배포까지 |
| 외부 노출 | 포트포워딩 0건 |
| 무인 운영 | 새벽 점검(공지, 백업, 재부팅)과 복구 보고를 사람 개입 없이 수행 |
| 복구 능력 | 백업만으로 격리 환경에 적재해 DB, 이슈, LFS 표본, 커밋·브랜치까지 판독 |

## 2. 겪은 문제와 해결

### 설계를 바꾼 문제

| 문제 | 해결 |
|---|---|
| WSL 배포판이 유휴 상태에서 종료됨. VM은 살아 있는데 배포판이 죽어 컨테이너가 전부 정리됨 | 배포판 안에서 `sleep infinity`를 상주시키는 keep-alive 작업을 두고, 작업의 실행 시간 제한을 무제한으로 설정 |
| VPN의 무인 모드가 기본으로 꺼져 있어 GUI 사용자가 로그아웃하면 연결이 끊김. 새벽 재부팅 후 5시간 불통 | VPN 클라이언트를 무인 모드(`--unattended`)로 설정 |
| 로그아웃하면 WSL의 외부 디스크 마운트(9p)가 끊겨 백업이 통째로 실패 | 백업 스크립트에 마운트 검사와 강제 해제·재마운트를 넣고, 일부러 끊어 시험 |
| 그냥 `shutdown /r`을 하면 WSL VM이 급사해서 DB가 crash recovery를 탐 | 컨테이너 정상 종료 → `wsl --shutdown` → 재부팅 순서로 고정 |
| 백업과 재부팅이 별도 작업이라 겹칠 위험 | 하나의 새벽 작업으로 순차 실행 |

### 설정을 넣었지만 동작하지 않은 문제

- Git 서버가 읽지 않는 설정 파일에 크기 제한을 넣어 두었다. 파일에는 값이 멀쩡히 있었지만 서버는 무시했고 600MB push가 그대로 통과했다. 설정을 서버가 실제로 읽는 위치로 옮기고 나서 600MB는 거부되고 50MB는 통과하는 것을 확인했다.
- 환경변수의 점(`.`) 인코딩 오류로 존재하지 않는 설정 섹션이 만들어져, 끈 줄 알았던 데일리 점검이 실제로는 켜져 있었다. 섹션 이름을 눈으로 확인하고서야 알았다.

### 외부 도구의 함정

- 이슈 도구의 기본 자격증명이 문서값 그대로여서 전부 무작위로 교체했다. 접속 URL에도 자격증명이 하드코딩돼 있어 함께 다시 써야 했다.
- 설치 스크립트가 릴리스 정보를 파싱하지 못해 중단돼서, 태그를 직접 조회해 버전을 고정했다.
- 클라우드 드라이브 오프사이트 백업에서, 앱이 만든 파일만 보이는 권한 범위와 인증 클라이언트 변경이 겹쳐 기존 업로드가 접근 불가가 되었다. 자체 인증 클라이언트를 발급하고 앱을 게시해 토큰 만료도 피했다.

### 내 코드의 결함

- 조회 실패(unknown)를 "꺼짐"으로 단정해 첫 무인 사이클에서 오탐 경보가 났다 → "모른다"와 "나쁘다"를 판정식에서 분리.
- 가동 시간으로 재부팅 여부를 판정해 정해진 시각 밖에서는 항상 오탐이 났다 → "오늘 새벽 이후 부팅했는가"로 변경.
- PowerShell 변수가 대소문자를 구분하지 않아 서로 다른 두 변수가 같은 변수가 되었다.
- 복원 리허설이 `pg_isready`를 준비 신호로 써서, 초기화 중인 임시 서버에 먼저 성공해 오판했다 → 실제 쿼리 성공으로 변경.
- 컨테이너 로그가 이전 기동 분까지 누적되는 것을 모르고 crash recovery를 두 번 오진했다.

## 3. 반복된 실패 패턴

개별 버그보다 같은 유형이 반복된 쪽이 중요했다.

| 패턴 | 내용 | 대응 |
|---|---|---|
| A. "설정했다"와 "동작한다"를 혼동 | 파일에는 값이 있었지만 적용되지 않음(3회) | 설정 확인이 아니라 **동작 시험**을 검증 기준으로 삼는다 |
| B. 관측하지 않은 구간을 관측한 것처럼 단정 | 프로세스가 떴다는 사실만으로 "로그인과 무관하다"고 결론 → 5시간 불통 | 무인 동작은 **무인 구간에 남은 로그**를 근거로 한다 |
| C. 확인 가능한 것을 추정으로 전제 | 무료 용량, 도구의 지원 여부, NAS 평가 등 | **제약은 조회한다.** 한 번의 조회로 답이 나오는 것은 추정하지 않는다 |
| D. 사람의 실시간 개입이 필요한 검증 | 재부팅 후 로그인하지 말 것을 3번 지키지 못해 검증 오염 | 사람이 할 일을 줄이고 판정은 기계가 남긴 타임스탬프로 한다 |
| E. 실행 환경의 특성을 모른 채 결론 | MSIX 가상화로 보이는 경로가 다름, 변수 대소문자, 로그 누적 | 이상하면 **우회 경로로 교차 확인**한 뒤 결론낸다 |

## 4. 잘 작동한 것

- 600MB push, 복원 리허설, 로그아웃 프로브처럼 **동작 검증을 실제로 수행한 것.** 전부 여기서 결함이 드러났다.
- 실패를 크게 울리도록 설계한 것. 백업 스크립트가 종료 코드로 마운트 문제를 정확히 보고했고, 헬스체크가 장애를 30분마다 기록했다.
- NAS 사고의 근본 원인을 처음부터 차단한 것. push 크기 제한, 메모리 상한, LFS 강제 덕분에 이관된 저장소는 LFS 규칙이 건전했다.
- 되돌릴 수 있게 만든 것. 설정 파일 백업, ACL 버전 히스토리, 각 단계의 롤백 절차.

## 5. 남은 개선 여지

| 우선순위 | 항목 |
|---|---|
| 높음 | 무로그인 상태 새벽에 VPN CLI 조회가 실패하는 원인 규명 |
| 중간 | 오프사이트 이중화(NAS를 파일 저장소로 추가하면 사본 2벌) |
| 중간 | SMTP 미설정(이슈 멘션과 초대 메일 불가) |
| 중간 | 신규 계정 승인이 관리자 수동이라 온보딩 때 병목 |
| 낮음 | 서비스 HTTPS 승격, CI 확장 |

## 6. 배운 점

1. 검증 기준은 "값을 넣었다"가 아니라 "시험해서 동작을 확인했다"여야 한다.
2. 무인 동작을 주장하려면 사람이 없던 구간에 기계가 남긴 기록으로 말한다.
3. 한 번의 조회로 알 수 있는 것은 추정하지 않는다.
4. 판정식에서 "모른다"와 "나쁘다"를 구분한다.
5. 장애의 근본 원인은 장비가 아니라 구성(작은 장비에 풀스택)에 있을 수 있다. 원인과 결과를 잘못 이어 붙이지 않는다.
6. 백업은 복원해 보기 전까지 백업이 아니다.

## 7. 약어·용어

| 용어 | 뜻 |
|---|---|
| keep-alive | 유휴 종료를 막으려고 상주시키는 프로세스 |
| crash recovery | DB가 비정상 종료 뒤 로그로 상태를 복구하는 동작 |
| 복원 리허설 | 백업만으로 격리 환경에 서비스를 다시 올려 보는 검증 |
| 오프사이트 | 서버와 물리적으로 떨어진 위치의 백업 사본 |
