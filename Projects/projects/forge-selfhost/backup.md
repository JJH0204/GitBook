## 설계 원칙

NAS 시절 데이터가 전부 사라진 경험이 있어서, 이 프로젝트는 백업을 가장 중요한 산출물로 두고 재부팅 자동화보다 먼저 세웠다. 원칙은 세 가지다.

1. 원본과 다른 물리 디스크에 둔다.
2. 이 PC 전체가 사라져도 남는 사본을 하나 둔다.
3. 복원해 보기 전까지는 백업으로 치지 않는다.

## 구성 요소

| 겹 | 무엇을 | 어디에 | 보존 | 열려면 | 출처 |
|---|---|---|---|---|---|
| 1. 평문 DB 덤프 | Gitea DB, Plane DB 덤프(gzip)와 설정 | 백업 전용 디스크의 일자별 폴더 | 7일(7일 초과 폴더는 `find -mtime +7`로 삭제) | 비밀번호 불필요 | `PLAN.md` Phase 6 |
| 2. 암호화 스냅샷 | 저장소·LFS(`/srv/gitea/data`), `/srv/plane`, 덤프 폴더 | 같은 백업 디스크의 restic 저장소 | 일 14, 주 8, 월 6 | restic 비밀번호 필요 | `PLAN.md` Phase 6 |
| 3. 오프사이트 | 백업 디스크의 폴더 전체(1과 2) | 클라우드 드라이브 폴더 | 원본 미러(`sync`) | 클라우드 계정과 restic 비밀번호 | `scripts/offsite-sync.ps1` |

{% hint style="danger" %}
WARNING: 복구 경로가 비대칭이다. 저장소와 LFS 객체는 암호화 스냅샷에만 있다. 평문 덤프는 DB만 되살리므로, restic 비밀번호를 잃으면 코드와 에셋은 복구할 수 없다. 비밀번호는 이 서버 밖에 따로 보관한다. 비밀번호의 값과 위치는 문서에 쓰지 않는다.
{% endhint %}

## 일일 시간표

```
05:00  야간 점검 시작 공지(채팅 알림)
       -> WSL 안 selfhost-backup.sh 실행 (덤프 -> 스냅샷 -> 보존 정리)
       -> 컨테이너 정상 종료 -> wsl --shutdown -> 호스트 재부팅 (30초 뒤)
05:03  부팅, 서비스 자동 복구
05:30  오프사이트 동기화 (Windows 쪽 작업, 최대 6시간 제한)
06:00  아침 보고(복구 판정, 백업 상태, 복원 가능 일수, 오프사이트 용량)
```

{% hint style="info" %}
NOTE: 초기 설계는 백업 04:30, 재부팅 05:00으로 작업이 둘이었다. 현재 스크립트(`scripts/maintenance.ps1`)는 05:00 작업 하나가 백업을 끝낸 뒤에만 재부팅한다. 백업이 길어져 재부팅과 겹치는 위험을 없애기 위해서다.
{% endhint %}

## 겹별 해설

### 1. 점검 작업: 백업 후 종료 (`scripts/maintenance.ps1`)

실행 순서는 네 단계이며 스크립트가 `1/4`부터 `4/4`까지 로그를 남긴다.

| 단계 | 동작 |
|---|---|
| 1/4 | 점검 시작 공지. 컨테이너 수, 직전 스냅샷 시각, 백업 디스크 여유를 필드로 보낸다 |
| 2/4 | `wsl.exe`로 WSL 안의 백업 스크립트를 root로 실행하고 종료 코드를 받는다 |
| 3/4 | 정상 종료 스크립트로 컨테이너를 멈추고 `wsl --shutdown`, 10초 대기 |
| 4/4 | `shutdown.exe /r /f /t 30`. 실패하면 즉시 알림. `-NoReboot`를 주면 재부팅 대신 배포판을 다시 올린다 |

```powershell
& wsl.exe -d srv -u root -e /usr/local/bin/selfhost-backup.sh 2>&1 | ForEach-Object { W "  $_" }
$bkRc = $LASTEXITCODE
```

- 백업이 실패(종료 코드 0이 아님)해도 스크립트는 알림만 보내고 3/4, 4/4로 계속 진행한다. 코드 2는 백업 디스크 마운트가 끊긴 경우로 해석해 알린다(로그아웃 시 WSL의 9p 마운트가 끊기는 문제). 실패 알림에는 "덤프는 남아 있어 복구는 가능"이라고 안내한다.
- 정상 종료 후 재부팅하는 이유는 호스트가 WSL 가상 머신을 강제로 끄면 PostgreSQL이 크래시 복구로 올라오기 때문이다.

{% hint style="warning" %}
CAUTION: 백업이 실패해도 재부팅이 진행된다. 실패 알림을 받으면 다음 점검 전에 원인을 해결해야 한다. 이 동작이 의도인지 원본에 없음, 확인 필요.
{% endhint %}

### 2. 스냅샷 (`selfhost-backup.sh`, 구축 기록 기준)

WSL 안의 스크립트 본문은 형상 보관본에 없어 아래는 구축 기록의 설계다.

1. `pg_dump`로 Gitea DB와 Plane DB를 덤프한다(일자별 폴더).
2. restic으로 `/srv/gitea/data`, `/srv/plane`, 덤프 폴더를 증분 백업한다. 수 GB급 저장소를 매일 통째로 압축하지 않기 위해서다.
3. `restic forget`으로 일 14, 주 8, 월 6개를 남기고 정리한다(prune 포함).
4. 결과를 로그에 남기고, 실패하면 0이 아닌 종료 코드를 반환한다.

실측(구축 기록, 2026-08-07): 처리 약 19.4GiB, 저장 약 12.3GiB, 소요 3분 21초. 덤프는 하루치 약 120KB.

### 3. 오프사이트 동기화 (`scripts/offsite-sync.ps1`)

| 항목 | 내용 |
|---|---|
| 실행 위치 | Windows 쪽. 백업 폴더가 일반 Windows 폴더라서 WSL과 9p 마운트에 의존하지 않는다 |
| 방향 | 백업 폴더 → 클라우드 폴더(`<원격>:<폴더>`) 단방향 `rclone sync` |
| 시각 | 05:30. 05:00 점검 뒤, 06:00 보고 앞이다. 백업 직전에 두면 첫 업로드가 재부팅을 지연시킨다 |
| 설정 파일 | 비밀 폴더의 rclone 설정을 `--config`로 명시 지정(경로 `<값 생략>`). 앱 컨테이너의 경로 가상화 때문에 기본 경로는 실행 문맥마다 달리 보인다 |
| 권한 범위 | `drive.file` (rclone이 만든 파일만 접근) |
| 병렬도 | `--transfers 8 --checkers 16 --drive-chunk-size 64M --fast-list` |
| 삭제 안전장치 | `--max-delete 500` |
| 결과 기록 | 상태 파일에 `OK|시각|용량|소요|드라이브 여유` 또는 `FAIL|...` 한 줄 |
| 실패 처리 | 종료 코드 9이면 "삭제 한도 초과, 로컬이 대량 삭제됐을 수 있으니 덮어쓰기 전에 확인" 안내를 담아 알림 |

```powershell
$args = @(
    'sync', $SRC, $DST,
    '--config', $conf,
    ...
    '--max-delete', '500',
```

- `rclone sync`는 미러라서 로컬이 통째로 사라지면 삭제가 원격까지 전파된다. `--max-delete`는 restic prune이 보통 수~수십 개만 지운다는 점을 근거로 한도를 500으로 둔 것이다. 넘으면 중단하고 사람이 판단한다.
- 동기화 뒤 `rclone size`와 `rclone about`으로 원격 용량과 드라이브 여유를 읽어 보고에 싣는다. 출력의 첫 `{`부터 마지막 `}`까지 잘라 JSON으로 파싱한다. `size`는 한 줄, `about`은 여러 줄로 출력하기 때문이다.
- 스크립트에서 경로 변수 `$RCLONE`과 종료 코드 `$syncRc`를 다른 이름으로 둔 이유: PowerShell 변수는 대소문자를 구분하지 않아서 예전에 `$RC`와 `$rc`가 같은 변수가 되어 성공 직후 용량 조회가 매번 실패했다.

{% hint style="info" %}
NOTE: 발췌한 `$args`는 PowerShell의 자동 변수 이름이다. 스크립트 범위에서 대입은 되지만 혼동하기 쉽다. 동작에 문제가 있었다는 기록은 원본에 없음, 확인 필요.
{% endhint %}

{% hint style="warning" %}
CAUTION: 클라우드 OAuth client_id를 바꾸면 `drive.file` 범위에서는 이전 client가 올린 파일이 보이지 않는다(다른 앱으로 취급). 구축 기록은 옛 폴더를 지우고 전량 재업로드했다. client_secret 회전은 영향이 없다. OAuth 동의 화면이 "테스트" 상태면 리프레시 토큰이 7일 뒤 만료되어 백업이 조용히 멈추므로 게시 상태여야 한다.
{% endhint %}

### 4. 알림 (`scripts/lib-notify.ps1`)

- 웹훅 주소는 스크립트가 아니라 비밀 폴더의 파일에서 읽는다(스크립트가 형상 보관과 로그로 복사되기 때문). 파일 경로와 값은 쓰지 않는다.
- 알림은 `ok`, `warn`, `fail`, `info` 네 단계 색으로 보낸다. 헬스체크 알림은 상태가 바뀔 때만 보낸다(같은 메시지가 반복 쌓이는 것을 막기 위해서).

## 복원 절차

원본에 복원 스크립트는 없고 아래는 구축 기록의 리허설 절차를 순서로 정리한 것이다. 명령 옵션은 쓰지 않는다. 모든 단계는 확인 상태: 미검증.

{% hint style="danger" %}
WARNING: 복원은 운영 데이터에 덮어쓰지 말고 임시 경로와 별도 포트의 격리 환경에서 먼저 한다.
{% endhint %}

### 준비

- 백업 디스크 또는 오프사이트 사본에 접근할 수 있다.
- DB만 복구하려면 최근 7일 평문 덤프로 충분하다. 저장소·LFS를 복구하려면 restic 비밀번호가 필요하다.
- PostgreSQL 메이저 버전이 스택별로 다르다(Gitea 17, Plane 15). 복원은 같은 메이저 버전의 임시 컨테이너에 한다.

### 절차

| 번호 | 작업 | 기대 결과 |
|---|---|---|
| SUBTASK 1 | 오프사이트에서 가져와야 하면 백업 폴더 구조(`restic/`, `daily/`)를 로컬로 내려받는다 | 두 하위 폴더가 존재한다 |
| SUBTASK 2 | `restic check`로 저장소 무결성을 확인한다 | 오류 0건 |
| SUBTASK 3 | 복원할 스냅샷을 정해 임시 경로로 `restic restore`한다 | 임시 경로에 저장소, LFS, 덤프가 나타난다 |
| SUBTASK 4 | 같은 메이저 버전의 임시 PostgreSQL 컨테이너를 띄운다 | 실제 쿼리(`select 1`)가 성공한다 |
| SUBTASK 5 | 덤프를 적재한다 | 적재 오류 0건 |
| SUBTASK 6 | DB를 검증한다 | Gitea 테이블 수, 저장소·계정 수, Plane 워크스페이스·프로젝트·이슈 수가 운영 값과 일치한다 |
| SUBTASK 7 | 저장소와 LFS를 검증한다 | 복원한 저장소의 커밋·브랜치 수가 운영과 같고, LFS 객체 표본의 SHA-256이 일치한다 |
| SUBTASK 8 | 필요하면 별도 포트로 Gitea를 기동해 저장소와 이슈가 살아나는지 눈으로 확인한다 | 웹에서 저장소와 이슈가 보인다 |

{% hint style="warning" %}
CAUTION: 준비 확인에 `pg_isready`를 쓰지 않는다. 공식 PostgreSQL 이미지는 초기화 중에 임시 서버를 띄우는데 `pg_isready`가 여기에 먼저 성공해서, 구축 중 적재가 `database does not exist`로 실패했다. 실제 쿼리 성공으로 판정한다.
{% endhint %}

### 복구 시나리오별 선택

| 상황 | 쓰는 사본 |
|---|---|
| DB 손상, 최근 7일 이내 | 평문 덤프 |
| 저장소·LFS 손상, 실수 삭제 | 암호화 스냅샷(14일 일 단위 시점) |
| 백업 디스크 장애 | 오프사이트 사본 |
| PC 전체 소실(화재, 도난, 랜섬웨어) | 오프사이트 사본 + 별도 보관한 restic 비밀번호 |

## 알려진 한계·주의

- 오프사이트 사본의 암호화는 restic에 의존한다. 평문 덤프도 같은 폴더에 있으므로 클라우드 계정이 곧 DB 내용 노출 범위가 된다. 이 위험의 수용 여부는 원본에 없음, 확인 필요.
- 백업 디스크와 서버 디스크가 같은 PC 안이다. 디스크 1대 고장과 실수 삭제는 막지만 PC 전체 사고는 오프사이트만 막는다.
- Plane 첨부파일(이름 있는 볼륨)이 스냅샷 경로에 포함되는지는 확인 필요([구성 지도](structure.md) 참조).
- 로그에서 구조만 확인했다. 최근 오프사이트는 상태 파일에 성공으로 기록돼 있으나 실행해 확인하지 않았다.
- 클라우드 API 사용은 표준 범위에서 무료이고, 저장 용량은 기존 계정 요금제에서 차감된다(구축 기록). 결제 계정을 연결하지 않으면 초과 시 요금 대신 오류가 난다.
