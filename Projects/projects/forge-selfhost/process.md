# 도입 과정

## 목표와 결정

| 항목 | 결정 |
|---|---|
| 서비스 | Gitea(코드) + Plane(이슈와 프로젝트) |
| 데이터 | 신규 구축(이관할 데이터 없음) |
| 외부 노출 | 포트포워딩 0건. VPN 오버레이 안에서만 접근 |
| 팀원 접근 | Tailscale **노드 공유**. 팀원을 내 네트워크에 넣지 않고 서버 한 대만 공유 |
| 런타임 | WSL2 Ubuntu + systemd + 네이티브 Docker(Docker Desktop은 쓰지 않음) |
| 재부팅 | 매일 새벽 무인 재부팅, 복구까지 자동 |

환경을 실측해서 정해진 제약도 있었다.

- 시스템 디스크의 여유가 적어서 WSL 가상 디스크와 컨테이너 데이터는 용량이 큰 다른 디스크에 두고, 백업은 물리적으로 또 다른 디스크에 두었다.
- 공유 노드는 짧은 이름이 아니라 전체 도메인 이름으로만 접근된다(Tailscale 사양). 그래서 모든 URL을 전체 도메인으로 통일했다.
- 태그가 붙은 노드는 공유할 수 없다. ACL은 태그 대신 호스트명으로 작성했다.
- 공유는 단방향이라 팀원 쪽에서 서버로만 접속되고 서버가 먼저 연결하지 못한다. 이 서버의 용도에는 문제없다.
- 새벽 재부팅은 그 시간대의 원격 세션도 같이 끊는다. 야간 장시간 작업과 충돌한다는 점을 미리 알렸다.

## 아키텍처

```
[팀원 기기] --(WireGuard, 공유 노드)--> [Windows 11 호스트, 24시간]
                                           - VPN 서비스(자동 복구)
                                           - 방화벽: VPN 대역에서만 서비스 포트 허용
                                           - 작업 스케줄러: 부팅 기동 / 백업 / 재부팅 / 헬스체크
                                                    |
                                          WSL2 Ubuntu (systemd + Docker)
                                           - Gitea + PostgreSQL
                                           - Plane 스택(공식 compose)
                                           - 백업 산출물 → 스냅샷 → 다른 디스크, 클라우드
```

DB, 캐시, 오브젝트 스토리지 같은 내부 서비스 포트는 컨테이너 네트워크 안에서만 쓰고 호스트에 열지 않았다.

## 단계별 진행

| 단계 | 한 일 |
|---|---|
| 0. 사전 정리 | Docker Desktop 제거, 기존 포트포워딩 점검과 제거, 노드 이름 정리 |
| 1. WSL2 | 큰 디스크에 배포판 구축, systemd 활성화, Docker 설치 |
| 2. 네트워크 | 방화벽을 VPN 대역에서만 열도록 구성, 공유 노드 설정 |
| 3. Gitea | 버전 고정(`:latest` 금지), 가입 비활성화와 로그인 강제, LFS 서버 켜기, push 크기 제한과 메모리 상한 |
| 4. Plane | 공식 compose로 구축, 기본 자격증명을 전부 무작위 값으로 교체 |
| 5. 접근 통제 | 노드 공유와 ACL로 필요한 서비스만 허용. Gitea 계정 하나로 Plane까지 로그인(OAuth) |
| 6. 무인 운영 | 백업, 새벽 재부팅, 자동 복구, 헬스체크 |
| 7. CI/CD | Gitea Actions 구축, 저장소 가드레일 검사, Unity 빌드 자동화 |

## 무인 운영 설계

핵심 원칙은 **백업을 재부팅 자동화보다 먼저 세운다**는 것이다.

- 새벽에 단일 작업이 순서대로 실행한다: 점검 공지 → 백업 → 컨테이너 정상 종료 → 재부팅. 백업과 재부팅을 별도 작업으로 나누면 저장소가 커질 때 겹칠 수 있어서 하나로 묶었다.
- 재부팅 후에는 부팅 작업이 WSL, Docker, 컨테이너를 순서대로 올리고, 일정 시간 뒤 복구 여부를 점검해 보고한다.
- 알림은 Discord 웹훅으로 보냈다. 점검 공지, 복구 보고, 장애 시 상태 변화를 알린다.
- 백업은 암호화 스냅샷(로컬 디스크), 최근 1주일치 평문 DB 덤프(즉시 복구용), 클라우드 드라이브 사본(오프사이트) 세 겹이다.
- 백업을 믿으려면 복원해 봐야 한다. 격리 환경에 백업만으로 서비스를 다시 올려 DB 테이블 수, 이슈 수, LFS 표본의 해시, 저장소 커밋과 브랜치 수를 확인하는 복원 리허설을 했다.

## CI/CD

1. **Gitea Actions + 러너**: 러너 컨테이너 1대, 동시 실행 2개(코어 수를 넘기면 서로 CPU를 뺏어 오히려 느려진다), 잡 타임아웃 1시간(새벽 재부팅에 물린 좀비 잡 방지).
2. **가드레일 검사 먼저**: Unity 빌드 CI는 라이선스, 수십 GB 이미지, 긴 빌드 시간이 필요하다. 반면 팀이 실제로 겪은 사고(LFS 대상 파일이 일반 바이너리로 커밋됨)를 막는 검사는 수초면 된다. 이쪽을 먼저 넣었다.
3. **Unity 빌드**: IL2CPP는 대상 플랫폼과 같은 OS의 에디터에서만 빌드되므로 Windows 러너를 썼다. 고정 경로에서 빌드해 Library 캐시를 재사용했고(13분이 1.4분으로), 첫 빌드 27분이 이후 8분이 되었다. 매 빌드마다 에셋이 수정되므로 강제 체크아웃으로 항상 커밋 상태를 복원한다. 설치 마법사는 관리자 권한이 필요 없게 만들어 팀원이 UAC 없이 설치한다.

## 팀 온보딩

팀원에게는 3단계(VPN 설치와 초대 수락, 서비스 로그인, Git 설정)를 15분 안에 끝내는 접속 안내 문서를 만들어 배포했다. 접속 주소는 반드시 전체 도메인으로 쓰도록 강조했다.
