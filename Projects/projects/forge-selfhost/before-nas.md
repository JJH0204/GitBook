| 확인 상태 | 미검증 (작성자의 기록을 정리한 것이며 이 환경에서 재현하지 않았다) |

## 1. 이전 구성

처음에는 팀의 Git 서버와 이슈 트래커를 NAS 한 대에 올려 운영했다. 이 NAS는 RAM이 4GB인 소형 장비였고, 그 위에서 코드 저장소와 이슈 관리 도구를 함께 돌렸다.

## 2. 증상

- 저장소 하나가 약 10GB였다.
- 서버 데이터가 통째로 사라졌다.
- 복구할 백업이 없어 이관할 데이터도 남지 않았고, 서버를 새로 구축해야 했다.

## 3. 가능 원인

| 번호 | 원인 | 근거 |
|---|---|---|
| 1 | 큰 바이너리가 Git LFS가 아니라 일반 Git 객체로 들어 있었다 | 게임 에셋 같은 큰 바이너리가 저장소에 일반 객체로 들어 있었다 |
| 2 | 저장소 점검(self-fsck)과 pack 작업이 메모리를 한꺼번에 많이 썼다 | 메모리 부족(OOM)이 났다 |
| 3 | 4GB 장비에 Git 서버와 이슈 도구를 함께 올렸다 | 위 두 원인이 같은 장비의 메모리를 나눠 썼다 |
| 4 | NAS 펌웨어 동작이 OOM 상태와 겹쳤다 | 그 상태에서 데이터가 사라졌다 |
| 5 | 백업이 없었다 | 소실 후 복구할 사본이 없었다 |

## 4. 격리 결론

처음에는 "NAS는 데이터를 잃은 전력이 있어 믿을 수 없다"고 정리했다. 나중에 이 문장이 원인과 결과를 잘못 이어 붙인 것임을 알았다.

- 데이터를 잃은 원인은 **4GB 장비에 풀스택(Git 서버 + 이슈 도구)을 올려 운영한 것**이지, 저장 장치로서 NAS가 실패한 것이 아니다.
- NAS를 파일 저장소로만 쓴다면 조건이 전혀 다르고 백업 대상으로 충분히 좋은 선택지다.
- 교훈: **이미 가진 자원을 먼저 검토한다.** 새 서버를 구축하기 전에 있는 것으로 풀 수 있는지부터 따져야 한다.

## 5. 시정 조치

새 서버에 구축 첫날부터 사고 원인별 방어책을 넣었다.

| 사고 원인 | 방어책 |
|---|---|
| 큰 바이너리 히스토리가 서버를 압박 | 서버가 일정 크기 이상의 push를 거부하도록 제한 |
| 대용량 파일이 일반 객체로 저장됨 | Git LFS를 서버에서 켜고 Unity용 `.gitattributes` 템플릿으로 LFS 대상 확장자를 강제 |
| 메모리 폭주가 장비 전체를 죽임 | 컨테이너에 메모리 상한을 걸어 폭주해도 그 컨테이너만 죽게 격리 |
| 주기적 self-fsck가 메모리 급증 유발 | 데일리 저장소 점검을 끔 |
| 백업이 없어 전량 소실 | **백업을 재부팅 자동화보다 먼저** 세움. 백업이 이 프로젝트의 가장 중요한 산출물이라고 정했다 |

NAS 시절의 포트포워딩 설정이 공유기에 남아 있을 수 있어, 구축 첫 단계에서 기존 포트포워딩을 전부 점검해 제거했다.

## 6. 환경이 바뀐 점

| 항목 | NAS 시절 | 새 서버 |
|---|---|---|
| 장비 | RAM 4GB 소형 NAS | 데스크톱(6코어, RAM 48GB) |
| 데이터 | 한 장비에 단일 사본 | 로컬 스냅샷 + 오프사이트 사본 |
| 노출 | 포트포워딩 사용 | 포트포워딩 0건, VPN 안에서만 |
| 대용량 대응 | 없음 | push 크기 제한, LFS 강제, 메모리 상한 |

## 약어·용어

| 용어 | 뜻 |
|---|---|
| OOM | 메모리 부족(Out Of Memory)으로 프로세스가 강제 종료되는 현상 |
| LFS | 큰 파일을 별도 저장소로 관리하는 Git 확장(Large File Storage) |
| self-fsck | Git 서버가 저장소 무결성을 주기적으로 검사하는 기능 |
