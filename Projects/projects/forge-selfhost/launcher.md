## 이 영역이 하는 일

팀원이 서버 웹 화면이나 설치 파일을 직접 찾지 않아도, 런처에서 버전을 고르면 설치 파일을 받아 조용히 설치하고, 파일이 변조되거나 빠지지 않았는지 검증한 뒤 실행한다. 한 창에서 여러 버전을 폴더별로 나란히 설치할 수 있다.

## 구성 요소

| 요소 | 역할 |
|---|---|
| 소스 | 단일 파일 `<런처 이름>.pyw`(Python 3.13, 표준 라이브러리 + 이미지 처리용 Pillow만) |
| `assets/` | 배경, 로고, 아이콘 이미지. 각각 선택 사항이며 없으면 기본 모양으로 대체 |
| 설정 | 사용자 설정 폴더의 `config.json`(설치 루트, 마지막 확인 목록 `seen`, 설치 비율 `install_ratio`) |
| 데이터 원본 | 서버 릴리스 API(인증 없는 공개 저장소). 한 릴리스에서 태그, 게시일, 사전 릴리스 여부, 본문(버전 메모), 첨부 목록(이름, 크기, 내려받을 주소) |
| 설치 파일 | Inno Setup 6으로 만든 설치 프로그램([CI 해체 분석](ci.md)) |
| 배포 | `build.ps1`이 PyInstaller 단일 실행 파일로 묶는다(에셋 포함, Python 불필요) |

## 데이터 흐름

```
 [릴리스 API <서버>/api/v1/repos/<조직>/<저장소>/releases?limit=50&page=N]
        | 빈 목록이 나올 때까지 페이지 순회
        v
 버전 목록(최신순) + 안내 영역(태그, 날짜, 크기, 본문)
        |
   [설치]  다운로드(1 MiB 조각, .part) -> 크기 대조 -> 설치 프로그램 실행 -> 실행 파일 존재 확인
           -> 매니페스트 기록(파일별 크기, sha256) -> 설치 파일 삭제
   [검증]  매니페스트의 모든 항목을 다시 계산해 대조
   [실행]  검증 통과 시에만 게임 실행(기다리지 않음)
   [삭제]  폴더 이름 변경(실패하면 게임이 파일을 잡고 있다는 뜻) -> 파일별 삭제 -> 제거 등록 항목 정리
```

작업은 모두 작업 스레드에서 돌고, 위젯은 메인 스레드만 만진다. 스레드는 `(종류, 내용)`을 큐에 넣고 메인 스레드가 100ms마다 비운다.

## 핵심 설계 해설

### 1. 설치 단계 (명세 Install)

1. 버전 폴더는 `<설치 루트>\<태그>`이고, 설치 파일은 `<설치 루트>\_downloads\<이름>.part`로 내려받아 완료 후 이름을 바꾼다.
2. 내려받은 크기가 릴리스가 알려준 크기와 같은지 확인한다. 다르면 지우고 오류를 낸다.
3. 설치 파일을 조용히 실행한다. 명세가 적은 인자는 다음과 같다(경로는 일반화).

```text
<설치 파일> /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /NOICONS /DIR="<버전 폴더>" /LOG="<로그 경로>"
```

   인자는 셸을 거치지 않고 리스트로 넘긴다. 종료 코드가 0이 아니면 로그 경로를 넣은 오류를 낸다. Inno Setup이 자체 CRC를 검사하므로 손상된 다운로드는 여기서 실패한다.
4. 버전 폴더에 게임 실행 파일이 있는지 확인한다. 이후 버전에서는 폴더의 `*.exe`를 글로브로 찾으며(`unins*`, 크래시 핸들러 제외) 제품 이름이 바뀌어도 런처를 고칠 필요가 없다.
5. 버전 폴더의 매니페스트에 모든 파일의 상대 경로와 `[크기, sha256]`을 기록한다(매니페스트 자신과 `unins*` 제외). 매니페스트가 있으면 "설치됨"이다.

### 2. 검증과 실행

검증은 매니페스트의 모든 항목을 다시 계산한다. 목록에 없는 파일(게임이 실행 중 만드는 로그와 캐시)은 무시한다. 변경·누락이 있으면 최대 20개까지 보여 주고 재설치 여부를 묻는다. 실행은 검증을 먼저 하고 통과할 때만 프로세스를 띄운다.

### 3. 진행 표시

- 막대는 캔버스에 직접 그린다(기본 진행 막대가 6px에서 보이지 않았다고 명세에 적혀 있다).
- 단계 표시는 설치 `[1/3] 다운로드`, `[2/3] 설치`(설치 로그에서 현재 파일 이름을 읽음), `[3/3] 무결성 기록`이다.
- 설치 단계 진행률은 추정이다. 설치된 바이트를 `(첨부 크기 × 비율)`로 나눈다. 비율은 설치마다 학습해 설정에 저장하며 기본 6.0이다(측정값 8.3, 4.6).

### 4. 새 빌드 알림과 삭제

- "새 빌드 확인" 버튼은 목록을 다시 받아, 설정의 `seen`에 없는 태그에 NEW 표시를 하고 가장 새 것을 선택한다. 트리 항목 식별자를 태그로 써서 항목이 끼어들어도 선택이 유지된다.
- 삭제는 폴더 이름부터 바꾼다(게임이 파일을 잡고 있으면 깨끗이 실패한다). 이후 파일별 진행률로 지우고, 사용자 영역의 제거 등록 항목은 설치 위치가 그 폴더일 때만 지운다. 재설치는 폴더를 먼저 비운다.

### 5. 자체 시험

처음 명세는 GUI 없이 도는 `--selftest`를 요구했다. 임시 폴더로 매니페스트를 만들어 검증 통과를 확인하고, 한 파일을 바꾸고 하나를 지워 각각 보고되는지 단언하고 `selftest ok`를 출력한다. 현재 소스에 이 옵션이 남아 있는지는 소스를 읽지 않아 모른다(확인 필요).

## 따라 만들기

확인 상태: 미검증. 기대 결과는 명세에 근거한 설명이다.

1. 릴리스 목록 모듈을 만든다. 서버 릴리스 API를 페이지 순회해 태그, 게시일, 본문, `.exe`로 끝나는 첫 첨부를 모은다. 기대 결과: 사전 릴리스 여부와 함께 최신순 목록이 나온다.
2. 설정 읽기·쓰기를 만든다. 예외를 잡고, 파일이 없거나 깨졌으면 기본값을 쓴다. 기대 결과: 설정 파일을 지워도 실행된다.
3. 작업 스레드와 큐 구조를 만든다. 작업 스레드는 위젯을 만지지 않고 큐에 넣고, 메인이 폴링한다. 기대 결과: 다운로드 중에도 창이 멈추지 않는다.
4. 설치를 구현한다. 다운로드, 크기 대조, 조용한 설치 실행, 실행 파일 존재 확인, 매니페스트 기록 순서다. 기대 결과: 설치 후 버전 폴더에 매니페스트가 생긴다.
5. 검증을 구현한다. 매니페스트 재계산, 변경·누락 목록, 재설치 제안이다. 기대 결과: 파일 하나를 바꾸면 그 파일이 목록에 나온다.
6. 실행과 삭제를 구현한다. 실행은 검증 선행, 삭제는 이름 변경 선행이다. 기대 결과: 게임이 켜져 있을 때 삭제하면 깨끗이 실패한다.
7. 진행 표시와 새 빌드 표시를 붙인다. 기대 결과: 단계 표시와 NEW 표시가 보이고 재시작 후에도 NEW가 유지되지 않는다(`seen` 저장).
8. 단일 실행 파일로 묶는다. 에셋을 포함하는 방식으로 `build.ps1`이 하는 일을 따라 한다. 기대 결과: Python이 없는 PC에서 실행된다.

## 알려진 한계·주의

- 명세의 처음 부분(Data source, Config, Layout)에는 옛 이름(설정 폴더, 실행 파일, 기본 설치 루트)이 남아 있다. 맨 위의 갱신된 서술이 우선한다.
- 데이터 원본이 인증 없는 공개 API라는 전제다. 서버가 VPN 안에서만 열리므로 팀원 PC가 그 네트워크에 속해 있어야 한다.
- 설치 단계 진행률은 학습한 비율에 의존하는 추정이다. 설치 프로그램에 디버그용 폴더가 포함되면 비율이 달라진다(측정값 차이의 원인으로 명세가 지적).
- 매니페스트는 설치 직후의 파일 상태를 기준으로 하므로, 게임이 실행 중에 만드는 파일은 검증 대상이 아니다.
- 이 문서는 명세만 읽고 썼다. 구현이 명세와 어긋난 곳은 알 수 없다.
