## 🎯 학습 목표

- 네트워크를 왜 나누는지(서브넷팅의 이유)를 이해한다
- 호스트 비트를 빌려 서브넷을 만드는 원리를 안다
- **블록 크기**로 네트워크 주소·브로드캐스트를 손으로 계산할 수 있다
- 서브넷의 개수·호스트 수를 계산할 수 있다
- 두 IP가 **같은 네트워크인지 판별**해서 통신 가능 여부를 말할 수 있다
- 필요한 호스트 수에 맞춰 크기가 다른 서브넷을 배정한다(**VLSM**)

## 🌉 다리 놓기: "한 동네가 너무 크면 생기는 문제"

클래스 C 하나(`/24`)면 호스트가 254개. 그런데 부서가 4개인 회사가 **전부 한 네트워크**에 있으면?

- 브로드캐스트가 254대 전체로 퍼짐 → 성능 저하 ([7_캐스트_유니_브로드_멀티](../day-01/lesson-7.md)의 **브로드캐스트 도메인**!)
- 부서 간 분리·보안도 어려움

그래서 큰 네트워크를 **작게 쪼갠다 = 서브넷팅**.

## 📖 왜 나누나 (서브넷팅의 이점)

- **브로드캐스트 도메인 축소** → 트래픽·혼잡 감소
- **보안·관리** 분리 (부서·용도별)
- **주소 낭비 감소** (필요한 만큼만 배분)

## 📖 어떻게 나누나 — 호스트 비트를 "빌린다"

- 서브넷 마스크를 **오른쪽으로 늘려**(호스트 비트 → 네트워크 비트) 네트워크를 쪼갬
- `/24` 에서 2비트를 빌리면 → `/26`, 서브넷 **2² = 4개**

## 📖 손계산 4단계 — 블록 크기(매직 넘버)

표를 **외우지 말고 만들어 내자.** 순서는 어떤 문제든 항상 똑같다.

```
① 마스크를 10진수로       /26  →  255.255.255.192
                          (자릿값 표: 11000000 = 128+64 = 192)

② 블록 크기 = 256 - 192 = 64      ← 이게 매직 넘버

③ 0부터 블록 크기씩 뛴다          0, 64, 128, 192
                                  = 각 서브넷의 네트워크 주소

④ 다음 네트워크 바로 앞 번호      63, 127, 191, 255
                                  = 각 서브넷의 브로드캐스트
```

> 💡 **"256 빼기 마스크"** 한 줄만 기억하면 된다.
> `/28` → 256 − 240 = **16** → 0, 16, 32, 48, 64 … / `/27` → 256 − 224 = **32** → 0, 32, 64, 96 …

- 네트워크 주소와 브로드캐스트 **사이에 낀 번호들**이 실제로 장비에 줄 수 있는 주소다
- 마스크 값 → 자릿값 표는 [2_IP클래스와_서브넷마스크](lesson-2.md) 참고

### 예제: `192.168.1.0/24` 를 `/26` 으로

위 4단계를 그대로 적용한 결과 (블록 크기 = 64):

| 서브넷 | 네트워크 주소 | 사용 가능 호스트 | 브로드캐스트 |
|--------|---------------|------------------|--------------|
| 1 | 192.168.1.0/26 | .1 ~ .62 | .63 |
| 2 | 192.168.1.64/26 | .65 ~ .126 | .127 |
| 3 | 192.168.1.128/26 | .129 ~ .190 | .191 |
| 4 | 192.168.1.192/26 | .193 ~ .254 | .255 |

## 📖 계산 공식

- **서브넷 개수** = 2^(빌린 비트 수)
- **서브넷당 전체 주소** = 2^(남은 호스트 비트 수)
- **사용 가능 호스트** = 전체 − 2  ← 네트워크 주소 + 브로드캐스트 주소 예약

> 💡 `/26` → 호스트 비트 6개 → 2⁶ = 64개, 사용 가능 = **62개**

## 📖 그래서 뭐가 달라지나 — "둘이 서로 통신될까?"

서브넷팅이 숫자 놀이가 아닌 진짜 이유. 나누는 순간 **통신 가능 여부가 바뀐다.**

> ❓ `192.168.1.10/26` 과 `192.168.1.100/26` 은 서로 ping이 될까?

**판별법: 각자의 네트워크 주소를 구해서 비교한다.** (블록 크기 64 → 경계는 0, 64, 128, 192)

| 호스트 | 속한 블록 | 네트워크 주소 |
|--------|-----------|---------------|
| 192.168.1.**10** | 0 ~ 63 | `192.168.1.0` |
| 192.168.1.**100** | 64 ~ 127 | `192.168.1.64` |

→ 네트워크 주소가 **다르다** = 서로 **다른 동네** = 직접은 통신 **불가**
→ 동네와 동네를 이어줄 장치가 필요하다 = **라우터**(각 PC 입장에서는 **기본 게이트웨이**)

반대로 둘 다 `/24`였다면? 네트워크 주소가 둘 다 `192.168.1.0` → **같은 동네** → 스위치만으로 바로 통신된다.

> 💡 **똑같은 IP 두 개인데 답이 달라진다.** `/24`면 통하고 `/26`이면 안 통한다.
> "IP만 맞으면 되는 거 아닌가요?" → 아니다. **IP + 서브넷 마스크가 한 세트**여야 의미가 생긴다.

- 현장에서 "핑이 안 나가요"의 상당수가 **마스크를 잘못 준 것** → 나 혼자 다른 동네에 서 있는 셈
- 이 판별이 3일차 ping 실습에서 눈으로 확인된다 → [3_ICMP와_ping](../day-03/lesson-3.md)

## 📖 크기가 다르면? — VLSM 맛보기

앞의 `/26` 4개는 **똑같이 62개씩** 자른 것이다. 그런데 현실은 부서마다 크기가 다르다.

> ❓ 영업 50대 · 개발 20대 · 총무 10대 · 회의실 5대 — `192.168.1.0/24` 하나로 어떻게 나눌까?

균등하게 `/26` 4개로 자르면 영업(50대)은 딱 맞지만, **회의실도 62개를 받아 57개가 낭비**된다.
→ 필요한 만큼만 **서로 다른 크기**로 자르는 것 = **VLSM**(가변 길이 서브넷 마스크)

**규칙: 큰 것부터 순서대로 배정한다.**

| 부서 | 필요 | **+2** | 넉넉한 2의 거듭제곱 | 마스크 | 배정 대역 |
|------|-----|-------|------------------|--------|-----------|
| 영업 | 50대 | 52 | 64 | **/26** | `192.168.1.0` ~ `.63` |
| 개발 | 20대 | 22 | 32 | **/27** | `192.168.1.64` ~ `.95` |
| 총무 | 10대 | 12 | 16 | **/28** | `192.168.1.96` ~ `.111` |
| 회의실 | 5대 | 7 | 8 | **/29** | `192.168.1.112` ~ `.119` |

- **`+2`를 잊지 말 것** — 네트워크 주소와 브로드캐스트는 못 쓴다. 50대면 50짜리가 아니라 **52 이상**이 필요해서 64(/26)로 올라간다
- 각 대역은 앞 대역이 끝난 **바로 다음 번호**에서 시작한다 (0 → 64 → 96 → 112)
- 남은 `.120 ~ .255`는 **여유분** → 나중에 부서가 늘어도 대응 가능

> 💡 **왜 큰 것부터?** 블록은 자기 크기의 배수 자리에서만 시작할 수 있다.
> 작은 것부터 넣으면 중간에 어중간한 틈이 생겨 큰 블록이 들어갈 자리를 잃는다. (짐 쌀 때 큰 짐부터 넣는 것과 같다)

- 실무 설계는 사실상 전부 VLSM이다. 자세한 설계는 라우팅과 함께 → [5일차 · 라우팅 프로토콜](../day-05/README.md)

## 🧪 실습: 손계산 + 코드로 검증

먼저 손으로 계산한 뒤, **subnet_calc.py** 로 답을 맞춰본다.

```bash
python subnet_calc.py
```

**[1] 한 개만 확인** — 입력 `192.168.1.10/26`

```
네트워크 주소    : 192.168.1.0
브로드캐스트     : 192.168.1.63
서브넷 마스크    : 255.255.255.192  (/26)
전체 주소 수     : 64
사용 가능 호스트 : 62개  (192.168.1.1 ~ 192.168.1.62)
└ 손계산 확인    : 블록 크기 = 256 - 192 = 64
```

**[2] 나눈 결과를 통째로 확인** — 입력 `192.168.1.0/24 > /26`

```
빌린 비트   : 2개   →  서브넷 2^2 = 4개
서브넷당    : 전체 64개 / 사용 가능 62개  (전체 - 2)

  #  네트워크 주소        사용 가능 호스트                    브로드캐스트
------------------------------------------------------------------------
  1  192.168.1.0/26       192.168.1.1 ~ 192.168.1.62         192.168.1.63
  2  192.168.1.64/26      192.168.1.65 ~ 192.168.1.126       192.168.1.127
  3  192.168.1.128/26     192.168.1.129 ~ 192.168.1.190      192.168.1.191
  4  192.168.1.192/26     192.168.1.193 ~ 192.168.1.254      192.168.1.255
```

> 💡 위 **손계산 표와 한 줄씩 대조**해 보자. 4단계로 만든 표와 완전히 같아야 한다.

**연습 문제 ① — 개수 세기**
- `192.168.10.0/24`를 `/28`로 나누면 서브넷 몇 개, 서브넷당 호스트 몇 개? (답: 16개 / 14개)
- `10.0.0.5/16`의 네트워크 주소와 브로드캐스트는? (답: 10.0.0.0 / 10.0.255.255)

**연습 문제 ② — 블록 크기로 손계산**
- `192.168.1.0/27`의 블록 크기와 네트워크 주소들을 모두 적어보자
  - (답: 256−224 = **32** → 0, 32, 64, 96, 128, 160, 192, 224 → 8개 서브넷, 각 30호스트)
- `172.16.5.4/20`의 네트워크 주소와 브로드캐스트는?
  - (답: 마스크 255.255.**240**.0 → 블록 16 → 5는 0~15 블록 → **172.16.0.0** / **172.16.15.255**)

**연습 문제 ③ — 통신될까?**
- `192.168.1.200/26` 과 `192.168.1.130/26` 은 서로 통신될까?
  - (답: 200은 192~255 블록, 130은 128~191 블록 → 네트워크가 다름 → **직접 통신 불가**)
- 위 두 IP를 그대로 두고 마스크만 `/24`로 바꾸면? (답: 둘 다 192.168.1.0 → **통신 가능**)

**연습 문제 ④ — VLSM 설계**
- `192.168.5.0/24` 를 A 100대 · B 50대 · C 25대 · D 10대에 나눠 배정해보자
  - (답: A `/25` = .0~.127 / B `/26` = .128~.191 / C `/27` = .192~.223 / D `/28` = .224~.239, 여유 .240~.255)

## 📝 강의 메모

- "호스트 비트를 빌려 네트워크를 늘린다"를 그림으로 반복
- **블록 크기 = 256 − 마스크**를 주문처럼 반복시키고, 예제마다 ①~④ 4단계를 소리 내어 밟게 하기
- 표를 먼저 보여주지 말 것 → 4단계로 **학생이 표를 만들게** 한 뒤 답을 공개
- "통신될까?" 문제는 매번 **네트워크 주소부터 구하기** 습관으로 유도 (감으로 찍지 않게)
- VLSM은 **개념과 순서(큰 것부터, +2)** 까지만. 학생이 지치면 연습문제 ④는 과제로 돌려도 됨
- 손계산 → `subnet_calc.py`로 즉시 채점하는 흐름이 이해에 효과적
