## 🎯 학습 목표

- 스위치가 MAC 주소 테이블을 학습하는 과정을 이해한다

## 🌉 다리 놓기: "스위치는 그 MAC을 어떻게 알까?"

3일차에 "스위치는 **MAC을 보고 해당 포트로만** 전달한다"고 했다. → [1_네트워크장비](../day-03/lesson-1.md)
그런데 처음엔 어느 MAC이 어느 포트에 있는지 모른다. 스위치는 이걸 **스스로 배운다(learning)**.

## 📖 MAC 주소 테이블 학습 (Learning)

- 프레임이 들어오면 **출발지(source) MAC**을 보고 "이 MAC = 이 포트" 라고 표에 기록
- 이 표가 **MAC 주소 테이블**(CAM 테이블)

```
PC0(MAC AAAA) → 포트1로 들어옴  ⇒  테이블: AAAA = 포트1
PC1(MAC BBBB) → 포트2로 들어옴  ⇒  테이블: BBBB = 포트2
```

> ⚠️ **배우는 건 "출발지", 보내는 건 "목적지".** 방향이 반대다.
> 프레임이 들어오면 **출발지 MAC으로 표를 채우고**, **목적지 MAC으로 내보낼 포트를 고른다.**

### 실제 출력은 이렇게 생겼다

```
Switch# show mac address-table

          Mac Address Table
-------------------------------------------
Vlan    Mac Address       Type        Ports
----    -----------       --------    -----
   1    0001.4295.1a01    DYNAMIC     Fa0/1
   1    000c.85b2.3c02    DYNAMIC     Fa0/2
```

| 칸 | 뜻 |
|----|-----|
| **Vlan** | 어느 VLAN 소속인지 (기본은 전부 `1`) |
| **Mac Address** | 학습한 MAC — 시스코는 `.` 로 4자리씩 끊어 쓴다 (`0001.4295.1a01`) |
| **Type** | `DYNAMIC` = 스스로 배운 것 / `STATIC` = 관리자가 고정한 것 |
| **Ports** | 그 MAC이 붙어 있는 포트 |

- **한 포트에 MAC이 여러 개** 찍힐 수도 있다 → 그 포트에 스위치가 하나 더 물려 있다는 뜻

## 📖 에이징(Aging) — 배운 것을 잊는다

표에 한 번 올라간 항목은 **영원히 남지 않는다.**

- 그 MAC에서 프레임이 안 오면 **기본 300초(5분)** 뒤 자동 삭제
- 왜 지우나? **장비가 다른 포트로 옮겨갈 수 있으니까** — 옛 정보를 붙들고 있으면 엉뚱한 포트로 보낸다
- 그래서 **한참 쉬었다가 다시 통신하면 또 플러딩**부터 시작한다

```bash
clear mac address-table dynamic     # 배운 것 전부 지우기 (실습용)
```

> 💡 **스위치의 3대 임무**로 정리하면
> ① **학습**(Learning) ② **전달·차단**(Forwarding / Filtering) ③ **루프 방지**(Loop Avoidance = STP, 아래)

## 📖 프레임 전달 3가지

| 동작 | 언제 | 결과 |
|------|------|------|
| **플러딩(Flooding)** | 목적지 MAC을 **아직 모를 때** | 들어온 포트만 빼고 **전체 포트로** 내보냄 |
| **포워딩(Forwarding)** | 목적지 MAC을 **테이블에서 알 때** | **해당 포트로만** 전달 |
| **필터링(Filtering)** | 출발지·목적지가 **같은 포트**일 때 | 내보내지 않고 **차단** |

> 💡 그래서 3일차 실습의 "첫 ping이 살짝 느린" 이유가 둘: ARP 해석([2_MAC주소와_ARP](../day-03/lesson-2.md)) + 스위치가 아직 MAC을 몰라 **플러딩**하기 때문.

## 📖 허브와 결정적 차이: 콜리전 도메인 분리

- **허브**: 모든 포트가 하나의 콜리전 도메인 → 충돌 잦음
- **스위치**: **포트마다 콜리전 도메인 분리** + 양방향 동시 통신(full-duplex) → 충돌 거의 없음
- 단, 브로드캐스트는 여전히 통과 → 스위치 전체가 **하나의 브로드캐스트 도메인** ([7_캐스트_유니_브로드_멀티](../day-01/lesson-7.md))

### 반이중 vs 전이중

| | **반이중**(Half-duplex) | **전이중**(Full-duplex) |
|---|---|---|
| 동작 | 한 번에 **한 방향**만 | 보내기·받기 **동시에** |
| 비유 | 무전기 ("오버!") | 전화 |
| 쓰는 곳 | 허브 연결 | **스위치 연결(요즘 기본)** |
| 충돌 | 발생 | **없음** |

- 요즘 장비는 속도·듀플렉스를 **자동 협상(auto-negotiation)** 한다
- 한쪽만 수동 고정하면 **듀플렉스 불일치**가 생겨 "되긴 되는데 엄청 느린" 증상이 나온다 → 실무 단골 장애

## 📖 루프는 왜 위험한가 — STP

스위치를 **두 대 이상 연결할 때** 안정성을 위해 선을 두 줄 잇는 경우가 있다. 그런데 그냥 두면 **재앙**이 된다.

```
   ┌── 링크 A ──┐
[SW1]           [SW2]
   └── 링크 B ──┘      ← 고리(루프)가 생겼다
```

**브로드캐스트 하나가 들어오면**

1. SW1이 플러딩 → 링크 A·B 양쪽으로
2. SW2가 받아서 또 플러딩 → 되돌아옴
3. **끝나지 않는다.** IP 패킷과 달리 2계층 프레임에는 **TTL이 없다** → 영원히 돈다

| 증상 | 이름 |
|------|------|
| 브로드캐스트가 무한 증식해 회선이 마비 | **브로드캐스트 스톰** |
| 같은 MAC이 이 포트 저 포트에서 보여 표가 요동 | **MAC 테이블 불안정** |
| 같은 프레임을 여러 번 받음 | **프레임 중복** |

### 그래서 STP (Spanning Tree Protocol)

- 스위치들이 서로 정보를 주고받아 **한쪽 링크를 논리적으로 막는다(Blocking)** → 고리를 끊어 **나무(tree) 모양**으로 만든다
- 쓰던 길이 끊기면 막아뒀던 링크를 **다시 열어** 통신을 살린다 → 이중화의 목적 달성
- 표준: **802.1D**, 요즘은 더 빠른 **RSTP(802.1w)**

> 💡 **3일차 실습의 "주황 점 30초"가 바로 이것이다.**
> 포트가 켜지면 STP가 "여기 연결해도 루프가 안 생기나?"를 확인하느라
> `Blocking → Listening → Learning → Forwarding` 단계를 거친다. 그동안은 통신이 안 된다.
> (PC만 꽂는 포트는 루프 걱정이 없어 **PortFast** 로 즉시 통과시키기도 한다)

- 상세 설정은 이 과정 범위를 넘는다 → 오늘은 **"왜 기다리나 / 루프가 왜 위험한가"** 까지

## 📖 (예고) VLAN

- 스위치 하나를 **논리적으로 여러 브로드캐스트 도메인**으로 나누는 기술 = VLAN
- 2일차 서브넷팅이 IP를 나눴다면, VLAN은 스위치를 나눔 → 심화에서 다룸

## 📝 강의 메모

- Learning(출발지로 배움) + Forwarding(목적지로 보냄)의 **방향 차이**를 강조
- 콜리전 도메인(포트별 분리) vs 브로드캐스트 도메인(전체 하나)을 구분
- **에이징은 "잊어야 하는 이유"와 함께** 설명 → 그냥 5분이라고 외우면 남지 않는다
- STP는 **3일차의 주황 점**을 회수하는 자리다 → "그때 기다렸던 거, 이것 때문이었어요"로 시작
- 2계층 프레임에 **TTL이 없다**는 점을 짚어야 "왜 영원히 도나"가 납득된다
