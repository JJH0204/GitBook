# 8. 오늘 정리 · 안 될 때 점검 — 어디서 막혔나

> 상위: [11일차 · 서버 보안](README.md)

## 🎯 학습 목표

- **ACL 과 ufw** 를 한 표로 비교해 설명한다
- 통신이 안 될 때 **네 단계로 범위를 좁혀** 원인 자리를 찾는다
- **타임아웃 / Connection refused / 로컬은 되는데 원격만 안 됨** 이 각각 무엇을 가리키는지 안다
- 오늘 만든 규칙을 **12일차로 넘길 상태**로 정리한다

## 🌉 다리 놓기: "막는 법을 배웠으니, 막힌 걸 푸는 법도"

오늘 우리는 하루 종일 **막는 연습**을 했다. 그런데 현장에서 더 자주 겪는 일은 그 반대다.

> 🗣 **"분명히 서버를 세웠는데, 안 됩니다."**

그리고 그 원인의 상당수가 **오늘 우리가 켠 그것** 이다. 그래서 **막는 법과 푸는 법은 한 세트**다.

---

## 📖 ① 오늘 배운 두 도구 — 한 표로

| | 시스코 **ACL** | 리눅스 **ufw** |
|---|---|---|
| 어디서 막나 | **라우터**(지나가는 길) | **서버 자신**(도착지) |
| 누가 관리 | 망 관리자 | 서버 관리자 |
| 기본 정책 | **암묵적 deny any** | **`default deny incoming`** |
| 규칙 순서 | 위에서부터, 처음 맞는 줄 | 위에서부터, 처음 맞는 줄 |
| 출발지만 보기 | **표준** (1~99) | `ufw deny from <IP>` |
| 포트까지 보기 | **확장** (100~199) | `ufw allow from <IP> to any port <N>` |
| 적용 | `ip access-group <N> in\|out` | `ufw enable` |
| 확인 | `show access-lists` | `ufw status numbered` |
| 대표 함정 | `permit any` 를 빠뜨려 **전부 차단** | `allow 22` 전에 `enable` → **내가 쫓겨남** |

> 🗣 **오늘 가져갈 한 문장 — "필요한 것만 열고, 나머지는 막는다. 도구가 달라도 생각은 하나다."**

### 3층 방어 다시 보기

```
 [ 바깥 ] ──▶ ① 네트워크 장비 ──▶ ② 서버 자신 ──▶ ③ 서비스
                 ACL              ufw            설정 파일
                 (오늘 4·5번)      (오늘 6·7번)    (12일차)
```

- 우리 교실은 **브릿지** 라 ① 이 없다 → **② 가 유일한 방어선** → 그래서 ufw 가 오늘의 주인공이었다

## 📖 ② 안 될 때 — 네 단계로 좁힌다 ⭐⭐

> 🗣 **"어디가 고장인지 모를 때는, 고장이 아닌 곳을 하나씩 지워 나갑니다."**

```
① 서비스가 떠 있나?      ss -tuln | grep <포트>          → LISTEN 이 없으면 ①
② 서버 자신에서 되나?    curl localhost:<포트>            → 여기서 실패면 ②(서비스 설정)
③ 방화벽이 막나?         sudo ufw status numbered         → 규칙이 없으면 ③
④ 그래도 안 되나?        ip a · ping · 상대방 쪽 문제      → 주소·경로·클라이언트
```

| 단계 | 확인 명령 | 통과 못 하면 원인 |
|------|-----------|------------------|
| ① **듣고 있나** | `ss -tuln` 에 `LISTEN` | 서비스가 안 떴다 → `systemctl status` |
| ② **안에서 되나** | `curl localhost:8000` · `ftp localhost` | 서비스 설정 문제 (방화벽 아님!) |
| ③ **문이 열렸나** | `sudo ufw status numbered` | **방화벽** → `ufw allow` |
| ④ **길이 맞나** | `ip a` · `ping <상대>` | 주소를 잘못 알았거나 망이 다르다 |

> ⭐ **①②가 되는데 밖에서만 안 된다 = 거의 확실히 방화벽이다.**
> 이 한 줄이 오늘 가져갈 가장 실용적인 지식이다. 12일차 내내 쓰게 된다.

## 📖 ③ 증상으로 원인 읽기

| 증상 | 가장 흔한 원인 | 먼저 볼 것 |
|------|---------------|-----------|
| 한참 기다리다 **타임아웃** | **방화벽이 조용히 버림**(`deny`) · 주소가 틀림 | `ufw status` → `ping` |
| 즉시 **`Connection refused`** | **서비스가 안 떠 있다** (문은 닿았는데 아무도 없음) | `ss -tuln` · `systemctl status` |
| **로컬은 되는데 원격만** 안 됨 | **방화벽** 또는 서비스가 `127.0.0.1` 만 듣는 중 | `ufw status` → `ss -tuln` 의 주소 칸 |
| **Host unreachable** | 주소·게이트웨이 문제 | `ip a` · `ip route` |
| **어제는 됐는데 오늘 안 됨** | DHCP 로 **서버 IP 가 바뀜** ⭐ | `ip a` 로 주소 다시 확인 |

> 💡 **`Connection refused` 는 사실 좋은 소식**이다. **패킷이 서버까지 갔다는 뜻**이니까. 망은 멀쩡하고 서비스만 없는 것이다.
> 반대로 **타임아웃은 나쁜 소식** — 어디서 사라졌는지 알 수 없다.

### 방화벽 로그 보기

```bash
sudo ufw status verbose          # 로깅이 켜져 있나
sudo ufw logging on              # 켜기
sudo tail -f /var/log/ufw.log    # 막힌 패킷이 찍힌다 ⭐
```

- `[UFW BLOCK]` 줄에 **출발지 IP 와 목적지 포트**가 그대로 찍힌다 → "정말 방화벽이 막았나"를 **증거로** 확인

## 📖 ④ 브릿지라서 생기는 것 — IP 가 바뀐다 ⚠️

우리 VM 은 **브릿지**라서 교실 공유기의 **DHCP 로 주소를 받는다.** 그래서 —

> ⚠️ **다음 주에 오면 서버 IP 가 바뀌어 있을 수 있다.**

| 매 수업 시작할 때 | 명령 |
|-------------------|------|
| 1. 내 서버 주소 확인 | `ip a` |
| 2. 방화벽 상태 확인 | `sudo ufw status numbered` |
| 3. 특정 IP 허용 규칙이 있으면 | **그 IP 도 바뀌었는지** 확인 후 수정 |

- [7_최소개방_설계](lesson-7.md) 에서 `allow from <내 Windows IP>` 를 넣었다면, **Windows 쪽 IP 도 바뀐다**
- 그래서 실무에서는 서버에 **고정 IP** 를 준다 (13일차 이후)

## 🧪 오늘 마무리 — 12일차로 넘길 상태 만들기

> 🖐 [대본 마무리](commands.md)

```bash
sudo ufw status numbered         # 1. 지금 규칙을 눈으로 확인
sudo ufw allow 22/tcp            # 2. SSH 는 반드시 열려 있어야 한다 ⭐
sudo ufw status verbose          # 3. Status: active 인지 확인
ip a                             # 4. 내 서버 IP 를 적어 둔다
sudo poweroff                    # 5. 얌전히 종료
```

> 📌 **방화벽을 켜 둔 채로 간다.** 12일차에 서버를 여섯 개 세우는데, 그 **6단계 중 ⑤ 개방(`ufw allow`)** 이
> 오늘 켜 둔 이 방화벽 때문에 **진짜로 필요해진다.** 꺼 두고 가면 ⑤ 단계가 공회전한다 → [12일차 공통 문법](../day-12/lesson-1.md)
