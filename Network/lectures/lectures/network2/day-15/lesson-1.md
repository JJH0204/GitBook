# 1. 왜 쿠버네티스인가 — Compose 가 못 하는 세 가지 ⭐

> 상위: [15일차 · 쿠버네티스 입문](README.md) · 대본 [STEP 1](commands.md)

## 🎯 학습 목표

- 14일차 Compose 로 **안 되는 일 세 가지**를 든다 ⭐
- **명령형과 선언형**의 차이를 한 문장으로 설명한다 ⭐⭐
- 쿠버네티스가 하는 일을 **"원하는 상태를 지킨다"** 로 요약한다
- 쿠버네티스를 **안 써도 되는 경우**를 안다

## 🌉 다리 놓기: 14일차의 그 한 줄

지난 시간 마지막 장면을 떠올려 보자.

```bash
git clone https://github.com/<아이디>/myweb.git demo && cd demo
cp .env.example .env
docker compose up -d        # 웹 + DB + 볼륨 + 네트워크가 선다
```

세 줄로 환경이 섰다. 훌륭하다. 그런데 **수업이 끝나고 집에 갔다고 해 보자.**

> 🗣 **"새벽 3시에 컨테이너가 죽었습니다. 누가 다시 띄우죠?"**

---

## 📖 ① Compose 가 못 하는 세 가지

### 하나. **죽으면 내가 살려야 한다**

14일차에 `restart: unless-stopped` 를 적었다. 그건 **"죽으면 다시 켜라"** 다. 그런데 이런 경우는 어떤가.

- 컨테이너는 살아 있는데 **안에서 프로그램이 먹통**이다 (응답을 안 한다)
- 호스트가 통째로 재부팅됐다
- 메모리를 다 먹고 **되살아나기를 반복**한다

> 📌 Compose 의 `restart` 는 **죽은 것을 다시 켜는 것**까지다. **"살아 있지만 일을 못 하는 상태"** 는 모른다.

### 둘. **늘리려면 내가 늘려야 한다**

접속이 몰린다. 웹 컨테이너를 3개로 늘리고 싶다.

```bash
docker compose up -d --scale web=3     # 된다. 그런데…
```

늘어난 셋에게 **어떻게 나눠 보낼 것인가?** 앞에 로드밸런서를 직접 세워야 하고, 하나가 죽으면 그 목록에서 **직접 빼야** 한다.

### 셋. **내 PC 한 대 안이다**

Compose 는 **한 대짜리** 도구다. 서버를 두 대, 열 대로 늘리면 Compose 는 그 사이를 모른다. 어느 서버에 무엇을 올릴지, 한 대가 꺼지면 그 위의 것들을 어디로 옮길지 — 전부 사람이 한다.

| 우리가 겪을 일 | Compose | 쿠버네티스 |
|----------------|---------|------------|
| 컨테이너가 죽었다 | `restart` 로 다시 켠다 | **개수를 다시 맞춘다** |
| 안 죽었는데 먹통이다 | 모른다 | **검사해서 갈아 끼운다** |
| 3개로 늘리고 싶다 | `--scale` + 로드밸런서는 내가 | **`replicas: 3`** 한 줄 |
| 서버가 여러 대다 | 한 대만 본다 | **여러 대를 한 덩어리로** |
| 새 버전으로 바꾼다 | 내렸다 올린다(잠깐 끊긴다) | **하나씩 갈아 끼운다** |

## 📖 ② 오늘의 한 문장 — 명령형과 선언형 ⭐⭐

지금까지 우리가 친 명령은 전부 **"해라"** 였다.

```bash
sudo apt install nginx          # 설치해라
sudo systemctl start nginx      # 켜라
docker run -d -p 8080:80 nginx  # 띄워라
```

쿠버네티스에 하는 말은 다르다.

```yaml
replicas: 3        # "web 이 3개 떠 있는 상태여야 한다"
```

> 📌 **명령형(imperative)** = **무엇을 하라**고 시킨다. 시킨 일이 끝나면 그걸로 끝이다.
> 📌 **선언형(declarative)** = **어떤 상태여야 하는지**를 적는다. 그 상태가 깨지면 **누군가 계속 되돌린다.**

> 💡 **비유: 에어컨.**
> 명령형은 **"3분간 찬바람을 틀어라"** 다. 3분 뒤에 더워지면 내가 또 틀어야 한다.
> 선언형은 **"24도를 유지해라"** 다. 더워지면 **에어컨이 알아서** 다시 돈다.
> 쿠버네티스는 온도계를 들고 계속 들여다보는 쪽이다.

> 🗣 **"`docker run` 은 '해라', 쿠버네티스는 '이렇게 되어 있어라' 입니다."**

이 차이가 **5번 절에서 눈으로 보인다** — Pod 를 지워도 돌아온다. 지운 것을 되살리는 게 아니라, **개수가 모자라서 새로 만드는 것**이다.

---

## 📖 ③ 그래서 쿠버네티스란

> **원하는 상태를 적어 두면, 실제 상태를 그 상태에 계속 맞춰 주는 시스템.**

맞추는 일을 하는 쪽이 **컨트롤 플레인**이고, 실제로 컨테이너가 도는 곳이 **노드**다.

```
   내가 적는다          쿠버네티스가 본다           실제
  "web 3개"     ──▶   지금 2개네? 하나 모자라  ──▶  하나 더 만든다
                 ◀──  계속 비교한다 (조정 루프)  ──
```

| 쿠버네티스 쪽 | 하는 일 | 14일차로 치면 |
|---------------|---------|---------------|
| **컨트롤 플레인** | 원하는 상태와 실제를 비교해 맞춘다 | 내가 터미널 앞에 앉아 지켜보던 일 |
| **노드** | 실제로 컨테이너를 돌린다 | Docker Engine 이 하던 일 |
| **kubectl** | 내가 원하는 상태를 **전달**한다 | `docker` 명령어 자리 |

> 🔎 **컨테이너를 돌리는 일 자체는 여전히 컨테이너 런타임이 한다.** 쿠버네티스는 그 위에서 **무엇을 몇 개 어디에** 돌릴지를 정한다. 14일차에 배운 것이 사라지는 게 아니라 **그 위에 층이 하나 얹히는** 것이다.

---

## 📖 ④ 만능은 아니다

| 상황 | 쿠버네티스가 불리한 이유 |
|------|--------------------------|
| **컨테이너가 몇 개 안 된다** | 배보다 배꼽이 크다. Compose 가 더 빠르고 단순하다 |
| **혼자 쓰는 개발 환경** | 매번 매니페스트를 쓰는 비용이 더 크다 |
| **서버가 한 대뿐이다** | 세 가지 문제 중 둘(여러 대·분산)이 애초에 없다 |
| **배울 시간이 없다** | 용어와 개념이 많다. 오늘 우리는 **셋만** 쓴다 |

> 📌 실무에서도 **Compose 로 충분한 곳은 Compose 를 쓴다.** 오늘 배우는 이유는 "이게 더 좋아서"가 아니라, **컨테이너가 많아졌을 때 세상이 어떻게 푸는지**를 알기 위해서다.

> 🗣 **"14일차에 쿠버네티스는 이름만 알아 두라고 했죠. 오늘 그 이름을 열어 봅니다."**

## 🧪 질문 / 실습

- 14일차 `restart: unless-stopped` 로 **풀리지 않는** 고장을 하나 들어 보자
- 에어컨 비유에서 **온도계** 역할을 하는 것은 쿠버네티스의 무엇일까?
- `docker run -d --name web nginx` 를 치고 `docker rm -f web` 을 하면 어떻게 되나? 쿠버네티스였다면?
- 우리 반처럼 **PC 한 대**에서 쓰는 것은 쿠버네티스를 제대로 쓰는 걸까? 아니라면 왜 배우나?

## 📝 강의 메모

- ⭐⭐ **칠판 한 줄로 시작한다** — `docker run`(해라) ↔ `kubectl apply`(이렇게 되어 있어라)
- ⭐ **에어컨 비유**가 가장 잘 먹힌다. "3분 틀어라" vs "24도 유지해라" 를 하루 종일 같은 말로 부를 것
- ⚠️ **여기서 용어를 쏟지 않는다.** Pod·Deployment·Service 는 3번 절에서 처음 꺼낸다
- ⚠️ "Compose 는 틀렸고 쿠버네티스가 맞다" 로 들리지 않게 한다 — ④를 꼭 짚는다. 학생이 현업에서 처음 만나는 건 대개 Compose 다
- 🗣 ③의 조정 루프 그림은 **화살표 두 개**로 충분하다. 컨트롤러·스케줄러 이름은 꺼내지 않는다
- ⏱ 이론 25분. **실습이 없다.** 설치가 백그라운드로 도는 동안 하는 절이다
