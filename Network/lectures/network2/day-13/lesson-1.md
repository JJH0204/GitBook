## 2. 구성 요소

### 버전 관리가 푸는 문제 세 가지

| 문제 | 파일명으로 할 때 | 버전 관리 도구로 할 때 |
|---|---|---|
| 이력: 언제, 누가, 왜 고쳤나 | 파일명에 적히지 않는다 | 커밋마다 기록된다 |
| 되돌리기: 어제 것으로 | 운 좋으면 복사본이 있다 | 아무 시점으로든 돌아간다 |
| 협업: 둘이 같은 파일을 고쳤다 | 한 사람 것이 덮어써진다 | 합치고, 겹치면 충돌로 알려 준다 |

Git은 2005년에 리눅스 커널을 관리하려고 만든 분산 버전 관리 시스템이다. Git과 GitHub는 다르다. Git은 도구이고, GitHub는 그 결과물을 올려 두는 웹 서비스이다.

비유: 게임 세이브 파일이다. 커밋은 세이브 지점이다. 보스전에서 죽으면 마지막 세이브로 돌아간다. 파일명에 날짜를 붙이는 것은 세이브 없이 스크린샷만 찍는 것과 같다.

### Git의 세 자리

오늘 하루를 관통하는 그림이다.

```
 ① 작업 디렉터리        ② 스테이지(Staging)        ③ 저장소(Repository)
   내가 고치는 곳    ──▶    "이번에 담을 것"    ──▶    확정된 이력
                   git add                    git commit

   파일을 고친다          장바구니에 담는다            영수증을 끊는다
```

| 자리 | 다른 이름 | 무슨 상태인가 | 확인 |
|---|---|---|---|
| ① 작업 디렉터리 | Working Directory | 고쳤지만 아직 Git이 모른다 | `git status`에 빨강 |
| ② 스테이지 | Index, Staging Area | 이번 커밋에 넣겠다고 고른 것 | `git status`에 초록 |
| ③ 저장소 | Repository(`.git/`) | 확정된 이력 | `git log` |

비유: 장보기이다. ① 매대에서 물건을 고르고(수정), ② 장바구니에 담고(`add`), ③ 계산한다(`commit`). 담지 않은 물건은 계산되지 않는다. `add`를 빠뜨리면 그 파일은 커밋에 들어가지 않는다.

"왜 두 단계인가, 그냥 저장하면 되지 않나"라는 질문의 답은 이렇다. 고친 것 전부가 아니라 의미가 맞는 것만 골라 묶기 위해서이다. 예를 들어 로그인 기능 파일 3개와 오타 수정 파일 1개를 고쳤다면 커밋 두 개로 나누는 것이 좋다.

### 커밋: 저장이 아니라 "의미 있는 한 묶음"

```
 커밋 = 변경 묶음 + 누가 + 언제 + 왜(메시지) + 고유 번호(해시)
```

```
commit a3f9c21e8b...          ← 해시 (지문)
Author: student <me@...>
Date:   2026-10-24

    로그인 폼 유효성 검사 추가       ← 메시지 = "왜"
```

| 나쁜 메시지 | 좋은 메시지 |
|---|---|
| `수정`, `ㅇㅇ`, `asdf` | `로그인 폼 유효성 검사 추가` |
| `여러 가지 고침` | `nginx 설정에서 포트 8080으로 변경` |

- 메시지 규칙은 하나다. 무엇을 왜 했는지 한 줄로 쓴다.
- 커밋 메시지를 영어로 써야 하는가는 팀 규칙을 따른다. 혼자 쓰면 한국어도 괜찮다.
- AI에게 `git diff`를 보여주고 메시지 초안을 받아도 된다. 단, 내가 읽고 고친다. → [10일차 AI 검증](../day-10/lesson-5.md)

{% hint style="warning" %}
CAUTION: 커밋은 자주, 작게 한다. 하루 종일 고치고 한 번에 커밋하면 되돌릴 지점이 없다.
{% endhint %}

## 3. 동작 원리

세 자리 사이를 파일이 이동하는 순서는 다음과 같다.

1. 작업 디렉터리에서 파일을 고친다. 이 변경은 Git이 아직 모른다.
2. `git add`로 이번 커밋에 넣을 변경을 스테이지에 담는다.
3. `git commit`으로 스테이지의 내용을 저장소에 확정한다. 이력에 해시와 메시지가 붙는다.
4. `git log`로 확정된 이력을 읽는다.

## 4. 약어·용어

| 용어 | 뜻 |
|---|---|
| 저장소(Repository, repo) | 이력이 담긴 프로젝트 폴더(`.git/`이 들어 있다) |
| 커밋(Commit) | 변경 한 묶음 = 세이브 지점 |
| 브랜치(Branch) | 갈라진 작업 줄기. → [4. 브랜치와 협업](lesson-4.md) |
| 원격 저장소(Remote) | 인터넷에 있는 저장소(= GitHub). → [3. GitHub와 원격 저장소](lesson-3.md) |
| `push` / `pull` | 내 것을 올리기 / 남의 것을 받기 |
| `clone` | 원격 저장소를 통째로 복제. → [5. 서버에 배포해 보기](lesson-5.md) |

## 강의 메모

- 도입은 `최종_진짜_최종.docx` 스크린샷 한 장이면 된다.
- 세 자리 그림을 칠판에 그리고 하루 종일 지우지 않는다. `git status`를 칠 때마다 "지금 어느 자리인가"를 묻는다.
- Git과 GitHub는 다르다는 점을 여기서 못 박는다. 뒤에서 계속 헷갈린다.
- 장바구니 비유가 가장 잘 먹힌다. `add`는 "담는다", `commit`은 "계산한다"로 계속 부른다.
- 이론은 20분이다. 실습은 2번부터이므로 여기서 오래 끌지 않는다.
