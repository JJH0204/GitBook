## 2. 구성 요소

### 브랜치: 평행 우주

```
                    ┌──● feature  "새 기능 실험"
                    │
 ●───●───●──────────┴──────●  main   "항상 동작하는 것"
 첫   둘   셋                 합침(merge)
```

브랜치는 갈라진 작업 줄기이다. 같은 폴더에서 다른 버전을 왔다 갔다 한다.

- `main`: 언제나 동작해야 하는 줄기(운영에 올리는 것)이다.
- `feature/...`: 실험하는 줄기이다. 망해도 버리면 그만이다.

비유: 문서의 "사본 만들어 고치기"인데, 합칠 때 Git이 알아서 섞어 준다는 점이 다르다.

| 명령 | 뜻 |
|---|---|
| `git branch` | 브랜치 목록(별표가 지금 위치) |
| `git switch -c feature/login` | 만들고 이동(옛 명령: `checkout -b`) |
| `git switch main` | 이동 |
| `git merge feature/login` | 지금 브랜치에 저 브랜치를 합친다 |
| `git branch -d feature/login` | 다 쓴 브랜치 삭제 |

{% hint style="warning" %}
CAUTION: `merge`는 받는 쪽에서 친다. `main`에 합치려면 `main`으로 이동한 뒤 `git merge feature/login`을 실행한다. 11일차 ACL의 "받는 쪽에서 친다"와 같은 감각이다.
{% endhint %}

`ls`로 파일이 사라졌다 나타나는 장면이 브랜치 설명의 전부이다. 브랜치를 바꾸면 같은 폴더의 파일이 그 브랜치의 모습으로 바뀐다.

### 충돌: Git이 묻는 질문

충돌은 고장이 아니다. Git이 "둘 중 어느 쪽인지 모르겠다"고 물어보는 것이다.

충돌 조건은 같은 파일의 같은 줄을 양쪽에서 다르게 고쳤을 때이다. 다른 파일이거나 다른 줄이면 Git이 알아서 합친다.

{% hint style="warning" %}
CAUTION: 먼저 갈라진 뒤 양쪽에서 각각 커밋해야 충돌이 난다. `main`에 먼저 커밋하고 브랜치를 만들면 갈라진 것이 아니라 앞서 나간 것이므로 Git이 `Fast-forward`로 조용히 합친다.
{% endhint %}

충돌이 나면 다음 메시지가 나온다.

```
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.
```

파일은 이렇게 바뀐다.

```
<<<<<<< HEAD
<h1>코리아IT</h1>              ← 지금 브랜치(main) 것
=======
<h1>KoreaIT Academy</h1>      ← 합치려는 브랜치(feature) 것
>>>>>>> feature/title
```

| 표시줄 | 뜻 |
|---|---|
| `<<<<<<< HEAD` | 아래부터 지금 브랜치의 내용 |
| `=======` | 두 내용의 경계 |
| `>>>>>>> <브랜치>` | 위까지가 합치려는 브랜치의 내용 |

### Pull Request: 개념만

실무에서는 `main`에 바로 merge하지 않는다.

```
 feature 브랜치 push ──▶ GitHub 에서 Pull Request 생성
                       ──▶ 동료가 코드 리뷰 ──▶ 승인 ──▶ merge
```

Pull Request(PR)는 "내 브랜치를 합쳐 달라"는 요청이자 리뷰하는 자리이다. 11일차 보안의 감각과 같다. 바로 반영하지 않고 한 번 거른다. 오늘은 개념까지만 다룬다. 혼자 하는 실습에서는 효과가 나지 않는다.

## 3. 동작 원리

충돌을 푸는 순서는 세 단계이다.

1. 표시줄 세 종류를 전부 지운다.
2. 남길 내용만 남긴다(한쪽, 양쪽, 새로 쓰기 중 선택).
3. `git add`, `git commit`을 차례로 실행한다.

합치기를 포기하고 합치기 전으로 돌아가려면 `git merge --abort`를 실행한다.

`merge`의 결과는 두 가지이다. 갈라진 뒤 `main`이 그대로이면 `Fast-forward`가 되어 이력이 일직선이다. 양쪽이 각각 커밋했으면 합치기 커밋이 생기고 이력이 갈라졌다 합쳐진 그림(`|\`)이 된다. 이 그림은 충돌을 풀고 나서 `git log --oneline --graph --all`에서 보인다.

## 4. 약어·용어

| 용어 | 뜻 |
|---|---|
| Fast-forward | 갈라지지 않아서 포인터만 앞으로 옮기는 합치기 |
| 충돌(conflict) | 같은 파일의 같은 줄을 양쪽이 다르게 고친 상태 |
| `HEAD` | 지금 있는 브랜치의 끝 |
| PR(Pull Request) | 브랜치를 합쳐 달라는 요청과 리뷰 자리 |

## 강의 메모

- `ls`로 파일이 사라졌다 나타나는 장면을 꼭 보여 준다. 브랜치 이해의 90%이다.
- 충돌은 반드시 일부러 낸다. 수업에서 내지 않으면 현업에서 처음 만나 당황한다.
- "표시줄을 지우는 것이 해결의 절반"을 강조한다. 학생들은 표시줄을 남긴 채 커밋한다.
- `checkout` 대신 `switch`를 가르친다. 요즘 권장이며 `checkout`은 하는 일이 너무 많아 혼란스럽다.
- 충돌 실습은 순서를 틀리면 충돌이 나지 않는다. 브랜치를 먼저 만든다. 원본 기록에 따르면 2026-10-16 실측으로 확인했다.
- PR은 개념만 다룬다. 시간이 없으면 화면 한 장 보여 주고 끝낸다.
- 실습은 25분이다. 시간이 모자라면 이 절을 통째로 줄인다(필수는 2, 3, 5번).
