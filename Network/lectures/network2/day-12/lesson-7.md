## 2. 구성 요소

### 프록시: 대신 다녀오는 심부름꾼

```
 [ 사내 PC ] ──"example.com 주세요"──▶ [ Proxy 3128 ] ──실제 요청──▶ [ 인터넷 ]
             ◀────── 받아다 준다 ──────               ◀── 응답 ──
                                         └ 기억해 둔다(캐시) · 기록한다(로그) · 막는다(필터)
```

| 얻는 것 | 설명 |
|---|---|
| 캐시 | 같은 것을 또 요청하면 밖에 안 나가고 바로 준다. 빠르고 회선을 아낀다 |
| 필터링 | 특정 사이트와 카테고리를 차단한다 |
| 로그와 감사 | 누가, 언제, 어디에 갔는지 남는다 |
| 익명성 | 상대 서버에는 프록시 IP만 보인다 |

### 포워드 vs 리버스

| | 포워드 프록시 | 리버스 프록시 |
|---|---|---|
| 누구 편 | 클라이언트 편 | 서버 편 |
| 위치 | 사내망 출구 | 웹서버 앞 |
| 아는 사람 | 클라이언트가 설정해서 쓴다 | 클라이언트는 모른다(그냥 웹서버인 줄 안다) |
| 목적 | 캐시, 차단, 감사 | 부하 분산, HTTPS 처리, 보호 |
| 예 | squid(오늘) | nginx, CDN, 로드밸런서, Ingress(14, 16일차) |

비유: 회사 우편실(포워드)과 건물 안내데스크(리버스)다. 우편실은 직원이 맡긴 편지를 대신 부친다. 안내데스크는 찾아온 손님을 받아 알맞은 사무실로 보낸다. 손님은 그것이 안내데스크인지 모른다.

리버스 프록시는 16일차에 Ingress라는 이름으로 다시 나온다. → [16일차](../day-16/README.md)

### 여섯 단계로 본 구축(squid)

| 단계 | 내용 |
|---|---|
| ① 설치, ④ 확인 | `sudo apt install squid -y`, `systemctl status squid`, `sudo ss -tulnp \| grep 3128`(프록시 표준 포트 3128) |
| ⑥ 검증 | `curl -I -x http://127.0.0.1:3128 http://example.com`(프록시 경유, `-x`) |
| ② 설정 | `/etc/squid/squid.conf`에 차단 규칙 추가 |

```
... TCP_MISS/200 ...   ← 처음: 캐시에 없어서 밖에 다녀왔다
... TCP_HIT/200 ...    ← 두 번째: 기억해 둔 것을 바로 줬다
```

두 번째 요청은 인터넷에 나가지도 않았다. 이것이 캐시다. `TCP_HIT`는 사이트가 캐시를 허용할 때만 뜬다. 안 뜨면 응답 헤더의 `Cache-Control` 때문이다. 캐시는 서버가 허락해야 한다.

### squid ACL

```
acl blocked_sites dstdomain .example.com
http_access deny blocked_sites
```

`acl`은 11일차 라우터에서 쓴 그 단어다. "순서대로 읽고 처음 맞는 규칙을 적용한다"는 원리까지 같다. → [11일차 ACL](../day-11/README.md) 다만 라우터 ACL은 IP와 포트로, 프록시 ACL은 도메인과 URL로 막는다. 계층이 다르다.

| 설정 | 뜻 |
|---|---|
| `acl localnet src 192.168.0.0/24` | 누가 쓸 수 있나(출발지) |
| `acl blocked_sites dstdomain .example.com` | 어디를 막나(목적지 도메인) |
| `http_access allow localnet` | 허용 |
| `http_access deny blocked_sites` | 차단. 위에서부터 순서대로 평가한다 |
| `http_port 3128` | 듣는 포트 |

{% hint style="warning" %}
CAUTION: `http_access`는 위에서부터 읽어 처음 맞는 줄을 적용한다. 차단 규칙은 같은 대상을 허용하는 줄(예: `http_access allow localhost`)보다 위에 둔다. 원본 노트는 `http_access deny all` 위쪽에 두라고 했으나, 우분투 기본 설정에서는 `allow localhost`가 더 위에 있어 차단이 먹지 않을 수 있다. 확인 필요. → [squid 프록시 구축과 차단 실습](lesson-7-lab.md)
{% endhint %}

### 클라이언트에 프록시를 설정한다는 것

| 어디 | 방법 |
|---|---|
| 리눅스 명령줄 | `export http_proxy=http://192.168.x.x:3128`(그 창에서만) |
| `curl` | `-x http://...:3128` |
| 브라우저, Windows | 설정 > 네트워크 > 프록시 서버 칸 |

{% hint style="info" %}
NOTE: HTTPS는 프록시가 내용을 볼 수 없다(암호화). 그래서 `CONNECT`로 터널만 뚫어주고 도메인 이름 정도만 안다. 회사가 HTTPS 내용까지 보려면 SSL 가로채기(인증서 설치)가 필요하다. 프라이버시 논쟁이 여기서 시작된다.
{% endhint %}

## 3. 동작 원리

### 프록시 vs NAT: 계층으로 구분한다

| | NAT (10일차) | 프록시 (오늘) |
|---|---|---|
| 계층 | 3, 4계층(IP, 포트) | 7계층(HTTP 등 응용) |
| 하는 일 | 주소 바꿔치기 | 요청을 대신 수행 |
| 클라이언트 설정 | 필요 없다(모르고 지나간다) | 프록시 주소를 넣어야 한다(포워드) |
| 볼 수 있는 것 | IP, 포트 | URL, 도메인, 내용 |
| 캐시 | 못 한다 | 한다 |

"사내에서 유튜브만 막아 주세요"를 NAT로 할 수 있을까? 유튜브 IP를 전부 알아야 하고 매일 바뀐다. 그래서 프록시(또는 7계층 방화벽)를 쓴다.

## 5. 약어·용어

| 용어 | 뜻 |
|---|---|
| 프록시 (proxy) | 클라이언트나 서버를 대신해 요청을 수행하는 중계 서버 |
| 포워드 / 리버스 프록시 | 클라이언트 편 / 서버 편 프록시 |
| squid | 대표적인 포워드 프록시. 기본 포트 3128 |
| 캐시 | 한 번 받은 응답을 기억해 두는 것 |
| `TCP_MISS` / `TCP_HIT` | squid 로그에서 캐시에 없었음 / 캐시에서 응답함 |
| ACL (Access Control List) | 허용과 차단 규칙 목록 |
| `CONNECT` | HTTPS용 터널을 여는 HTTP 메서드 |

- 여유가 없으면 차단 규칙까지만 하고 캐시는 시연으로 한다(또는 반대).
