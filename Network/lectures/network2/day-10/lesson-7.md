## 학습 목표

- TCP와 UDP가 OSI 4계층(전송 계층)의 두 방식임을 안다.
- 연결, 신뢰성, 순서, 속도로 TCP와 UDP를 비교한다.
- 3-way handshake(SYN → SYN-ACK → ACK)를 설명하고 `tcpdump`로 직접 본다.
- 서비스마다 TCP를 쓸지 UDP를 쓸지 이유와 함께 고른다.

## 이전 학습과의 연결

[6. 서버란 무엇인가](lesson-6.md)에서 서버는 요청을 기다린다고 했다. 그 요청은 네트워크를 타고 온다. 그런데 네트워크는 완벽하지 않다. 패킷은 사라지고, 순서가 뒤섞이고, 늦게 도착한다(3일차 `ping`의 `Request timed out`).

그래서 꼼꼼히 챙길 것인가, 그냥 빨리 보낼 것인가의 두 가지 운반 방식이 있다. 1일차 OSI 7계층의 4계층(전송 계층)이 이 일을 한다. → [6. 프로토콜과 OSI 7계층](../../network1/day-01/lesson-6.md)

## 1. 한눈에 비교

| | TCP | UDP |
|---|---|---|
| 풀이 | Transmission **Control** Protocol | User **Datagram** Protocol |
| 연결 | 연결 먼저(3-way handshake) | 연결 없이 그냥 보낸다 |
| 신뢰성 | 잃어버리면 다시 보낸다(ACK, 재전송) | 잃어버리면 끝 |
| 순서 | 번호표로 순서대로 재조립 | 보장하지 않는다 |
| 속도·부담 | 느리고 무겁다 | 빠르고 가볍다 |
| 헤더 | 20바이트 이상 | 8바이트 |
| 잘 맞는 곳 | 하나라도 틀리면 안 되는 것: 웹, 파일, 메일, SSH | 늦으면 소용없는 것: 영상통화, 게임, 스트리밍, DNS 질문 |

{% hint style="info" %}
NOTE: 등기우편과 전단지에 비유한다. TCP는 등기우편이다. 받는 사람이 있는지 먼저 확인하고, 받았다는 서명(ACK)을 받고, 안 오면 다시 보낸다. 확실하지만 느리다. UDP는 전단지다. 우편함에 그냥 넣고 간다. 받았는지 챙기지 않는다. 대신 매우 빠르게, 많이 뿌릴 수 있다.
{% endhint %}

{% hint style="info" %}
NOTE: 전화와 무전기에 비유할 수도 있다. TCP는 "여보세요?", "네!" 하고 연결된 뒤 말한다. UDP는 무전기처럼 그냥 말한다.
{% endhint %}

## 2. 3-way handshake — TCP의 "여보세요?"

TCP는 데이터를 보내기 전에 세 번 인사한다.

```
 클라이언트                                       서버 (LISTEN 중)
     │ ① SYN        "연결해도 될까요?"     ─────▶  │
     │ ② SYN + ACK  "네, 저도 연결할게요"  ◀─────  │
     │ ③ ACK        "확인, 시작합니다"     ─────▶  │
     │ ════════════ 연결 완료 (ESTABLISHED) ════════ │
     │   데이터 ──▶  ◀── ACK (받았음)                │
```

| 단계 | 플래그 | tcpdump 표시 | 뜻 |
|---|---|---|---|
| ① | SYN (synchronize) | `[S]` | 연결 요청과 "내 번호표는 여기서 시작" |
| ② | SYN, ACK | `[S.]` | 요청 받음(ACK)과 나도 연결 요청(SYN) |
| ③ | ACK (acknowledge) | `[.]` | 확인 |
| 끝 | FIN | `[F.]` | "이제 끊겠다"(정중한 종료) |
| 거절 | RST (reset) | `[R.]` | "그 문 없다". LISTEN하는 프로그램이 없다 = `Connection refused` |

- `tcpdump`에서 `.`이 ACK라는 것만 알면 읽을 수 있다.
- 연결이 맺어지면 `ss -tn`에 `ESTAB`(ESTABLISHED)으로 보인다.

{% hint style="info" %}
NOTE: 9일차에 SSH 서버를 켜기 전에 접속하면 나오던 `Connection refused`가 바로 RST다. 서버가 "그 문 없다"고 답한 것이다.
{% endhint %}

- UDP는 인사가 없다. 첫 패킷부터 바로 데이터를 보낸다. 문이 없으면 ICMP로 알려 줄 뿐, 연결이라는 개념이 없다.

## 3. 누가 무엇을 쓰나

| 서비스 | 전송 | 이유 |
|---|---|---|
| 웹 HTTP / HTTPS | TCP | 웹 페이지 글자 하나가 빠지면 깨진다 |
| SSH, Telnet | TCP | 명령 한 글자가 빠지면 사고다(`rm -rf /tmp/x` → `rm -rf /`) |
| FTP, 메일 | TCP | 파일은 1비트도 틀리면 안 된다 |
| DNS 질문 | UDP (큰 응답, 서버끼리 복사는 TCP) | 질문 하나, 답 하나다. 인사하는 시간이 아깝다. 안 오면 다시 물으면 된다 |
| DHCP | UDP | 아직 IP도 없어 연결을 맺을 수 없다(8일차 DORA가 브로드캐스트였던 이유) |
| SNMP | UDP | 가벼운 감시. 수백 대 장비에 뿌린다 |
| 영상통화, 게임, 스트리밍 | UDP | 0.5초 늦게 온 화면은 버리는 것이 낫다 |

{% hint style="info" %}
NOTE: UDP는 나쁜 TCP가 아니다. 확실함보다 "지금"이 중요한 곳에서는 UDP가 정답이다. 요즘 웹의 HTTP/3(QUIC)는 오히려 UDP 위에 자기만의 신뢰성을 얹었다. 이름만 알아 둔다.
{% endhint %}

## 4. 확인 질문

- 파일 다운로드 도중 패킷 하나가 사라지면? → TCP가 다시 보낸다. 파일은 멀쩡하다.
- 영상통화에서 패킷 하나가 사라지면? → UDP라서 화면이 잠깐 깨지고 넘어간다. 다시 보내면 더 늦어진다.
- DHCP가 TCP를 못 쓰는 이유는? → 연결을 맺으려면 내 IP가 있어야 하는데 아직 없다.
- `tcpdump`에 `[S]` 다음 `[R.]`이 왔다. 무슨 일인가? → 서버에 그 포트를 LISTEN하는 프로그램이 없다.

## 5. 약어·용어

| 용어 | 뜻 |
|---|---|
| TCP | Transmission Control Protocol. 연결형, 재전송으로 신뢰성을 보장 |
| UDP | User Datagram Protocol. 비연결형, 빠르고 가볍다 |
| SYN / ACK / FIN / RST | 연결 요청 / 확인 / 정상 종료 / 강제 거절 플래그 |
| 3-way handshake | TCP 연결을 맺는 세 번의 교환 |
| ESTABLISHED | TCP 연결이 맺어진 상태 |
| 세그먼트 | TCP 데이터 단위 |

## 진행 메모

- 등기우편과 전단지 비유 하나로 표 전체를 설명할 수 있다. 표는 비유 다음에 본다.
- 3-way handshake는 칠판 그림에서 tcpdump 실물 순서로 진행한다. `[S]` `[S.]` `[.]` 세 줄이 찍히는 순간이 오늘의 하이라이트다.
- `Connection refused` = RST로 9일차 에러를 회수하면 "아!"가 나온다.
- DHCP가 UDP인 이유를 8일차 DORA와 묶는다. "IP가 없어서 브로드캐스트, IP가 없어서 UDP"다.
- 시퀀스 번호, 윈도우 크기, 흐름 제어는 이름만 언급한다. 네트워크관리사 필기 대비로 "있다" 정도로 다룬다.
