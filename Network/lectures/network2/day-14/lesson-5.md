## 학습 목표

- Dockerfile이 12일차 ①설치와 ②설정을 적어 두는 문서임을 이해한다.
- `FROM`, `COPY`, `RUN`, `EXPOSE`, `CMD`를 읽고 쓴다.
- `docker build`로 내 이미지를 만들어 띄운다.
- 13일차 Git 저장소에 Dockerfile을 넣어 코드와 환경을 함께 관리한다.
- 옆자리 저장소를 `clone`해서 똑같이 띄워 재현성을 눈으로 확인한다.

## 1. 목적

[2. 설치와 첫 컨테이너](lesson-2.md)에서 "여섯 단계 중 ①설치와 ②설정은 어디로 갔는가?"라는 질문을 남겼다. 답은 이미지 안에 있다는 것이다. 누군가 미리 해서 포장해 둔 것이다. 오늘은 그 포장을 내가 한다. 그 레시피를 적는 문서가 Dockerfile이다.

```
 Dockerfile  ──docker build──▶  이미지  ──docker run──▶  컨테이너
  (레시피 · Git 에 들어간다)      (붕어빵 틀)              (붕어빵)
```

[4. 데이터와 볼륨](lesson-4.md)의 바인드 마운트는 "내 코드를 빌려 보여 주는" 방식이었다. Dockerfile은 "내 코드를 이미지에 넣어 통째로 옮기는" 방식이다. 옮기려면 이쪽이어야 한다.

## 2. 구성 요소

### Dockerfile은 여섯 단계의 ①②를 적은 문서

```dockerfile
FROM nginx:alpine                          # 바탕 이미지 (① 설치의 출발점)
COPY ./site /usr/share/nginx/html          # 내 파일을 넣는다 (② 설정)
EXPOSE 80                                  # 이 포트를 쓴다 (문서용 표시)
CMD ["nginx", "-g", "daemon off;"]         # 켤 때 실행할 명령 (③ 기동)
```

| 명령어 | 뜻 | 12일차 대응 |
|---|---|---|
| `FROM` | 바탕 이미지. 맨 위에 꼭 하나 | OS를 고르는 것 |
| `COPY` | 호스트 파일을 이미지 안으로 | 설정 파일 넣기 |
| `RUN` | 빌드할 때 실행(`apt install` 등) | ① 설치 |
| `WORKDIR` | 기본 작업 폴더 | `cd` |
| `EXPOSE` | 쓰는 포트 표시(여는 것은 `-p`) | 없음 |
| `CMD` | 컨테이너가 켜질 때 실행 | ③ 기동 |

{% hint style="warning" %}
CAUTION: `EXPOSE`는 포트를 열지 않는다. 문서용 표시일 뿐이고 실제로 여는 것은 `docker run -p`이다. 3번 절의 방화벽 이야기와 헷갈리기 쉬운 지점이다. `-p`만이 문을 연다.
{% endhint %}

`RUN`과 `CMD`의 차이는 이렇다. `RUN`은 붕어빵 틀을 만들 때 한 번, `CMD`는 붕어빵을 구울 때마다 실행된다.

### 내 이미지 만들기: 13일차 포트폴리오로

13일차에 만든 작업 폴더(`~/myweb` 등 각자 저장소 이름)에 `site/` 폴더를 만들어 `index.html`, `about.html`을 옮기고 Dockerfile을 쓴다.

```dockerfile
FROM nginx:alpine
COPY ./site /usr/share/nginx/html
EXPOSE 80
```

- `nginx` 이미지는 `CMD`가 이미 들어 있어서 생략해도 된다. `FROM`이 물려준다.
- `:alpine`은 알파인 리눅스 기반의 가벼운 판이다. `nginx:latest`보다 몇 배 작다(`docker images`로 비교한다).

`docker build -t mysite:1.0 .`의 조각은 다음과 같다.

| 조각 | 뜻 |
|---|---|
| `build` | Dockerfile로 이미지를 굽는다 |
| `-t mysite:1.0` | 이름:태그(태그는 버전) |
| `.` | 빌드 컨텍스트. 이 폴더를 Docker에 넘긴다. 점을 빠뜨리면 오류이다 |

이제 이 이미지 하나만 있으면 어느 서버에서든 `docker run` 한 줄로 똑같이 뜬다. [1. 왜 컨테이너인가](lesson-1.md)의 "제 컴퓨터에선 됐는데요가 사라진다"가 여기서 증명된다.

### `.dockerignore`: 13일차 `.gitignore`와 같은 발상

```
.git
.env
*.key
node_modules
*.log
```

{% hint style="danger" %}
WARNING: `.git` 폴더를 이미지에 넣지 않는다. 이력 전체가 딸려 들어가 이미지가 커지고, 과거 커밋에 남은 비밀이 함께 배포된다. 13일차 "비밀은 지워도 이력에 남는다"와 정확히 같은 사고이다.
{% endhint %}

`.dockerignore`는 빌드 컨텍스트(`.`)에서 제외할 목록이다. `.gitignore`가 커밋에서 빼는 것과 자리가 같다.

### Git 저장소에 Dockerfile을 넣는다

`Dockerfile`, `.dockerignore`, `site/`를 `add`, `commit`, `push`한다. 이것이 오늘의 결말이다.

```
  13일차:  Git = 내 코드
  14일차:  Git = 내 코드 + 돌리는 방법(Dockerfile)
```

13일차에는 코드만 Git에 있었다. 이제 "이 코드를 어떤 환경에서 어떻게 돌리는지"까지 Git에 들어갔다.

{% hint style="warning" %}
CAUTION: GitHub Pages를 쓰고 있는 저장소라면 `index.html`을 `site/`로 옮기는 순간 Pages 주소가 깨질 수 있다. 둘 중 하나로 간다. ① Pages 설정에서 폴더를 `/site`로 바꾼다. ② `site/`로 옮기지 않고 `COPY . /usr/share/nginx/html`로 쓰고 `.dockerignore`로 걸러낸다. 13일차 결과물(Pages)을 깨지 않는 것이 중요하다. 수업에서는 ①을 권한다.
{% endhint %}

### 재현성 실험: 옆자리 저장소를 띄워 본다

"어디서나 똑같이 돈다"는 말만으로는 믿기 어렵다. 옆자리 저장소를 `clone`해서 `build`, `run`해 본다.

| 내가 한 일 | 내가 하지 않은 일 |
|---|---|
| `clone`, `build`, `run` | nginx 설치, 설정 파일 수정, 포트 열기, 버전 맞추기 |

이 장면이 14일차의 핵심 증거이다. 옆자리 PC 환경을 하나도 묻지 않았는데 똑같이 떴다. 12일차에 서버 하나 세우는 데 여섯 단계 곱하기 여러 명령이 필요했다. 지금은 세 줄이다. 16일차에는 이 이미지를 그대로 쿠버네티스 클러스터에 올린다.

### 고치면 다시 굽는다

이미지는 고칠 수 없다(읽기 전용). 다시 굽는다. 태그를 올려(`1.0` → `1.1`) 빌드한다.

- 두 번째 빌드는 훨씬 빠르다. 바뀐 층부터만 다시 굽는다(레이어 캐시). [1. 왜 컨테이너인가](lesson-1.md)의 레이어가 여기서 보인다.
- 태그를 올리면 문제가 생겼을 때 이전 이미지로 바로 되돌릴 수 있다. 13일차 커밋과 같은 역할이다.
- `docker images | grep mysite`에 1.0과 1.1이 모두 있으면 되돌릴 수 있다.

## 3. 동작 원리

1. Dockerfile에 바탕 이미지, 넣을 파일, 포트, 시작 명령을 적는다.
2. `docker build`가 빌드 컨텍스트(`.`)를 Docker에 넘긴다. `.dockerignore`에 적힌 것은 빼고 넘긴다.
3. 위에서부터 한 줄씩 실행해 층을 쌓아 이미지가 된다. 바뀌지 않은 층은 캐시를 쓴다.
4. `docker run`이 이미지로 컨테이너를 만들고 `CMD`를 실행한다.
5. 같은 저장소를 `clone`해 `build`하면 어디서든 같은 이미지가 된다.

## 4. 약어·용어

| 용어 | 뜻 |
|---|---|
| Dockerfile | 이미지를 만드는 레시피 파일 |
| 빌드 컨텍스트(build context) | `docker build`가 Docker에 넘기는 폴더(`.`) |
| 태그(tag) | 이미지 버전 표시(`mysite:1.0`) |
| `alpine` | 가벼운 리눅스 기반 이미지 판 |
| `.dockerignore` | 빌드 컨텍스트에서 제외할 목록 |
| 재현성(reproducibility) | 같은 입력으로 어디서나 같은 결과가 나오는 성질 |

## 강의 메모

- "①②는 누가 해 둔 걸까?"에서 "오늘은 내가 한다"로 열면 2번 절과 깔끔히 이어진다.
- 옆자리 저장소 띄우기가 오늘의 가장 좋은 장면이다. 반드시 시간을 남긴다. 저장소 주소를 칠판이나 채팅방에 서로 공유하게 하면 빠르다. 공개 저장소여야 `clone`이 된다. 13일차에 공개로 만들었는지 확인한다.
- Git에 Dockerfile을 넣는 장면이 13, 14일차를 하나로 묶는다. "코드 + 돌리는 방법"을 칠판에 적는다.
- Pages가 깨질 수 있다는 주의를 빼먹지 않는다. 13일차 결과물이 눈앞에서 깨지면 학생 체감이 크다.
- `docker build` 끝의 `.`을 빠뜨리는 실수가 1위이다. `"docker build" requires exactly 1 argument`가 그 증상이다.
- `EXPOSE`가 포트를 열지 않는다는 점은 3번 절의 방화벽 이야기와 묶어서 한 번 더 말한다.
- AI 활용: Dockerfile 초안을 받게 하되 `FROM`의 태그와 `COPY` 경로는 직접 확인시킨다(10일차 검증 원칙).
- 소요는 35분이다. 시간이 모자라면 재빌드(고치면 다시 굽는다)를 생략하고 옆자리 재현은 남긴다. 옆자리 재현이 오늘의 증거이다.
