## 학습 목표

- 컨테이너가 일회용이라는 뜻을 이해한다.
- 바인드 마운트와 볼륨의 차이를 안다.
- 13일차에 `clone`한 내 포트폴리오 폴더를 컨테이너에 연결한다.
- DB 컨테이너(MariaDB)를 띄우고 데이터를 살려 둔다. 12일차에 세운 MariaDB를 회수한다.

## 1. 목적

[3. 핵심 명령과 포트](lesson-3.md)에서 `exec`로 컨테이너 안에 들어가 봤다. 안에서 파일을 고치고 컨테이너를 지운 뒤 같은 이미지로 다시 띄우면 고친 내용이 원래대로 돌아와 있다. 컨테이너는 일회용이다. 지우면 안에 있던 것은 전부 사라진다. 이 절은 그 이유와, 남겨야 할 데이터를 밖에 두는 두 가지 방법을 설명한다.

## 2. 구성 요소

### 컨테이너는 왜 일회용인가

```
 이미지 (읽기 전용)  +  컨테이너 레이어 (쓰기 가능)  =  돌아가는 컨테이너
        ▲ 안 바뀜              ▲ docker rm 하면 사라진다
```

- 컨테이너 안에서 쓴 것은 컨테이너 레이어에만 쌓인다.
- `docker rm`은 그 레이어를 버리는 것이다.

이 성질이 단점만은 아니다. [1. 왜 컨테이너인가](lesson-1.md)의 "청소"가 바로 이 성질이다. 12일차처럼 설정 파일이 `/etc`에 여기저기 남지 않는다. 대신 남겨야 할 것은 따로 챙겨야 한다. 그래서 데이터는 밖에 둔다.

```
  컨테이너 (일회용)  ←──  연결  ──→  호스트의 폴더 / 볼륨 (영구)
```

### 두 가지 방법: 바인드 마운트와 볼륨

| | 바인드 마운트 | 볼륨 |
|---|---|---|
| 쓰기 | `-v /호스트/경로:/컨테이너/경로` | `-v 이름:/컨테이너/경로` |
| 실체 | 내가 지정한 호스트 폴더 | Docker가 관리하는 영역 |
| 보기 | `ls /호스트/경로`로 바로 | `docker volume ls` |
| 좋은 때 | 내 소스코드를 넣을 때 | DB 데이터처럼 Docker가 알아서 할 때 |

### 바인드 마운트: 13일차 포트폴리오 연결

13일차에 `git clone`한 `/var/www/mysite`를 컨테이너의 `/usr/share/nginx/html`에 연결한다.

| 조각 | 뜻 |
|---|---|
| `/var/www/mysite` | 호스트 폴더(13일차 `git clone`한 것) |
| `/usr/share/nginx/html` | 컨테이너 안의 경로 |
| `:ro` | 읽기 전용. 컨테이너가 못 고친다(11일차 최소 권한) |

13일차와 오늘이 처음으로 맞물리는 지점이다. 같은 코드가 세 곳에서 돌고 있다. GitHub Pages(남의 호스팅), 호스트 nginx(80), 컨테이너(8080)이다. 이어서 `cd /var/www/mysite && sudo git pull`로 폴더만 갱신하면 컨테이너를 건드리지 않아도 새로고침에서 바뀐다. 보여 주는 폴더가 같은 폴더이기 때문이다.

12일차 NFS는 시간이 없어 넘어갔지만(Samba로 대체했다) 그 발상은 여기서 그대로 쓴다.

| | 파일 공유(12일차 NFS, Samba) | 바인드 마운트(오늘) |
|---|---|---|
| 한 줄 | 옮기지 않고 남의 폴더를 붙여 쓴다 | 옮기지 않고 호스트 폴더를 붙여 쓴다 |
| 명령 | `mount -t nfs 서버:/srv/share /mnt` | `-v /호스트:/컨테이너` |
| 차이 | 네트워크를 건넌다 | 같은 기계 안이다 |

"복사가 아니라 연결"이다. 한쪽을 고치면 양쪽에서 보인다. 이 감각이 핵심이다.

### 볼륨: DB처럼 Docker에게 맡길 때

12일차에 MariaDB를 설치했을 때 몇 분이 걸렸다. 이번에는 DB 컨테이너이다.

| 조각 | 뜻 |
|---|---|
| `-e KEY=VALUE` | 환경 변수. 이미지에 설정을 넣는 방법(②설정에 해당) |
| `MARIADB_ROOT_PASSWORD` | 이 이미지가 요구하는 변수. 없으면 컨테이너가 바로 죽는다 |
| `-v dbdata:/var/lib/mysql` | DB 파일을 볼륨에 저장 |
| `-p 127.0.0.1:3306:3306` | 밖에 열지 않는다. 11일차 "DB는 절대 공개 금지" |

환경 변수가 "②설정"의 자리이다. 12일차에는 `nano`로 설정 파일을 고쳤다. 이미지는 고칠 수 없으니 밖에서 변수로 넣어 준다. 이 변수들을 파일에 모아 두면 [Compose](lesson-6.md)가 된다.

DB는 처음 뜰 때 데이터 디렉터리를 만든다(몇 초에서 십여 초). `docker logs -f db`에서 `ready for connections`가 보일 때까지 기다린다. 기다리지 않고 바로 접속하면 `Can't connect`가 나는데 에러가 아니라 아직 준비 중이라는 뜻이다. 12일차 ④ 확인 단계와 같은 자리이다. 띄웠다고 끝이 아니라 "받을 준비가 됐는지"를 본다.

클라이언트 명령은 `mysql`이 아니라 `mariadb`이다. 최근 MariaDB 이미지는 `mysql` 이름을 뺐다.

컨테이너를 지워도 데이터가 살아남는지 확인한다. 테이블을 만들고, `docker rm -f db`로 컨테이너를 통째로 지우고, 같은 볼륨으로 다시 띄워 조회하면 행이 그대로 있다.

```
+------+
| id   |
+------+
|    1 |     ← 살아 있다
+------+
```

컨테이너는 지웠는데 데이터는 남았다. 이것이 볼륨이다. 두 번째 기동이 더 빠른 이유는 볼륨에 데이터가 이미 있어서 초기화를 건너뛰기 때문이다.

{% hint style="danger" %}
WARNING: 비밀번호를 명령줄에 쓰는 것은 실습용이다. 실무에서는 환경 파일(`.env`)로 빼고 그 파일은 13일차 `.gitignore`에 넣는다. → [6. 환경을 코드로](lesson-6.md)
{% endhint %}

### 정리와 청소

| 명령 | 뜻 |
|---|---|
| `docker ps -a` | 멈춘 컨테이너가 쌓인다 |
| `docker rm $(docker ps -aq -f status=exited)` | 멈춘 것 정리 |
| `docker volume ls` | 볼륨 목록 |
| `docker volume rm dbdata` | 볼륨 삭제. 데이터가 사라진다 |
| `docker image prune` | 안 쓰는 이미지 정리 |

{% hint style="danger" %}
WARNING: `docker system prune -a`는 3초 멈추고 실행한다. 이미지, 컨테이너, 네트워크, 캐시를 전부 지운다. 11일차 `ufw reset`, 13일차 `git reset --hard`와 같은 자리의 명령이다.
{% endhint %}

볼륨은 `prune`으로도 잘 지워지지 않는다. 그래서 데이터를 두는 자리로 적합하다.

## 3. 동작 원리

1. 컨테이너는 이미지(읽기 전용) 위에 쓰기 가능한 컨테이너 레이어를 얹어 돈다.
2. 컨테이너 안에서 쓴 것은 컨테이너 레이어에 쌓인다.
3. `-v`로 호스트 폴더나 볼륨을 컨테이너 경로에 연결하면 그 경로의 읽기와 쓰기가 레이어가 아니라 연결된 쪽으로 간다.
4. `docker rm`은 컨테이너 레이어만 버린다. 연결된 호스트 폴더와 볼륨은 남는다.
5. 같은 볼륨으로 새 컨테이너를 띄우면 데이터를 그대로 이어받는다.

## 4. 약어·용어

| 용어 | 뜻 |
|---|---|
| 컨테이너 레이어 | 컨테이너 실행 중 쓰기가 쌓이는 층. `rm` 하면 사라진다 |
| 바인드 마운트(bind mount) | 호스트의 폴더를 컨테이너 경로에 연결 |
| 볼륨(volume) | Docker가 관리하는 영구 저장 영역 |
| `:ro` | 읽기 전용(read-only) 연결 |
| 환경 변수(`-e`) | 컨테이너에 값을 넣어 설정하는 방법 |
| `prune` | 안 쓰는 리소스를 일괄 삭제하는 명령 |

## 강의 메모

- "고쳤는데 사라졌어요"를 먼저 체험시킨다. 설명이 필요 없어진다.
- 바인드 마운트가 이 절의 중심이다. 13일차 포트폴리오가 컨테이너에서 뜨는 장면이다. 같은 코드가 Pages, 호스트 nginx, 컨테이너 세 곳에서 도는 것을 칠판에 그린다.
- "컨테이너를 지워도 데이터가 남는" 장면을 반드시 눈으로 보여 준다.
- DB 초기화 대기를 설명 없이 넘기면 `Can't connect`로 질문이 쏟아진다. `docker logs -f`를 띄워 두고 기다리는 법을 가르친다.
- DB를 `127.0.0.1`에만 바인딩하는 이유를 꼭 말한다. 3번 절 방화벽 함정과 한 세트이다.
- 12일차에 MariaDB를 직접 설치했던 반이므로 "그때 몇 분 대 지금 몇 초" 대조가 잘 먹힌다.
- 소요는 25분이다. 시간이 모자라면 DB는 강사 시연만 하고 바인드 마운트만 따라 치게 한다(DB는 6번 절에서 Compose로 다시 나온다).
