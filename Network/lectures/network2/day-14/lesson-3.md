## 📖 ① 명령 대응표 — 12일차와 나란히 ⭐

| 하고 싶은 일 | 12일차 (systemd) | 오늘 (docker) |
|--------------|------------------|---------------|
| 떠 있나 | `systemctl status X` | **`docker ps`** |
| 전부 보기 | `systemctl list-units` | **`docker ps -a`** |
| 로그 | `journalctl -u X` | **`docker logs X`** |
| 로그 실시간 | `journalctl -fu X` | **`docker logs -f X`** |
| 멈추기 | `systemctl stop X` | **`docker stop X`** |
| 켜기 | `systemctl start X` | **`docker start X`** |
| 재시작 | `systemctl restart X` | **`docker restart X`** |
| 없애기 | `apt remove X` | **`docker rm X`** (멈춘 뒤) |
| 설치된 것 | `apt list --installed` | **`docker images`** |
| 안에 들어가기 | `ssh` | **`docker exec -it X bash`** |

> 💡 **이름만 다르고 생각은 같다.** 12일차에 익힌 감각을 그대로 옮기면 된다.

```bash
docker ps                      # 돌아가는 것
docker ps -a                   # 멈춘 것까지
docker logs web                # 접속 로그 (13일차 nginx 로그와 같은 모양)
docker logs -f web             # 실시간 (Ctrl+C 로 나감)
docker stop web
docker start web
docker rm web                  # ⚠️ 멈춘 뒤에만. 강제는 docker rm -f web
docker images
docker rmi nginx               # 이미지 삭제 (쓰는 컨테이너가 없어야)
```

> 🧪 **로그를 실시간으로 켜 두고** 브라우저에서 `http://localhost:8080` 을 몇 번 새로고침해 보자.
> `GET / HTTP/1.1" 200` 이 쌓인다 — **13일차 nginx 액세스 로그와 똑같은 줄**이다.

## 📖 ② 컨테이너 안에 들어가기 — `exec`

```bash
docker exec -it web bash
```

```
root@a3f9c21e:/#                       ← 컨테이너 안의 쉘!
```

```bash
ls /usr/share/nginx/html               # nginx 가 보여주는 폴더
cat /etc/nginx/conf.d/default.conf     # 설정 파일 — ②설정이 여기 들어 있다
hostname                               # 컨테이너 ID
ps -ef                                 # ⭐ 프로세스가 nginx 뿐이다!
exit                                   # 나가기
```

| 조각 | 뜻 |
|------|-----|
| `exec` | 돌아가는 컨테이너 **안에서 명령 실행** |
| `-it` | **대화형**(interactive + tty) — 쉘을 쓰려면 필요 |
| `bash` | 실행할 명령 (가벼운 알파인 이미지는 `sh` 만 있다) |

> ⭐ **`ps -ef` 가 이 절의 하이라이트다.** 컨테이너 안에는 **그 서비스 하나**만 돈다.
> 9일차 VM 안에서 `ps -ef` 를 치면 수십 개가 나왔다 — **"컨테이너는 기계가 아니라 포장된 프로세스"** 라는 뜻이다.
> 💡 `ssh` 로 서버에 들어가는 **느낌은 같지만**, 컨테이너에는 SSH 서버가 없다. `exec` 가 그 역할을 한다.
> ⚠️ **안에서 고친 것은 컨테이너를 지우면 사라진다** → [4_데이터와_볼륨](lesson-4.md) · [5_Dockerfile](lesson-5.md)

## 📖 ③ `-p` 포트 매핑 — 11일차 포트포워딩 그대로

```
 🪟 Windows localhost : 8080
            │
            ▼
  [ WSL (호스트) ] ── -p 8080:80 ──▶ [ 컨테이너 ] : 80
      왼쪽이 호스트                   오른쪽이 컨테이너
```

> 💡 **11일차 PT 공유기의 포트포워딩과 똑같은 그림**이다.
> 공유기: `External 80 → 192.168.0.10:80` · Docker: `-p 8080:80`

```bash
docker run -d -p 8081:80 --name web3 nginx    # 같은 이미지로 하나 더
docker ps                                      # 두 개가 뜬다
sudo ss -tulnp | grep -E ':(8080|8081)'
```

| 쓰기 | 뜻 |
|------|-----|
| `-p 8080:80` | 호스트 **모든 주소**의 8080 → 컨테이너 80 (`0.0.0.0:8080`) |
| `-p 127.0.0.1:8080:80` | **내 안에서만** 접근 (밖에서 못 온다) ⭐ |
| `-P` (대문자) | 이미지가 지정한 포트를 **아무 번호에나** 자동 연결 |
| (안 쓴다) | 밖에서 **전혀** 접근 못 함 — 컨테이너끼리는 통한다 → [6_환경을_코드로](lesson-6.md) |

> 🔎 `ss` 출력의 **왼쪽 주소**를 꼭 보게 한다 — `0.0.0.0:8080` 과 `127.0.0.1:8080` 의 차이가 오늘 보안의 전부다.

## 🚨 ④ 함정 — Docker 는 `ufw` 를 우회한다 ⭐⭐

11 · 12일차에 우리는 **방화벽으로 문을 닫는 법**을 배웠다. 그 감각이 Docker 에서 **조용히 무너진다.**

### 대조 실험 — 같은 방화벽, 같은 클라이언트, 서비스 두 개

**(ㄱ) 호스트에서 직접 띄운 서비스** — 10일차에 쓴 그 한 줄

```bash
cd /tmp && python3 -m http.server 8000 &     # 호스트 프로세스로 8000 번
```

**(ㄴ) 컨테이너로 띄운 서비스**

```bash
docker run -d -p 8080:80 --name web nginx    # 컨테이너로 8080 번
```

**둘 다 `ufw` 에 허용한 적이 없다.**

```bash
sudo ufw status numbered                      # 22 · 80 만 있다. 8000 도 8080 도 없다
```

**이제 밖에서 두 번호를 각각 열어 본다.**

```
🪟 내 Windows 브라우저
   http://localhost:8000   →  ❌ 안 열린다   ← ufw 가 막았다 (의도한 대로)
   http://localhost:8080   →  ✅ 열린다  ⚠️  ← 막히지 않았다!
```

> 🗣 **"같은 PC, 같은 방화벽, 같은 '허용 안 함'. 그런데 컨테이너만 열립니다. 왜죠?"**

### 왜 그런가 — 규칙을 직접 본다 (이건 어느 환경에서나 보인다)

```bash
sudo iptables -t nat -L DOCKER -n | head         # DNAT 규칙: 8080 → 컨테이너 IP:80
sudo iptables -L FORWARD -n --line-numbers | head   # DOCKER 체인이 ufw 체인보다 앞
```

- `ufw` 가 심사하는 자리는 **INPUT**(이 기계 자신에게 오는 트래픽)이다
- Docker 가 띄운 포트는 **DNAT 으로 주소가 바뀌어** 컨테이너로 **FORWARD** 된다 → **INPUT 을 지나가지 않는다**
- 그래서 `ufw` 의 심사대 앞을 **아예 지나치지 않는다**

Docker 공식 문서도 이것을 **설계상 그렇다**고 밝히고 있다 — 포트를 공개하면 트래픽이 돌려지고,
**"방화벽 규칙이 적용되기 전에 라우팅되어, 결국 방화벽 설정을 무시한다"** 는 취지의 문장이 그대로 적혀 있다.

| 잘못된 믿음 | 실제 |
|-------------|------|
| "`ufw` 가 켜져 있으니 안전하다" | **컨테이너 포트는 그대로 열려 있다** |
| "열지 않은 포트는 막혀 있다" | `-p` 로 띄운 순간 **공개된다** |
| "`ufw deny 8080` 하면 막힌다" | **안 막힌다** (성공 메시지만 나온다) |

> 🗣 **"11일차에 배운 최소 개방 원칙이, Docker 를 쓰는 순간 조용히 무너집니다."**

### 대응 — 쉬운 것부터

```bash
# ① 밖에 열 이유가 없으면 로컬에만 바인딩 ⭐ 입문 단계의 정답
docker rm -f web
docker run -d -p 127.0.0.1:8080:80 --name web nginx
sudo ss -tulnp | grep 8080              # 127.0.0.1:8080 으로만 LISTEN ⭐
```

**닫혔는지 확인하는 가장 확실한 방법** — WSL 안에서 **내 IP 로** 쳐 본다

```bash
MYIP=$(ip route get 1.1.1.1 | awk '{print $7; exit}')
curl -m 3 http://127.0.0.1:8080     # ✅ 열린다  (루프백에 붙어 있으니)
curl -m 3 http://$MYIP:8080         # ❌ Connection refused  ⭐ 닫혔다는 증거
```

> ⚠️ **`127.0.0.1` 바인딩의 "밖"은 WSL 모드에 따라 다르게 보인다 — 여기서 헷갈리지 말 것**
>
> | | NAT (`172.x`) | mirrored (`192.168.x`) |
> |---|---|---|
> | 🪟 Windows 브라우저 `localhost:8080` | ❌ 안 열린다 | **✅ 열릴 수 있다** ⚠️ |
> | 🐧 WSL 에서 `curl http://<내 IP>:8080` | ❌ refused | ❌ refused |
>
> mirrored 모드는 **Windows 와 WSL 이 `127.0.0.1` 을 공유**한다(마이크로소프트 문서). 그래서 "로컬에만 열었는데 Windows 에서 보인다" 가 **정상**이다.
> 👉 그래서 **검증은 `curl http://<내 IP>:8080` 로 통일**한다. **두 모드 모두에서 같은 결과**가 나온다.

```bash
# ② 끝났으면 (ㄱ)의 호스트 서비스도 정리
kill %1          # python3 -m http.server 종료
```

- ③ **제대로 막으려면** `ufw` 가 아니라 **`DOCKER-USER` 체인**에 규칙을 넣는다 — Docker 가 자기 규칙보다 먼저 거치도록 비워 둔 자리다
  (실무에서는 `ufw-docker` 같은 보조 스크립트를 쓴다. 이 과정에서는 **"그런 자리가 있다"** 까지만)
- ④ 꼭 공개해야 하면 **앞에 리버스 프록시를 두고** 컨테이너는 로컬에만 연다 → 16일차 **Ingress**
- 🛑 `/etc/docker/daemon.json` 에 `"iptables": false` 는 **권하지 않는다** — 컨테이너 네트워크가 깨진다

> 📌 **오늘 가져갈 한 줄** — **"`-p` 는 방화벽에 구멍을 뚫는 것과 같다. 꼭 필요한 것만 `-p` 한다."**
> 11일차 [최소 개방](../day-11/lesson-3.md) 원칙이 Docker 에서는 **`-p` 를 아끼는 것**으로 나타난다.

## 📝 강의 메모

- ⭐ **명령 대응표(①)** 를 칠판에 — 12일차를 배운 반이라 "아 그거랑 같은 거구나" 가 바로 온다
- ⭐⭐ **④ 방화벽 우회는 오늘의 가장 중요한 15분**이다. **대조 실험 형태로** 간다
  1. **(ㄱ) 호스트 8000 · (ㄴ) 컨테이너 8080** 을 동시에 띄운다
  2. `ufw status` 로 **둘 다 허용한 적 없음**을 확인시킨다
  3. 브라우저로 둘을 **차례로** 연다 → **하나는 막히고 하나는 열린다** (여기서 놀란다)
  4. `iptables -t nat -L DOCKER` 로 **범인을 보여준다**
  5. `127.0.0.1` 바인딩으로 다시 띄워 **닫히는 것을** `curl http://<내 IP>:8080` 로 확인
  - 11 · 12일차를 배운 우리 반에서 이걸 빼면 **"방화벽만 켜면 안전"** 이라는 잘못된 감각이 남는다
- 🚨 **mirrored 모드 학생 주의** — `127.0.0.1` 로 묶어도 **Windows 브라우저에서는 열린다**. 이때 "실패한 게 아니다" 를 즉시 말해 줄 것
  - 👉 검증 기준을 **`curl http://<내 IP>:8080`** 으로 통일하면 반 전체가 같은 결과를 본다
- ⚠️ `python3 -m http.server 8000 &` 를 **반드시 정리**시킨다 (`kill %1`). 안 그러면 다음 STEP 에서 포트가 지저분해진다
- `exec -it` 의 `-it` 를 빼고 쳐 보게 하면 왜 필요한지 바로 안다
- ⏱ 40분 중 **④에 15분**은 확보할 것
