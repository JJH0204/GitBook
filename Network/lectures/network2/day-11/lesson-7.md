## 학습 목표

- 서비스별로 꼭 필요한 포트만 골라 규칙을 설계한다.

## 이전 학습과의 연결

[6. 리눅스 방화벽 ufw](lesson-6.md)(LEC-N2-11-011-DO)에서 도구는 다 배웠다. `allow`, `deny`, `from`, `delete`. 남은 질문은 하나다. 그래서 서버는 무엇을 열어야 하는가.

정답표는 없다. 쓰임에 따라 다르다. 그래서 고르는 방법을 익힌다.

## 1. 구성 요소

### 1.1 두 가지를 따로 정한다

방화벽 규칙 한 줄은 두 개의 질문에 답한다.

```
sudo ufw allow from 192.168.0.0/24 to any port 22 proto tcp
                   └──── ① 누구에게? ────┘      └─ ② 무엇을? ─┘
```

| 질문 | 선택지 | 좁은 쪽 → 넓은 쪽 |
|---|---|---|
| ① 누구에게 | 특정 호스트 → 특정 대역 → Anywhere | `from 192.168.0.50` → `from 192.168.0.0/24` → (생략) |
| ② 무엇을 | 특정 포트 → 포트 범위 → 전체 | `22/tcp` → `40000:40010/tcp` → `allow all` |

둘 다 좁히는 것이 최선이지만 한쪽만 좁혀도 크게 낫다. 관리용 포트(SSH)는 ①을 좁히고, 공개 서비스(웹)는 ②만 좁히는 것이 일반적인 감각이다.

### 1.2 서비스별 최소 개방표

10일차 포트표를 "누구에게 열 것인가" 관점으로 다시 쓴 것이다.

| 서비스 | 포트 | 보통 누구에게 | 메모 |
|---|---|---|---|
| SSH | 22/tcp | 관리자 대역만 | 전 세계에 열면 하루 수천 번 두드려 맞는다 |
| HTTP | 80/tcp | Anywhere | 공개가 목적이다 |
| HTTPS | 443/tcp | Anywhere | 가능하면 80 대신 이쪽 |
| FTP | 21/tcp + 패시브 범위 | 내부망만 | 평문이다. 가능하면 SFTP로 → 12일차 |
| NFS | 2049/tcp | 내부망만 | 파일 공유. 밖에 열 이유가 없다 |
| DNS | 53/udp(+tcp) | 내부망 / 용도에 따라 | 10일차 "UDP인 것" 회수 |
| 메일 | 25, 110, 143 | 용도별로 | 25번을 아무에게나 열면 스팸 중계가 된다 |
| MySQL | 3306/tcp | 절대 Anywhere 금지 | 가능하면 `127.0.0.1`만 듣게 한다 |

{% hint style="danger" %}
WARNING: 데이터베이스 포트를 인터넷에 여는 것은 사고의 단골이다. DB는 웹서버만 접근하면 된다. 가장 좋은 방법은 방화벽 이전에 서비스가 `127.0.0.1`만 듣게 하는 것이다. → [3. 왜 막아야 하나](lesson-3.md)의 ③ 서비스 설정 자리.
{% endhint %}

## 2. 동작 원리

### 2.1 종이 먼저, 명령은 나중

방화벽은 치면서 생각하면 늦다. 끊기고 나서 생각하게 되기 때문이다. 규칙표를 먼저 쓴다. 세 칸이면 충분하다.

| 누구에게 | 무엇을 | 왜 |
|---|---|---|
| 관리자 PC `192.168.0.50` | 22/tcp | 내가 관리해야 하니까 |
| 교실 대역 `192.168.0.0/24` | 8000/tcp | 실습 결과를 서로 봐야 하니까 |
| (나머지 전부) | - | 기본 거부 |

그대로 옮긴다.

```bash
sudo ufw allow from 192.168.0.50 to any port 22 proto tcp
sudo ufw allow from 192.168.0.0/24 to any port 8000 proto tcp
sudo ufw enable                      # 22 를 먼저 열었으니 안전
sudo ufw status numbered             # 적은 대로 들어갔나 확인
```

- 표의 줄 수가 규칙 수다. 표에 없는 줄이 `status`에 있으면 누가 왜 넣었는지 모르는 규칙이다. 지운다.

### 2.2 열어 둔 것은 썩는다

규칙은 만든 날이 가장 정확하고 그 뒤로는 계속 낡는다.

| 흔한 일 | 결과 |
|---|---|
| 테스트하려고 잠깐 열고 닫지 않음 | 몇 달 뒤 아무도 이유를 모르는 구멍 |
| 퇴사한 담당자의 집 IP가 허용 목록에 남음 | 관리되지 않는 통로 |
| 서비스는 껐는데 규칙은 남음 | 나중에 그 포트를 다른 서비스가 쓰면 의도치 않게 공개 |

```bash
sudo ufw status numbered         # 정기 점검: 이 줄, 아직 필요한가?
```

방화벽 점검은 여는 일이 아니라 지우는 일이다.

### 2.3 방화벽보다 상위 해법: 서비스를 끈다

방화벽으로 막는 것보다 서비스를 끄는 것이 낫다. 문이 아예 없으면 규칙도 필요 없다. 학생들은 방화벽만 생각하기 쉽다.

## 3. 약어와 용어

| 용어 | 뜻 |
|---|---|
| 최소 개방 | 필요한 사람에게 필요한 포트만 연다는 설계 원칙 |
| 규칙표 | "누구에게, 무엇을, 왜" 세 칸으로 적은 방화벽 설계표 |
| 허용 목록(allowlist) | 열어 준 출발지와 포트의 목록 |
