## Q1. 스위치는 무엇을 보고 배우나 — [1_스위치_동작원리](lesson-1.md)

A switch receives a frame on port Fa0/3.
Which address does the switch use to **update its MAC address table**?
(스위치가 프레임을 받았다. MAC 주소 테이블을 갱신할 때 쓰는 주소는?)

- A. 목적지 MAC (Destination MAC)
- B. 출발지 MAC (Source MAC)
- C. 목적지 IP
- D. 출발지 IP

{% hint style="success" %}
**정답 및 해설**

**정답: B**
- **배우는 건 출발지, 보내는 건 목적지** — 방향이 반대다
- 프레임이 Fa0/3으로 들어왔다 = 그 **출발지 MAC이 Fa0/3 쪽에 있다**는 뜻 → 표에 기록
- **목적지** MAC은 표를 **조회**할 때 쓴다 (있으면 포워딩, 없으면 플러딩)
- C·D가 오답인 이유: 스위치는 **2계층** 장비라 IP를 보지 않는다 → [1_네트워크장비](../day-03/lesson-1.md)
- 되짚기: Lab 10 에서 `ping` 한 번에 **양쪽 MAC이 모두** 학습된 이유 — 요청과 응답이 오갔으니까
{% endhint %}

## Q2. 루프는 왜 재앙인가 — [1_스위치_동작원리](lesson-1.md)

Two switches are connected by **two redundant links** with STP disabled.
Why does a single broadcast frame cause a **broadcast storm**?
(STP를 끈 채 스위치 두 대를 두 줄로 연결했다. 브로드캐스트 하나가 왜 폭풍이 되나?)

- A. 스위치가 브로드캐스트를 복제해서 보내도록 설계되었기 때문
- B. 2계층 프레임에는 **TTL이 없어** 무한히 순환하기 때문
- C. 브로드캐스트 주소가 잘못 설정되었기 때문
- D. 라우터가 브로드캐스트를 되돌려 보내기 때문

{% hint style="success" %}
**정답 및 해설**

**정답: B**
- IP 패킷은 라우터를 지날 때마다 **TTL이 1씩 줄어** 언젠가 사라진다 → [2_라우터_동작원리](lesson-2.md)
- 그런데 **2계층 프레임에는 그런 장치가 없다** → 고리에 들어가면 **영원히** 돈다
- 게다가 갈림길마다 복제되어 **기하급수적으로 늘어난다** → 회선 마비
- 곁들여 오는 문제: **MAC 테이블 불안정**(같은 MAC이 여러 포트에서 보임), **프레임 중복**
- 그래서 **STP**가 한쪽 링크를 막아 고리를 끊는다 → 3일차 실습의 **주황 점 30초**가 이 확인 과정
- D가 오답인 이유: 라우터는 브로드캐스트를 **차단**한다. 애초에 되돌려 보내지 않는다
{% endhint %}

## Q3. 어느 경로를 고를까 — [2_라우터_동작원리](lesson-2.md)

A router must forward a packet to `172.16.5.10`.
The routing table contains `0.0.0.0/0`, `172.16.0.0/16`, and `172.16.5.0/24`.
Which route is used?
(목적지가 172.16.5.10이고 세 경로가 모두 일치한다. 어느 것을 쓰나?)

- A. `0.0.0.0/0`
- B. `172.16.0.0/16`
- C. `172.16.5.0/24`
- D. 세 경로로 나눠서 보낸다

{% hint style="success" %}
**정답 및 해설**

**정답: C**
- **Longest Prefix Match** — 일치하는 것 중 **마스크가 가장 긴(구체적인)** 경로가 이긴다
- `/24` (24비트 일치) > `/16` (16비트) > `/0` (0비트)
- 비유: `서울시`보다 `서울시 강남구 역삼동`이 배달에 더 유용하다
- A(`0.0.0.0/0`)는 **가장 덜 구체적** → 다른 게 아무것도 안 맞을 때만 쓰인다 (그래서 "디폴트")
- 되짚기: 2일차에 마스크로 "동네 범위"를 정한 것이 여기서 **판단 기준**이 된다 → [4_서브넷팅](../day-02/lesson-4.md)
{% endhint %}

## Q4. 누구 말을 믿을까 — [2_라우터_동작원리](lesson-2.md)

The same network is learned via a **static route** (AD 1) and via **RIP** (AD 120).
Which one is installed in the routing table?
(같은 네트워크를 정적 경로와 RIP이 각각 알려준다. 테이블에 오르는 것은?)

- A. 정적 경로 (Static)
- B. RIP
- C. 둘 다 올라간다
- D. 메트릭이 더 작은 쪽

{% hint style="success" %}
**정답 및 해설**

**정답: A**
- **AD(Administrative Distance) = 정보의 신뢰도, 낮을수록 신뢰**한다
- 정적 **1** < RIP **120** → 정적 경로가 이긴다
- 순서: 직접 연결 **0** → 정적 **1** → EIGRP **90** → OSPF **110** → RIP **120**
- "내 눈으로 본 것 > 관리자가 알려준 것 > 남이 전해준 것"
- D가 오답인 이유: **메트릭은 같은 방식끼리** 비교할 때 쓴다. 방식이 다르면 **AD가 먼저**다
- 이 개념이 6일차 **재분배**의 핵심이 된다 → [6일차](../day-06/README.md)
{% endhint %}

## Q5. 왜 ping이 안 될까 — [3_CLI기초와_실습](lesson-3.md)

R1 has a static route to `192.168.30.0/24`, but **R2 has no route back** to `192.168.10.0/24`.
PC0 (192.168.10.1) pings PC1 (192.168.30.1). What happens?
(R1에는 가는 경로가 있지만 R2에 돌아오는 경로가 없다. ping 결과는?)

- A. 성공한다 — 가는 길만 있으면 된다
- B. 실패한다 — 요청은 가지만 **응답이 돌아올 길이 없다**
- C. 실패한다 — R1의 경로 설정이 잘못되었다
- D. 성공하지만 매우 느리다

{% hint style="success" %}
**정답 및 해설**

**정답: B**
- **라우팅은 왕복이다.** 가는 길과 오는 길을 **양쪽 라우터에 각각** 넣어야 한다
- 요청 패킷은 PC1까지 잘 도착한다 → PC1이 응답을 만든다 → 그런데 **R2가 10.0 으로 가는 길을 모른다** → 버린다
- Lab 12 에서 한쪽 경로를 지웠을 때 나온 그 현상 → [3_CLI기초와_실습](lesson-3.md)
- 확인 방법: 양쪽에서 `show ip route` → **`S` 항목이 각각 있는지**
- C가 오답인 이유: R1 설정은 정상이다. 문제는 **R2 쪽**에 있다
- 💡 이런 "한쪽만 설정"을 자동으로 막아주는 것이 **동적 라우팅** → 다음 시간!
{% endhint %}
