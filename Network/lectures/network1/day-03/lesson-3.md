## 🌉 다리 놓기: "연결했는데, 통신이 되긴 하나?"

그럼 **실제로 잘 통하는지 어떻게 확인**할까? 가장 먼저 쓰는 도구가 **ping**, 그 바탕이 **ICMP**다.

## 📖 ICMP란?

- **ICMP(Internet Control Message Protocol)**: 3계층에서 **오류 보고·상태 진단**을 담당
- 데이터를 실어 나르는 게 아니라, "잘 갔는지 / 왜 안 갔는지"를 알려주는 **연락용** 프로토콜

## 📖 ping — "살아 있니?"

```
내 PC ──(ICMP Echo 요청)──▶ 상대
내 PC ◀──(ICMP Echo 응답)── 상대     → 응답 오면 연결 정상!
```

- 응답이 오면 = 통신 OK, **RTT(왕복 시간, ms)**로 속도도 확인
- 응답이 없으면 = 어딘가 끊김(케이블·IP설정·방화벽 등) → 문제 진단의 첫걸음

```bash
ping 192.168.0.20
ping 8.8.8.8        # 인터넷(구글 DNS)까지 되는지
```

### 자주 쓰는 옵션 (윈도우)

| 옵션 | 뜻 | 쓰는 상황 |
|------|-----|----------|
| `-t` | **계속** 보냄 (`Ctrl+C`로 중지) | 케이블 흔들며 끊김 확인 |
| `-n 10` | 10번만 보냄 | 기본은 4번 |
| `-l 1000` | 패킷 크기 1000바이트 | 큰 패킷도 지나가는지 |
| `-a` | 상대 **이름**도 찾아봄 | IP만 알 때 |

## 📖 ping 결과 읽기 — 메시지마다 원인이 다르다

실습 중 반드시 마주친다. **"안 돼요"가 아니라 "무슨 메시지가 떴나요?"** 로 물어야 한다.

| 메시지 | 뜻 | 유력한 원인 |
|--------|-----|------------|
| `Reply from ... time=1ms TTL=128` | **성공** | — |
| `Request timed out.` | 보내긴 했는데 **답이 없다** | 상대 꺼짐 · 방화벽이 막음 · 돌아올 길이 없음 |
| `Destination host unreachable.` | **길을 모른다**고 누군가 알려줌 | 게이트웨이 설정 오류 · 라우팅 없음 · 같은 망인데 ARP 실패 |
| `TTL expired in transit.` | 홉을 너무 많이 지남 | 라우팅 루프 |
| `General failure.` | 내 PC 쪽 문제 | 내 IP·NIC 설정 이상 |

> 💡 **`timed out` 과 `unreachable` 의 차이**가 핵심이다.
> `timed out` = 편지는 부쳤는데 **답장이 없음** / `unreachable` = **"그런 동네 몰라요"** 라고 반송됨.

### TTL 값으로 상대 OS 추측하기

`Reply` 줄 끝의 `TTL=` 은 **남은 홉 수**다. 출발할 때의 초깃값이 OS마다 달라서 역산할 수 있다.

| 초깃값 | OS |
|--------|-----|
| **128** | 윈도우 |
| **64** | 리눅스 · macOS · 안드로이드 |
| **255** | 네트워크 장비(라우터·스위치) |

- `TTL=128` → 같은 망의 **윈도우 PC** / `TTL=117` → 원래 128에서 **11홉**을 지나온 윈도우 서버
- 라우터를 하나 지날 때마다 **1씩 줄어든다** → 이게 아래 traceroute의 원리다

## 📖 문제가 생기면 — 안에서 밖으로 5단계

무작정 찔러보지 말고 **가까운 곳부터 순서대로** 확인한다. **처음 실패하는 곳이 곧 원인의 위치**다.

```
① ping 127.0.0.1        내 PC의 네트워크 기능 자체는 살아 있나?
② ping <내 IP>          내 랜카드 · IP 설정은 정상인가?
③ ping <게이트웨이>      같은 동네 통신과 대문까지는 정상인가?
④ ping 8.8.8.8          인터넷까지 나가는 길은 정상인가?
⑤ ping google.com       이름을 주소로 바꾸는 것(DNS)은 정상인가?
```

| 처음 실패한 곳 | 범인 |
|---------------|------|
| ① | TCP/IP 스택 (드물다 · 재설치급) |
| ② | 내 IP·마스크 설정, 랜카드 |
| ③ | 랜선 · 스위치 · **게이트웨이 주소** · 서브넷 마스크 |
| ④ | 라우터 · 공유기 · 회선 |
| ⑤ | **DNS** (8일차 → [2_DHCP와_DNS](../day-08/lesson-2.md)) |

> 💡 2일차의 **"증상으로 원인 좁히기"** 표가 여기서 실제 명령으로 바뀐다.

## 📖 traceroute — "어디를 거쳐 가지?"

- 목적지까지 **거쳐가는 라우터(홉)들**을 순서대로 보여줌
- 어느 구간에서 막히는지 파악에 유용
- 윈도우: `tracert 8.8.8.8` / 리눅스: `traceroute 8.8.8.8`

### 어떻게 홉이 보이는 걸까 — TTL을 하나씩 늘린다

```
TTL=1 로 보냄  →  첫 번째 라우터에서 0이 됨  →  "TTL 초과" 를 되돌려줌
                  그 답장의 출발지 = 1번째 홉의 주소!
TTL=2 로 보냄  →  두 번째 라우터가 답장       →  2번째 홉
TTL=3, 4, 5 …  →  목적지에 닿을 때까지 반복
```

- 즉 **일부러 실패시켜서** 중간 장비들의 정체를 알아내는 영리한 방법
- `* * *` 로 나오는 홉은 **죽은 게 아니라** 응답을 안 하도록 설정된 장비다 (보안상 흔함)

## 🧪 실습 / 질문

- **5단계를 순서대로** 직접 쳐보기 (①~⑤) → 어디까지 성공하는지 기록
- 옆 사람 PC로 `ping` → 응답/RTT 확인, **TTL 값으로 상대 OS 맞히기**
- `ping 8.8.8.8` 성공, `ping google.com` 실패라면? → IP는 되는데 **DNS** 문제 (8일차)
- `tracert 8.8.8.8` → 몇 홉을 지나는지, `* * *` 이 나오는 구간이 있는지 확인
- **일부러 고장 내보기**: 게이트웨이 주소를 없는 주소로 바꾼 뒤 `ping 8.8.8.8`
  - 어떤 메시지가 뜨나? 5단계 중 몇 번에서 처음 실패하나? (원복 잊지 말 것)

## 📝 강의 메모

- ping = "네트워크 청진기" 비유로 각인 (문제 생기면 제일 먼저 하는 것)
- ICMP는 3계층 → 1일차 OSI 표와 연결 ([6_프로토콜_OSI7계층](../day-01/lesson-6.md))
- **"안 돼요" → "무슨 메시지가 떴어요?"** 로 되묻는 습관을 학생에게 심어줄 것
- 5단계는 **오늘 이후 모든 실습의 기본기**다 → 칠판 한쪽에 적어두고 매번 참조
- 일부러 고장 내보는 실습이 이해도가 가장 높다 (단, **원복 확인**까지 시킬 것)
