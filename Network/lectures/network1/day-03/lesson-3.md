## 2. 구성 요소

### 2.1 ICMP

- ICMP(Internet Control Message Protocol)는 3계층에서 오류 보고와 상태 진단을 담당한다.
- 데이터를 실어 나르는 프로토콜이 아니라 "잘 갔는지, 왜 안 갔는지"를 알려 주는 연락용 프로토콜이다.

### 2.2 ping

ping은 "살아 있니?"를 묻는 명령이다.

```
내 PC --(ICMP Echo 요청)--> 상대
내 PC <--(ICMP Echo 응답)-- 상대     응답이 오면 연결 정상
```

- 응답이 오면 통신이 정상이다. RTT(왕복 시간, ms)로 속도도 확인한다.
- 응답이 없으면 어딘가 끊긴 것이다(케이블, IP 설정, 방화벽 등). 문제 진단의 첫걸음이다.

```bash
ping 192.168.0.20
ping 8.8.8.8        # 인터넷(공개 DNS)까지 되는지
```

자주 쓰는 옵션(Windows)은 다음과 같다.

| 옵션 | 뜻 | 쓰는 상황 |
|---|---|---|
| `-t` | 계속 보낸다(`Ctrl+C`로 중지) | 케이블을 흔들며 끊김을 확인할 때 |
| `-n 10` | 10번만 보낸다 | 기본은 4번 |
| `-l 1000` | 패킷 크기를 1000바이트로 한다 | 큰 패킷도 지나가는지 볼 때 |
| `-a` | 상대 이름도 찾아본다 | IP만 알 때 |

### 2.3 ping 결과 읽기

메시지마다 원인이 다르다. "안 돼요"가 아니라 "무슨 메시지가 떴나요?"로 묻는다.

| 메시지 | 뜻 | 유력한 원인 |
|---|---|---|
| `Reply from ... time=1ms TTL=128` | 성공 | 없음 |
| `Request timed out.` | 보냈지만 답이 없다 | 상대 꺼짐, 방화벽이 막음, 돌아올 길이 없음 |
| `Destination host unreachable.` | 길을 모른다고 누군가 알려 줬다 | 게이트웨이 설정 오류, 라우팅 없음, 같은 망인데 ARP 실패 |
| `TTL expired in transit.` | 홉을 너무 많이 지났다 | 라우팅 루프 |
| `General failure.` | 내 PC 쪽 문제 | 내 IP나 NIC 설정 이상 |

{% hint style="info" %}
NOTE: `timed out`과 `unreachable`의 차이가 핵심이다. `timed out`은 편지를 부쳤는데 답장이 없는 것이고, `unreachable`은 "그런 동네는 모른다"고 반송된 것이다.
{% endhint %}

`Reply` 줄 끝의 `TTL=`은 남은 홉 수다. 출발할 때의 초깃값이 OS마다 달라서 역산할 수 있다.

| 초깃값 | OS |
|---|---|
| 128 | Windows |
| 64 | Linux, macOS, Android |
| 255 | 네트워크 장비(라우터, 스위치) |

- `TTL=128`은 같은 망의 Windows PC다. `TTL=117`은 원래 128에서 11홉을 지나온 Windows 서버다.
- 라우터를 하나 지날 때마다 1씩 줄어든다. 이것이 traceroute의 원리다.

## 3. 동작 원리

### 3.1 안에서 밖으로 5단계

문제가 생기면 무작정 찔러보지 말고 가까운 곳부터 순서대로 확인한다. 처음 실패하는 곳이 곧 원인의 위치다.

| 단계 | 명령 | 확인하는 것 | 처음 실패했을 때의 범인 |
|---|---|---|---|
| 1 | `ping 127.0.0.1` | 내 PC의 네트워크 기능 자체가 살아 있나 | TCP/IP 스택(드물며 재설치급) |
| 2 | `ping <내 IP>` | 내 랜카드와 IP 설정이 정상인가 | 내 IP·마스크 설정, 랜카드 |
| 3 | `ping <게이트웨이>` | 같은 동네 통신과 대문까지 정상인가 | 랜선, 스위치, 게이트웨이 주소, 서브넷 마스크 |
| 4 | `ping 8.8.8.8` | 인터넷까지 나가는 길이 정상인가 | 라우터, 공유기, 회선 |
| 5 | `ping google.com` | 이름을 주소로 바꾸는 것(DNS)이 정상인가 | DNS([8일차 DHCP와 DNS](../day-08/lesson-2.md)) |

2일차의 "증상으로 원인 좁히기" 표가 여기서 실제 명령으로 바뀐다. [2일차 공인 IP와 사설 IP](../day-02/lesson-3.md)를 본다.

### 3.2 traceroute

- 목적지까지 거쳐 가는 라우터(홉)를 순서대로 보여 준다.
- 어느 구간에서 막히는지 파악하는 데 유용하다.
- Windows는 `tracert 8.8.8.8`, Linux는 `traceroute 8.8.8.8`을 쓴다.

홉이 보이는 이유는 TTL을 하나씩 늘리기 때문이다.

1. TTL=1로 보낸다. 첫 번째 라우터에서 0이 되어 "TTL 초과"를 되돌려 준다. 그 답장의 출발지가 1번째 홉의 주소다.
2. TTL=2로 보낸다. 두 번째 라우터가 답장한다. 2번째 홉이다.
3. TTL=3, 4, 5, ...로 목적지에 닿을 때까지 반복한다.

- 일부러 실패시켜서 중간 장비의 정체를 알아내는 방법이다.
- `* * *`로 나오는 홉은 죽은 것이 아니라 응답하지 않도록 설정된 장비다(보안상 흔하다).

실습 절차는 [3-1. 실습: ping 5단계 진단과 traceroute](lesson-3-lab.md)에 있다.

## 4. 약어·용어

| 용어 | 풀이 |
|---|---|
| ICMP | Internet Control Message Protocol, 오류 보고와 상태 진단용 3계층 프로토콜 |
| RTT | Round Trip Time, 왕복 시간 |
| TTL | Time To Live, 패킷이 거칠 수 있는 남은 홉 수 |
| 홉(hop) | 패킷이 지나는 라우터 한 개 |
| DNS | Domain Name System, 이름을 주소로 바꾸는 시스템 |

## 강의 메모

- ping은 "네트워크 청진기" 비유로 각인한다. 문제가 생기면 제일 먼저 하는 것이다.
- ICMP는 3계층이다. 1일차 OSI 표와 연결한다. [1일차 프로토콜 OSI 7계층](../day-01/lesson-6.md)을 본다.
- "안 돼요"를 "무슨 메시지가 떴어요?"로 되묻는 습관을 학생에게 심어 준다.
- 5단계는 오늘 이후 모든 실습의 기본기다. 칠판 한쪽에 적어 두고 매번 참조한다.
- 일부러 고장 내 보는 실습이 이해도가 가장 높다. 단, 원복 확인까지 시킨다.
