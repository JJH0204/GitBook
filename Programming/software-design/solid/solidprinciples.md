## 1. 정의

SOLID는 객체지향 설계에서 변경에 강한 구조를 만들기 위한 다섯 원칙의 첫 글자를 모은 약어다. 원칙은 규칙이 아니라 판단 기준이다. 코드가 작고 변경이 드물면 모든 원칙을 적용하지 않아도 된다.

{% hint style="info" %}
NOTE: SOLID는 클래스 수를 늘리는 것이 목적이 아니다. 목적은 "한 가지 변경이 코드 여러 곳으로 번지는 일"을 줄이는 것이다.
{% endhint %}

## 2. 구성 요소

| 약어 | 원칙 | 정의 | 위반 징후 | 상세 문서 |
|---|---|---|---|---|
| S | 단일 책임 원칙 (Single Responsibility Principle) | 클래스는 변경 이유가 하나여야 한다 | 서로 다른 이유로 같은 클래스를 자주 고친다 | [SRP](srpsingleresponsibilityprinciple.md) |
| O | 개방 폐쇄 원칙 (Open-Closed Principle) | 확장에는 열려 있고 수정에는 닫혀 있어야 한다 | 기능을 추가할 때마다 기존 `if`/`switch`를 고친다 | [OCP](ocpopenclosedprinciple.md) |
| L | 리스코프 치환 원칙 (Liskov Substitution Principle) | 하위 타입은 상위 타입의 계약을 유지해야 한다. 상위 타입이 쓰이는 곳에 하위 타입을 넣어도 올바르게 동작해야 한다 | 하위 클래스에서 예외를 던지거나 상위 클래스의 기대를 깬다 | [LSP](lspliskovsubstitutionprinciple.md) |
| I | 인터페이스 분리 원칙 (Interface Segregation Principle) | 클라이언트는 자신이 쓰지 않는 메서드에 의존하지 않아야 한다 | 구현 클래스에 빈 메서드나 `NotSupportedException`이 있다 | [ISP](ispinterfacesegregationprinciple.md) |
| D | 의존관계 역전 원칙 (Dependency Inversion Principle) | 고수준 모듈은 저수준 구현이 아니라 추상에 의존해야 한다. 저수준 모듈도 같은 추상에 의존한다 | 업무 규칙 클래스가 `new 구체클래스()`로 DB·파일·네트워크 클래스를 직접 만든다 | [DIP](dipdependencyinversionprinciple.md) |

## 3. 동작 원리

다섯 원칙은 응집도는 높이고 결합도는 낮춘다는 하나의 방향으로 모인다.

| 방향 | 관련 원칙 | 설명 |
|---|---|---|
| 응집도를 높인다 | SRP, ISP | 한 클래스·인터페이스에 같은 이유로 바뀌는 것만 모은다 |
| 결합도를 낮춘다 | OCP, DIP | 구체 구현이 아니라 추상을 사이에 둔다 |
| 추상의 신뢰성을 지킨다 | LSP | 추상(상위 타입)을 믿고 쓸 수 있게 하위 타입이 계약을 지킨다 |

원칙 사이의 의존은 다음과 같다.

1. OCP를 만족하려면 추상(인터페이스, 추상 클래스)이 필요하다.
2. 추상을 신뢰하려면 하위 타입이 LSP를 지켜야 한다.
3. 추상이 너무 크면 ISP로 쪼갠다.
4. 추상의 소유와 방향은 DIP로 정한다.

## 4. 약어·용어

| 용어 | 뜻 |
|---|---|
| 책임(responsibility) | 변경이 필요해지는 이유 하나(보통 한 이해관계자의 요구) |
| 계약(contract) | 사전 조건, 사후 조건, 불변 조건 등 타입이 약속하는 동작 |
| 고수준 모듈 | 업무 규칙·정책을 담은 모듈 |
| 저수준 모듈 | DB, 파일, 네트워크 같은 세부 구현을 담은 모듈 |
