## 1. 목적

바이너리를 분석하려면 소스 코드가 기계어가 되는 과정과 그 역과정을 알아야 한다. 이 문서는 컴파일 4단계와 디스어셈블·디컴파일의 차이를 정리한다.

## 2. 구성 요소

| 용어 | 뜻 |
|---|---|
| 프로그램 | 연산 장치가 수행할 동작을 정의한 것. 프로그램을 저장 장치에 이진 형태로 저장하는 방식(Stored-Program)이 상용화되면서 실행 파일을 바이너리라고도 부른다 |
| 소스 코드 | CPU가 수행할 명령을 프로그래밍 언어로 작성한 것 |
| 컴파일 | 한 언어로 작성된 소스 코드를 다른 언어의 목적 코드(object code)로 번역하는 행위. 소스 코드를 어셈블리어로 번역하는 것도, 기계어로 번역하는 것도 컴파일이다 |
| 컴파일러 | 컴파일하는 소프트웨어(GCC, Clang, MSVC) |
| 인터프리터 | 스크립트를 실행 시점에 번역해 수행하는 소프트웨어 |
| 어셈블러 | 어셈블리어를 기계어로 바꾸는 소프트웨어 |
| 디스어셈블러 | 기계어를 어셈블리어로 바꾸는 소프트웨어 |
| 디컴파일러 | 기계어(또는 어셈블리어)를 고급 언어에 가까운 코드로 바꾸는 소프트웨어 |
| 고급·저급 언어 | 사람이 읽기 쉬운 언어(C, Python)와 기계에 가까운 언어(어셈블리어, 기계어) |

Python과 JavaScript는 소스 코드를 바로 실행하는 것처럼 보이지만, Python은 바이트코드(`.pyc`)로 컴파일해 가상 머신이 실행하고 JavaScript 엔진은 JIT 컴파일을 쓴다. 두 언어는 C처럼 기계어 실행 파일을 미리 만들지 않는 경우가 많다는 점이 다르다.

## 3. 동작 원리

### 3.1 C 코드의 컴파일 4단계

C 코드는 일반적으로 전처리, 컴파일, 어셈블, 링크를 거쳐 바이너리가 된다.

| 순서 | 단계 | 하는 일 | 입력 → 출력 |
|---|---|---|---|
| 1 | 전처리 (Preprocess) | 헤더 포함, 매크로 전개 | `.c` → 전처리된 `.i` |
| 2 | 컴파일 (Compile) | 전처리된 소스를 어셈블리어로 변환 | `.i` → `.s` |
| 3 | 어셈블 (Assemble) | 어셈블리어를 기계어(오브젝트 코드)로 변환 | `.s` → `.o` |
| 4 | 링크 (Link) | 여러 오브젝트 파일과 라이브러리를 결합해 실행 파일 또는 라이브러리 생성 | `.o` → 실행 파일 |

링크 단계는 [링커와 로더](../../os_memory/executables-and-linking/linking-and-loading.md)에서 다룬다.

### 3.2 디스어셈블과 디컴파일

| 구분 | 디스어셈블 | 디컴파일 |
|---|---|---|
| 변환 | 기계어 → 어셈블리어 | 기계어 → 고급 언어에 가까운 코드 |
| 대응 관계 | 어셈블리어와 기계어는 거의 일대일이라 오차 없는 변환이 가능하다 | 고급 언어와 어셈블리어는 일대일 대응이 없다 |
| 결과 | 정확하지만 큰 바이너리는 이해하기 어렵다 | 원본 소스와 같은 코드는 복원하지 못한다(변수 이름, 주석, 구조 일부 손실) |
| 대표 도구 | `objdump -d`, GDB | Ghidra, IDA의 Hex-Rays 디컴파일러 |

디컴파일 결과의 오차는 대개 바이너리의 동작 이해를 크게 왜곡하지 않으며 분석 효율을 높이므로, 디컴파일러를 쓸 수 있으면 먼저 쓰고 의심스러운 부분은 디스어셈블 결과로 확인한다.

## 4. 예제 코드

원본 예제를 보존한다.

{% code title="add.c" %}
```c
// Name: add.c

#include "add.h"

#define HI 3

int add(int a, int b) { return a + b + HI; }  // return a+b
```
{% endcode %}

{% code title="add.h" %}
```c
// Name: add.h

int add(int a, int b);
```
{% endcode %}

디스어셈블 결과:

```
$ objdump -d ./add -M intel
...
000000000000061a <add>:
 61a:   55                      push   rbp
 61b:   48 89 e5                mov    rbp,rsp
 61e:   89 7d fc                mov    DWORD PTR [rbp-0x4],edi
 621:   89 75 f8                mov    DWORD PTR [rbp-0x8],esi
 624:   8b 55 fc                mov    edx,DWORD PTR [rbp-0x4]
 627:   8b 45 f8                mov    eax,DWORD PTR [rbp-0x8]
 62a:   01 d0                   add    eax,edx
 62c:   5d                      pop    rbp
 62d:   c3                      ret
 62e:   66 90                   xchg   ax,ax
...
```

### 4.1 코드 설명

| 주소 | 명령 | 설명 |
|---|---|---|
| 61a ~ 61b | `push rbp`, `mov rbp,rsp` | 스택 프레임을 만든다 |
| 61e ~ 621 | `mov [rbp-0x4],edi`, `mov [rbp-0x8],esi` | System V 호출 규약에 따라 레지스터 edi(첫째 인자 a), esi(둘째 인자 b)를 스택에 저장한다 |
| 624 ~ 627 | `mov edx,[rbp-0x4]`, `mov eax,[rbp-0x8]` | a를 edx에, b를 eax에 읽는다 |
| 62a | `add eax,edx` | 더한 값이 eax(반환 값 레지스터)에 남는다 |
| 62c ~ 62d | `pop rbp`, `ret` | 프레임을 되돌리고 반환한다 |
| 62e | `xchg ax,ax` | 다음 함수 정렬을 위한 패딩(사실상 `nop`)이다 |

{% hint style="warning" %}
CAUTION: 위 디스어셈블 출력에는 상수 3을 더하는 명령이 없다. 이 출력은 `return a + b;` 버전의 결과이며, 위 `add.c`(`+ HI`)를 같은 방식으로 컴파일하면 `add eax,edx` 뒤에 3을 더하는 명령이 추가될 것이다. 이 환경에서 컴파일하지 않았으므로 미검증이다. 주소(61a 등)는 컴파일러와 옵션에 따라 달라진다.
{% endhint %}

### 4.2 재현 순서(참고)

이 순서는 이 환경에서 실행하지 않았다(미검증).

```
$ gcc -c add.c -o add.o
$ objdump -d add.o -M intel
```

## 5. 약어·용어

| 용어 | 뜻 |
|---|---|
| JIT | Just-In-Time 컴파일. 실행 중에 기계어로 번역 |
| 오브젝트 코드 | 컴파일·어셈블 결과의 기계어 파일(`.o`, `.obj`) |
