## 1. 목적

컴파일 결과인 오브젝트 파일은 아직 실행할 수 없다. 링커(linker)가 이들을 하나로 묶고, 로더(loader)가 실행 파일을 메모리에 올린다. 이 문서는 두 단계가 하는 일을 정리한다.

## 2. 구성 요소

| 구성 | 시점 | 역할 |
|---|---|---|
| 링커 (`ld`, `link.exe`) | 빌드 | 오브젝트 파일과 라이브러리를 결합해 실행 파일·라이브러리를 만든다 |
| 로더 | 실행 | 실행 파일을 메모리에 올리고 실행을 시작한다. Linux에서는 커널이 세그먼트를 매핑한다 |
| 동적 링커 (`ld.so`) | 실행 | 공유 라이브러리를 올리고 심볼 주소를 해결한다 |

## 3. 동작 원리

### 3.1 링커가 하는 일

| 단계 | 내용 |
|---|---|
| 심볼 해결(symbol resolution) | 각 심볼 참조(함수·전역 변수 사용)를 하나의 심볼 정의에 연결한다. 정의가 없으면 `undefined reference` 오류, 정의가 둘이면 `multiple definition` 오류가 난다 |
| 재배치(relocation) | 입력 섹션을 합쳐 최종 주소를 배정하고, 코드 안의 주소 참조를 그 주소로 고친다. 재배치 정보(`.rela.*`)를 쓴다 |

* 함수와 초기화된 전역 변수는 강한 심볼, `__attribute__((weak))`로 표시한 심볼은 약한 심볼이다. 강한 심볼이 둘이면 오류이고, 강한 하나와 약한 여럿이면 강한 쪽이 선택된다. 초기화하지 않은 전역 변수를 여러 파일에 정의하는 코드는 GCC 10부터 기본 설정(`-fno-common`)에서 중복 정의 오류가 난다.
* 정적 라이브러리(`.a`)는 링커가 필요한 오브젝트 멤버만 골라 실행 파일에 복사한다.
* 동적 라이브러리는 이름과 심볼 목록만 기록하고 실제 주소는 실행 시에 정한다([동적 링크 라이브러리](dll.md)).

### 3.2 예: add.c와 main.c

(참고용 명령, 실행하지 않았다.)

```
$ gcc -c add.c -o add.o      # 컴파일 + 어셈블
$ gcc -c main.c -o main.o
$ gcc main.o add.o -o app    # 링크: main.o의 add 참조를 add.o의 정의에 연결
```

main.o에는 `add`가 미정의 심볼로 남아 있다. 링커가 add.o의 정의를 찾아 호출 위치의 주소를 채운다.

### 3.3 로더가 하는 일

Linux에서 `execve`로 실행 파일을 시작할 때의 흐름이다.

| 순서 | 동작 |
|---|---|
| 1 | 커널이 ELF 헤더를 읽고 프로그램 헤더의 로드 가능 세그먼트(`PT_LOAD`)를 새 프로세스의 가상 주소 공간에 매핑한다 |
| 2 | `.bss` 영역을 0으로 채운다 |
| 3 | 프로그램 헤더에 인터프리터(`PT_INTERP`, 보통 동적 링커)가 있으면 이를 함께 올린다 |
| 4 | 스택을 만들고 인자·환경 변수를 둔다 |
| 5 | 동적 링커가 필요한 공유 라이브러리를 올리고 재배치를 처리한다 |
| 6 | 진입점(`_start`)으로 점프하고, 이후 `main`이 호출된다 |

### 3.4 지연 바인딩

동적 링크된 함수는 보통 처음 호출될 때 주소를 찾는다(lazy binding). 첫 호출은 PLT를 거쳐 동적 링커가 주소를 찾아 GOT에 기록하고, 이후 호출은 GOT의 주소로 바로 간다. 보안 설정(RELRO 등)에 따라 시작 시 모두 바인딩하기도 한다.

## 4. 약어·용어

| 용어 | 뜻 |
|---|---|
| 심볼 | 함수·변수 이름과 주소를 연결하는 항목 |
| 재배치 | 링크·로드 때 주소 참조를 최종 주소로 고치는 작업 |
| 진입점 | 실행이 시작되는 주소(`_start`) |
| RELRO | Relocation Read-Only. 재배치 후 GOT를 읽기 전용으로 만드는 보호 설정 |
