## 1. 목적

쿠버네티스는 여러 대의 서버에서 컨테이너를 배치하고 관리하는 컨테이너 오케스트레이션(orchestration) 도구다. 컨테이너는 애플리케이션이 실행되는 환경을 격리하는 기술이다. 도커 같은 컨테이너 런타임(Container Runtime)이 컨테이너를 실행하고, 쿠버네티스는 그 컨테이너를 여러 노드에 걸쳐 배치하고 상태를 유지한다. 이 문서는 클러스터의 구성 요소와 동작 원리를 정리한다.

K8s는 Kubernetes의 약어다. K와 s 사이에 8글자가 있다.

## 2. 구성 요소

### 2.1 클러스터 구조

| 번호 | 구성 요소 | 위치 | 역할 | 비고 |
|---|---|---|---|---|
| 1 | 클러스터(Cluster) | 전체 | 컨트롤 플레인과 노드의 집합이다 | 노드 1개로도 구성할 수 있다(단일). 둘 이상이면 멀티 노드다 |
| 2 | 컨트롤 플레인(Control Plane) | 노드 | 클러스터를 중앙에서 통제한다 | 원본의 Master Node. 현재 공식 용어는 컨트롤 플레인 |
| 3 | 워커 노드(Worker Node) | 노드 | 컨테이너(파드)가 실제로 실행된다 | 서버 또는 VM 한 대에 해당한다 |

### 2.2 컨트롤 플레인 구성 요소

| 번호 | 구성 요소 | 역할 | 비고 |
|---|---|---|---|
| 1 | kube-apiserver | 클러스터의 모든 요청이 지나가는 API 진입점이다 | `kubectl`, kubelet, 다른 구성 요소가 이 API를 호출한다 |
| 2 | etcd | 클러스터 상태와 설정을 저장하는 키-값 저장소다 | 원본의 "인증을 위한 키, 데이터 저장"에 해당한다 |
| 3 | kube-scheduler | 새 파드를 어느 노드에 배치할지 정한다 | 노드의 남은 CPU·메모리 등을 본다 |
| 4 | kube-controller-manager | 현재 상태를 원하는 상태에 맞추는 컨트롤러를 실행한다 | 예: 파드 수를 지정한 개수로 유지 |

### 2.3 워커 노드 구성 요소

| 번호 | 구성 요소 | 역할 | 비고 |
|---|---|---|---|
| 1 | kubelet | 컨트롤 플레인과 통신하고 노드의 파드 실행과 상태를 관리한다 | 원본의 "ControlPlane과 통신을 담당" |
| 2 | 컨테이너 런타임 | 컨테이너를 실제로 실행한다 | containerd, CRI-O 등. Docker Engine 직접 지원(dockershim)은 쿠버네티스 1.24에서 제거됐다 |
| 3 | kube-proxy | 서비스의 가상 IP로 오는 트래픽을 파드로 전달하는 네트워크 규칙을 관리한다 | 원본은 "노드 간 통신도 프록시를 통해야 가능하다"고 적었다. 실제로는 서비스 트래픽 전달을 담당하며, 노드 간 파드 통신은 CNI 플러그인이 맡는다. 확인 필요 |
| 4 | CNI 플러그인 | 파드 네트워크를 구성한다 | 예: Calico, Flannel. 설치 전에는 노드가 `NotReady`다 |

### 2.4 워크로드 개체

| 번호 | 개체 | 역할 | 비고 |
|---|---|---|---|
| 1 | 파드(Pod) | 쿠버네티스가 다루는 가장 작은 배포 단위다 | 컨테이너 1개 이상을 담는다. 원본의 "Unit(가장 단순한 구조)" |
| 2 | 디플로이먼트(Deployment) | 파드 개수와 업데이트 방식을 선언한다 | 파드 수 유지, 롤링 업데이트 |
| 3 | 서비스(Service) | 파드 집합에 고정된 접속 주소를 준다 | 타입: ClusterIP, NodePort, LoadBalancer |
| 4 | 네임스페이스(Namespace) | 리소스를 논리적으로 나눈다 | 예: `kube-system`, `default` |

### 2.5 도구

| 번호 | 도구 | 용도 |
|---|---|---|
| 1 | kubectl | API 서버에 명령을 보내는 명령줄 도구다 |
| 2 | kubeadm | 클러스터를 부트스트랩(초기 구성)하는 도구다. 같은 목적의 다른 도구가 여럿 있다 |
| 3 | kind | 컨테이너를 노드로 쓰는 로컬 테스트용 클러스터 도구다 |

## 3. 동작 원리

### 3.1 선언형 관리

1. 사용자가 원하는 상태(예: nginx 파드 2개)를 매니페스트(YAML)로 `kubectl`에 전달한다.
2. kube-apiserver가 요청을 받아 etcd에 저장한다.
3. kube-controller-manager가 현재 상태와 원하는 상태의 차이를 확인하고 파드 생성을 요청한다.
4. kube-scheduler가 파드를 실행할 노드를 정한다.
5. 해당 노드의 kubelet이 컨테이너 런타임에 컨테이너 실행을 지시한다.
6. 파드가 죽으면 컨트롤러가 다시 만들어 개수를 유지한다.

### 3.2 서비스 접속

1. 파드는 생성될 때마다 IP가 바뀔 수 있다.
2. 서비스가 파드 집합 앞에 고정 주소를 둔다.
3. kube-proxy가 서비스 주소로 온 요청을 해당 파드로 전달한다.
4. NodePort 타입이면 모든 노드의 같은 포트(기본 범위 30000-32767)로 외부에서 접속할 수 있다.

### 3.3 확장성

노드를 추가하거나 제거해 서비스 규모를 조정할 수 있다. 컨테이너가 이미지 기반이므로 같은 이미지를 여러 노드에 반복 배포할 수 있다.

## 4. 약어·용어

| 용어 | 풀이 |
|---|---|
| K8s | Kubernetes의 약어 |
| CNI | Container Network Interface, 컨테이너 네트워크 규격 |
| CRI | Container Runtime Interface, kubelet이 런타임과 통신하는 규격 |
| etcd | 분산 키-값 저장소 |
| EKS | Elastic Kubernetes Service, AWS의 관리형 쿠버네티스 서비스 |

{% hint style="warning" %}
CAUTION: 원본은 EKS를 "엘라스틱 서치 쿠버네티스 시큐리티"로 적었다. EKS는 Amazon Elastic Kubernetes Service이며 Elasticsearch와 관계가 없어 정정했다.
{% endhint %}
