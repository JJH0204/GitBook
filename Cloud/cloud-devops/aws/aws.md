## 1. 목적

AWS를 쓰기 전에 알아야 할 두 가지 구조를 정리한다. 하나는 누가 어떤 권한으로 접속하는지(접근 관리), 다른 하나는 어떤 트래픽을 허용하는지(보안 그룹, 네트워크 ACL)이다.

## 2. 구성 요소

### 2.1 계정과 접근 관리

| 번호 | 구성 요소 | 역할 | 비고 |
|---|---|---|---|
| 1 | 루트(root) 사용자 | 계정을 만든 최상위 사용자다. 모든 권한을 가진다 | 결제 카드(마스터/비자 등)가 필요하다. 일상 작업에 쓰지 않는다 |
| 2 | IAM(Identity and Access Management) 사용자 | 사용자별로 권한을 다르게 줄 수 있는 계정이다 | 콘솔 로그인과 원격 접속에 쓴다 |
| 3 | IAM 그룹과 정책 | 그룹에 정책(권한 규칙)을 붙이고 사용자를 넣는다 | 사용자 생성과 그룹 생성의 순서는 상관없다. 정책은 JSON 형식이다 |
| 4 | 액세스 키(Access Key) | CLI로 접속할 때 쓰는 키다 | 분실하면 보안에 취약하다. 문서에 쓰지 않는다 |
| 5 | MFA(다중 인증) | 2차 인증이다 | 설정을 권장한다 |
| 6 | AD(Active Directory) | 여러 디렉터리를 하나의 도메인으로 관리한다 | 외부 인증 서버로 접근 자격을 검증한다 |
| 7 | 키 페어 | EC2 원격 접속에 쓰는 키다 | 이미 만든 키를 올려 쓸 수 있다 |

접근 제어 방식은 RBAC(Role-Based Access Control, 역할 기반 접근 제어)다. 역할(그룹)에 권한을 붙이고 사용자를 역할에 넣는다. 사용자별로 권한을 따로 붙이는 방식보다 관리가 쉽다.

### 2.2 네트워크 접근 제어

| 번호 | 구성 요소 | 적용 단위 | 상태 | 동작 |
|---|---|---|---|---|
| 1 | 보안 그룹(Security Group) | 인스턴스 | 상태 유지(stateful) | 인바운드(inbound) 요청을 허용하면 그 응답은 아웃바운드(outbound) 정책과 무관하게 나간다 |
| 2 | 네트워크 ACL(Access Control List) | 서브넷 | 상태 비유지(stateless) | 인바운드와 아웃바운드 정책을 따로 적용한다. 규칙 순서가 중요하다 |

| 항목 | 보안 그룹 | 네트워크 ACL |
|---|---|---|
| 기본값 | 인바운드를 모두 거부한다 | 서브넷에 연결하는 기본 네트워크 ACL은 모든 트래픽을 허용한다. 새로 만든 네트워크 ACL은 모두 거부한다 |
| 규칙 종류 | 허용 규칙만 쓴다 | 허용과 거부 규칙을 쓴다 |

{% hint style="info" %}
NOTE: 원본은 보안 그룹의 인바운드·아웃바운드를 "동일하게 적용한다"고 적었다. 보안 그룹은 상태 유지 방식이라 요청에 대한 응답이 자동 허용되는 것이므로 표현을 정정했다. 확인이 필요하다.
{% endhint %}

### 2.3 부가 서비스

| 번호 | 서비스 | 설명 | 비고 |
|---|---|---|---|
| 1 | 로그 기록 서비스 | 접근 기록을 열람하고 분석한다 | 요금이 부과된다 |
| 2 | 탄력적 IP(Elastic IP) | 고정 IP를 할당한다 | 인스턴스에 연결하지 않으면 요금이 부과될 수 있다 |
| 3 | 리전(Region) | 서비스를 둘 지역이다 | 원본은 서울로 설정했다 |

## 3. 동작 원리

1. 루트 사용자로 계정을 만들고 MFA를 설정한다.
2. IAM 그룹을 만들고 정책을 선택한다.
3. IAM 사용자를 만들어 그룹에 넣는다.
4. 사용자가 콘솔 또는 CLI(액세스 키)로 접속한다.
5. 가상 서버(EC2)를 만들 때 보안 그룹으로 인스턴스 단위 접근을 정한다.
6. 서브넷 단위 접근은 네트워크 ACL로 정한다.
